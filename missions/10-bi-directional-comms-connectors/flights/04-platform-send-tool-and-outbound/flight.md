## Pre-Flight

### Objective

Land the **outbound side** of the connector subsystem: register `send_to_platform_channel` as a built-in tool, widen the `ConnectorClient` Protocol to carry the outbound method, wire the tool through the existing F1 pool to a connector's `ConnectorClient.send(...)`, add per-agent attachment via `AgentConfig.connector_account_ids`, auto-load the tool's schema at session start for connector-attached agents (the deliberate F10 baseline carve-out), compose a connector-aware system prompt (enabled-tool vs disabled-tool directives), and tag the agent's outputs in connector-attached sessions with the right `visibility` value so peer-visible vs operator-only is decided structurally rather than by trust.

After this flight: a connector-attached agent that has the platform-send tool operator-enabled can deliver replies to the external platform via a deliberate tool call; the same agent with the tool operator-disabled still receives inbound and replies into the operator console only, with no outbound code path reachable. Both states are mission-mandated invariants and are pinned by tests. The Admin built-in-tools toggle (existing surface) is the operator's enable/disable lever — no new UI in this flight. The Studio agent-attach UI for connector accounts is Flight 6 territory; F4 ships the data-model field and tests seed it directly. F4 still exercises end-to-end against the F1 `StubPlugin` (now widened with a `send` method) — Discord lands in Flight 8.

### Design Decisions

**`ConnectorClient` Protocol widening, NOT `getattr`-sentinel optional hook**

- **Choice**: Widen the `runtime_checkable` `ConnectorClient` Protocol in `connectors/base.py` to declare `async def send(target: OutboundTarget, content: str) -> SendResult`. Every connector in scope (StubPlugin, Discord at F8, the second connector at F9) implements `send` as a required method. Add a new `SendResult` `@dataclass(frozen=True, slots=True)` alongside the existing `OutboundTarget`, `InboundEnvelope`, `DoctorReport` (mirror their shape).
- **Rationale**: F1's `ConnectorClient` docstring explicitly invited F4 to widen for outbound ("Flight 4 widens this to add an outbound-send method when the platform-send tool needs it"). `runtime_checkable` Protocol widening is additive — existing `isinstance(client, ConnectorClient)` checks remain valid; new code that depends on `send` gets it via duck-typing. The mission constraint "every platform message originates from an explicit tool call" makes outbound non-optional — EVERY connector must support it. The `getattr`-sentinel pattern F3 introduced (`display_channel`) is for genuinely-optional hooks where a sensible default exists at the call site; outbound has no sensible default (silent drop = leakage failure mode; raise = error noise).
- **Trade-off**: A connector author cannot ship a read-only "subscribe to platform messages, never reply" connector under this design without adding a no-op `send` that raises. Acceptable: such a connector violates the mission's bi-directional premise; F10 hardening's "do-nothing on edit/delete" question is the closest analog and resolves the same way (do nothing = explicit no-op, not absent).
- **Documentation**: codify the `protocol-widening-for-required-capability` convention in `agents.md` alongside F3's `optional-plugin-hook-via-getattr-sentinel` codification (both land in leg 6). Citation: this flight's `ConnectorClient.send` widening; pattern is now the established choice when a capability moves from "future" to "required by every plugin in scope."

**`SendResult` shape: `platform_message_id` + `details` dict**

- **Choice**: `@dataclass(frozen=True, slots=True) SendResult` in `connectors/base.py` with two fields: `platform_message_id: str | None` (best-effort — some platforms return one, others don't) and `details: dict[str, Any] = field(hash=False, compare=False)` (frozen-dataclass-with-hash=False-compare=False shape mirroring `DoctorReport.details`). Required at construction; `details` may be `{}`.
- **Rationale**: The minimal viable outbound result. `platform_message_id` is the only field F10's "edit/delete correspondence" question would need — leaving it as `str | None` gives F10 the surface to act without F4 pre-committing to edit semantics. `details` is the forward-compat surface for rate-limit headers, edit timestamps, attachment-id-arrays, etc.
- **Trade-off**: The tool's stringified return wraps the SendResult into a one-line summary (operator-readable). Future flights wanting structured access to `platform_message_id` can read it from the LLM tool-result wire format OR off the `SendResult` dataclass directly when the tool calls into a richer dispatcher. F4's first-pass needs only the string.

**Tool target validation in F4: account-scope only; channel/thread/peer ACLs are F6**

- **Choice**: `SendToPlatformChannelTool.execute()` validates `target.account_id ∈ self._connector_account_ids` (the agent-scoped set passed at factory time). On mismatch: return `"[error] [constraint] account_id <id> is not attached to this agent"` (the standard ConstraintError-formatting wrapper at `tools/base.py:ConstraintError`). Channel-level / thread-level / peer-level ACL enforcement is a documented hook point — leg 2 leaves a one-line `# F6: AllowlistResolver consultation lands here` marker that F6's PR replaces.
- **Rationale**: F4's mission criterion is account-scope ("connector accounts the calling agent is currently attached to"). F6's mission criterion is the finer-grained ACL ("conversation locations the agent has access to per the same allowlist/ACL resolution"). Shipping F4 with just account-scope keeps the leg small and lets F6 land its `AllowlistResolver` Protocol cleanly without F4 pre-committing to the resolution shape.
- **Trade-off**: Between F4 and F6, an operator-misconfigured attachment lets an agent post to any channel within an attached account. The mission's security model already accounts for this — a Discord bot token grants posting rights to a server; the trust boundary is whoever sends messages to the bot. F4-without-F6 is a workable interim state; F6 is the per-channel narrowing, not the foundational gate.

**`AgentConfig.connector_account_ids` mirrors `mcp_source_ids` exactly**

- **Choice**: Add `connector_account_ids: list[str] = Field(default_factory=list)` to `AgentConfig` in `the_one/agent/config.py`, mirror-positioned next to `mcp_source_ids` (~line 76). No `Optional`, no `None`-as-locked-down-NULL — the empty-list default is the no-attached state. `extra="ignore"` on `AgentConfig` (existing) means pre-F4 stored agent rows deserialize cleanly (the field defaults to `[]`).
- **Rationale**: Mirror MCP. The locked-down-NULL semantic that `enabled_tools` / `tool_overrides` / `mcp_overrides` use is for narrow/substitute resolver fields; `connector_account_ids` is a plain attachment list — empty means none, exactly as `mcp_source_ids` already shapes the MCP case.
- **Trade-off**: An operator with a malformed AgentConfig JSON (`"connector_account_ids": null`) sees a Pydantic validation error. Acceptable: matches the same failure mode `mcp_source_ids: null` would exhibit today; the agent-editor JSON serializer always emits `[]`, never `null`.

**Auto-load tool schema at session start via the existing F10 L1 shared-container pattern**

- **Choice**: In `AgentFactory.create()`, after the tool registry is built but BEFORE `Agent(...)` is constructed, IF `config.connector_account_ids` is non-empty AND `send_to_platform_channel` is operator-enabled in the `ToolConfigRepository` (the same `.enabled` value the registry-build filter already consults a few lines earlier in `factory.py:301`), append the tool's schema to `loaded_schemas` and its name to `loaded_tool_names`. The Agent's `_compute_visible_schemas()` returns `[SEARCH_TOOLS, CONTINUE] + self._loaded_schemas`, so the pre-population is the F10 baseline carve-out: at turn 1, the connector-attached agent's tool list is `[search_tools, continue, send_to_platform_channel]`; non-connector agents stay at `[search_tools, continue]`.
- **Rationale**: This pattern is exactly what F10 L1 codified for the search-stub case — the factory pre-mutates the shared `loaded_schemas` / `loaded_tool_names` containers. The Agent doesn't need to know it's connector-attached; the shared-container plumbing already exists. The F10 baseline assertion in `agent/core.py:30-34` documents `search_tools` as "the ONLY non-`continue` schema visible to the LLM at session start"; F4 adds the platform-send tool as the second documented exception, with the comment block at the assertion site updated accordingly.
- **Trade-off**: The connector-attached agent sees three schemas at turn 1 instead of two. The agent's discovery search still works for ANY other tool — it just doesn't have to search for the platform-send tool, which is the whole point ("auto-available to any agent attached to a connector account").

**System-prompt composition: extract free function; factory calls it; AgentConfig keeps signature**

- **Choice**: Create `compose_system_prompt(base: str, persona: str, *, connector_attached: bool, send_tool_enabled: bool) -> str` as a module-level function in `the_one/agent/config.py`. `AgentConfig.get_system_prompt()` keeps its signature `(self) -> str` and calls `compose_system_prompt(BASE_PROMPT, self.system_prompt, connector_attached=False, send_tool_enabled=False)` — non-connector callers (existing WS handler at `interfaces/web/app.py:_spawn_message_processing`, all existing tests) see byte-identical output. `AgentFactory.create()` calls `compose_system_prompt(BASE_PROMPT, config.system_prompt, connector_attached=bool(config.connector_account_ids), send_tool_enabled=<resolved>)` and passes the result as the agent's `system_prompt`. Connector-aware text is appended AFTER `BASE_PROMPT`, BEFORE the persona separator `\n\n---\n\n` — keeps the persona override at the bottom (highest semantic weight for the LLM).
- **Rationale**: `AgentConfig` doesn't know about connector state and shouldn't — the connector state is a factory-time concern (the same way provider config and tool registry are factory-time). Extracting the composition logic to a free function is the minimum-invasive shape: `AgentConfig.get_system_prompt()` stays for back-compat, but the canonical compositions live in one function. Non-connector code paths (the WS handler's `_restore_session` agent recreation, tests) all bottom out at `AgentConfig.get_system_prompt()` and produce byte-identical strings.
- **Trade-off**: The WS handler at `interfaces/web/app.py:469-487` (where `_save_session_to_db` lives) is in a connector-attached session's persistence path BUT does not recreate the agent — that's `_restore_session`'s job, and `_restore_session` runs via `_spawn_message_processing`'s `factory.create()` call. So a WS-typed message into a connector-attached session DOES go through the factory and DOES get the connector-aware prompt. F5's WS-into-dispatcher routing decision (the open mission Known Issue) is the place where this assumption gets validated; F4 documents the assumption as a Pre-Flight invariant.
- **Mid-session enable/disable note** (architect-surfaced): if the operator toggles `send_to_platform_channel` enable/disable during an in-flight turn, the cached `Session.agent` reference keeps the system_prompt that was set at the PREVIOUS `factory.create()`. The new prompt applies at the NEXT `factory.create()` (next session re-join OR next connector-inbound dispatch). This matches existing MCP-attachment mid-session-change semantics (see `app.py:381-385`). Worth a one-line note in the leg-3 flight log entry so operators know toggling the tool doesn't immediately preempt an in-flight turn.

**Dispatcher visibility tagging: post-step pass over new messages, USER messages skipped**

- **Choice**: Extend `dispatch_inbound` in `connectors/_inbound.py` to tag new messages with `visibility` BEFORE the `encode_messages(agent.messages)` call. Logic: snapshot `agent.messages` length before the `agent.step` async-iter loop (call it `pre_step_len`); after the loop completes, walk `agent.messages[pre_step_len:]` and apply:
  - **SKIP** any message with `m.role == Role.USER`. The inbound user message that `agent.step` appends internally at `agent/core.py:138` (`self.messages.append(Message.user(user_input))`) defaults to `visibility=None` (platform-visible) — which is exactly the right tag for peer-originated content. Re-tagging it as `"operator"` would mis-tag the peer's own message as operator-only. Architect-flagged design gap fixed.
  - Default for connector-attached session, NON-user messages: `m.visibility = OPERATOR_VISIBILITY` (the `"operator"` constant from `the_one.connectors.__init__`).
  - EXCEPTION: a `Message` whose role is `TOOL` (tool_result message) AND whose corresponding tool_call (resolved via `m.tool_result.tool_call_id` — the correlation field on the nested `ToolResult` dataclass at `llm/base.py:28-32`, NOT on the `Message` directly — matched against the most recent assistant message's `tool_calls[].id`) had name `"send_to_platform_channel"` AND whose content starts with `PLATFORM_SEND_OK_PREFIX`: `m.visibility = None` (platform-visible). The leg-4 author confirms the correlation shape by reading `llm/base.py:28-32` (`ToolResult.tool_call_id: str`) and `db/codec.py:37-46` (the codec's tool-result encoding).
- **Rationale**: The mission's enforcement-by-construction stance (the tool is the only path to `ConnectorClient.send`) makes leakage impossible regardless of how visibility is tagged — visibility is a presentation-layer metadata, not a security gate. The tagging is correct for the F5 Chat UI's two-layer rendering: peers (read off the connector account's session via Chat UI's connector-bound listing) see only the platform-visible messages; the operator sees the unified history with `visibility="operator"` distinction. The post-step pass is the simplest correct shape — the dispatcher already owns the persist step, and `Message.visibility` mutation is allowed (the dataclass is unfrozen per F3's prerequisite check). The `Role.USER` skip is critical: without it, the peer's own inbound message would be silently re-tagged as operator-only, breaking the visibility-layer contract.
- **Trade-off**: Mutation of `agent.messages` after `agent.step()` completes assumes the agent's in-memory list is the canonical session history at that moment. F3's dispatcher already holds this invariant — `agent.step()` completes; dispatcher reads `agent.messages`; dispatcher encodes-and-persists. F4 adds a `for m in agent.messages[pre_step_len:]: if m.role == Role.USER: continue; m.visibility = ...` step BEFORE the encode. No race; same thread.

**Tool's tool-execute success sentinel string**

- **Choice**: The tool's execute() returns `f"[platform-send-ok] sent to {account_id}:{channel_id}{thread_clause}: {content!r}"` on success (where `thread_clause` is `f' (thread {thread_id})'` or empty). The dispatcher's visibility tagger matches on the literal prefix `[platform-send-ok]` to decide `visibility=None`. Failure paths return `[error] [constraint] ...` or `[error] ...` per `tools/base.py:ConstraintError` precedent — no `[platform-send-ok]` prefix means `visibility="operator"`.
- **Rationale**: A literal-prefix sentinel is the simplest cross-module contract. The string is grep-able, doesn't require a structured side-channel between tool and dispatcher, and is debuggable. The `f"{content!r}"` wrap on the content escapes embedded brackets so a peer-supplied message of `"[platform-send-ok] fake"` cannot cause the dispatcher to mis-tag a different message.
- **Trade-off**: The literal prefix is a private API between `SendToPlatformChannelTool` and `_inbound.py`. Codify it as a module-level constant in `the_one/connectors/__init__.py` next to `OPERATOR_VISIBILITY` so the literal lives in one place: `PLATFORM_SEND_OK_PREFIX = "[platform-send-ok]"`. Both consumers import it.

**Promote `db/models._now_iso` to public `now_iso` AND rewire `db/repositories.py`'s shadow definition**

- **Choice**: Bundle the F3 debrief carry-forward into leg 4 — with one critical correction surfaced by architect review.
