## Outcome

MCPs become a first-class user-managed capability in the-one. The operator can register, configure, and test MCP servers from a Settings surface; configurations are persisted with sensitive fields encrypted at rest using the same Fernet key + rotation path that already protects LLM-provider credentials. Both transports defined in the current Model Context Protocol specification are supported — process-spawned stdio servers, and remote streaming-HTTP servers with OAuth 2.1 + PKCE token flows. Local stdio servers run inside an OS-level sandbox with a fixed environment allowlist, no inherited host secrets, and an idle-TTL reaper that releases server processes after a period of disuse — mirroring the lifecycle pattern that the interactive shell session tool already uses for ptys. A simplified inspector surfaced from each server's Settings detail page lets the operator verify a connection, list the server's tools, and invoke any tool with form-driven inputs against the live server — covering the minimum needed to prove a configured MCP works before any agent attaches to it. Resources, prompts, sampling, and notifications are deliberately deferred — the inspector and the runtime cover tools-list and tools-call only in this mission. Once configured, an MCP source can be attached to any number of agents through the Studio agent editor's existing MCPs tab, which stops being a stub. Each agent attachment composes through the same two-layer resolver that the built-in tools already use: shared defaults at the source level, narrow-or-substitute overrides at the agent level — so the operator can have one GitHub MCP source defined globally and two agents each with their own substituted personal access token, without duplicating the source. The agent's tool registry is extended to include MCP tools alongside built-in tools, with stable name-spacing so tool names from different servers cannot collide. The runtime is architected for cross-platform support — the sandbox layer is isolated behind a clear abstraction and verified on Linux now; macOS and Windows backends are explicit follow-up work, not in this mission's scope.

## Context

Mission 05 built the operator-controlled tool surface around three categories — filesystem, execution, web — and was deliberately shaped so MCPs could land on top of it without restructuring. Specifically: the two-layer config model (`tool_configs` + `AgentConfig.tool_overrides`), the resolver's per-key Narrow/Substitute dispatch, the encrypted-credential pattern (Fernet + `__MASKED__` sentinel) on `LLMProviderConfig`, the idle-TTL reaper for pty sessions, the `ToolProvider` protocol with `BuiltinToolProvider` as the canonical implementation, and the `mcp_sources` table + `AgentConfig.mcp_source_ids` field — all of these were sized with MCPs as the next consumer. M05 F2's substitution unit-test even uses an MCP-shaped fixture to lock in the resolver's substitution semantics ahead of any real MCP work.

The MCP specification has moved meaningfully since M05 closed. The current revision (`2025-11-25`) deprecated the older HTTP+SSE transport in favor of Streamable HTTP, made RFC 8707 Resource Indicators and audience-bound tokens mandatory for OAuth flows, and added experimental primitives (Tasks, URL elicitation, Icons) that this mission does not need. The Python `mcp` SDK at the 1.x line is stable and async-native, covering both client and server roles; `the-one` only consumes the client side. Stdio servers receive credentials via environment variables and SHOULD NOT use OAuth per the spec; remote servers use OAuth 2.1 + PKCE and the host MUST audience-validate tokens and MUST NOT pass them through to upstream services. These constraints shape the encryption model (different fields are sensitive on different transports) and the attach/override surface (env-var substitution for stdio, token substitution for remote).

Local-MCP sandboxing is the design choice with the most divergence from the rest of M05's posture. The spawned-subprocess-with-an-env-allowlist pattern is a "trip-wire, not fence" model — appropriate for built-in execution tools the operator wrote, insufficient for arbitrary third-party MCP servers the operator is being asked to trust. The right reference is the bubblewrap-on-Linux + sandbox-exec-on-macOS approach published as `@anthropic-ai/sandbox-runtime`: process-tree isolation, no container engine, no IDE-environment standard, no Docker Desktop hard dependency on Mac/Windows. Dev Containers are explicitly the wrong layer for this — that spec is designed for IDE workspace materialization, not for spawning short-lived service processes; it would require Docker Desktop on the eventual Mac/Windows targets and consume ~95% of a JSON spec's surface area for the ~5% of it that actually applies. Linux is the only verified target for this mission; macOS and Windows backends slot behind the same sandbox-adapter interface as follow-on work.

Today, the Studio agent editor's MCPs tab renders a one-line stub message; the `mcp_sources` REST endpoints exist but have no spawn or connect logic; `AgentConfig.mcp_source_ids` is persisted but does not affect the agent's tool registry. This mission turns those stubs into a working capability and lands the operator surfaces (Settings page, simplified inspector, Studio attach + override panels) needed to make MCPs usable end-to-end.

## Success Criteria

- [ ] The operator can register, edit, and remove MCP server definitions through a Settings surface that follows the existing design language and admin patterns, with sensitive configuration fields persisted in encrypted form using the same key + rotation pipeline that already protects LLM-provider credentials
- [ ] Both transports defined in the current MCP specification are supported by the runtime — process-spawned stdio servers and remote streaming-HTTP servers — with capability negotiation handled per the spec's lifecycle requirements (initialize handshake, version negotiation, post-init protocol-version header for HTTP)
- [ ] Remote MCP servers requiring OAuth are usable end-to-end from the Settings UI without manual bearer-token paste: the operator initiates the flow, completes consent through the identity provider, and the resulting access and refresh tokens are stored encrypted and used on all subsequent calls — covering the spec's mandatory protections (PKCE, RFC 8707 Resource Indicators on auth and token requests, audience-bound tokens, refresh-token rotation, no token-passthrough to upstream services)
- [ ] Locally spawned MCP server processes run inside an OS-level sandbox with a fixed environment allowlist, no inherited host secrets, and a clear extension seam for additional platform backends; the implementation is verified on Linux against a reference local MCP server
- [ ] Idle local MCP server processes are reaped after a configurable period of disuse and respawned transparently on next use, with the FastAPI lifespan integrated cleanly so the server process tree is drained on shutdown
- [ ] A simplified inspector accessible from each MCP source's Settings detail page lets the operator verify the connection lifecycle, view the server's negotiated capabilities, list its tools with full input-schema visibility, and invoke any tool with form-driven inputs against the live server — covering the tools-list and tools-call subset of the inspector's surface
- [ ] An agent can be configured to attach to any number of registered MCP sources through the Studio agent editor's MCPs tab; the attached MCP servers' tools become callable by the agent during a session alongside the built-in tools
- [ ] Per-agent override of MCP source configuration is supported through the same resolver pattern the built-in tools already use, so an operator can have one MCP source globally defined and multiple agents each with their own substituted credential without duplicating the source definition
- [ ] When two attached MCP servers expose tools with the same short name, both remain individually addressable from the agent's tool registry under stable name-spacing rules that prevent collisions and remain readable to the LLM
- [ ] Credentials never appear in plaintext outside the encryption boundary — not in API responses, not in logs, not in the inspector trace pane — and the existing edit-form sentinel pattern is preserved so an operator can re-save an MCP source without retyping its secrets
- [ ] Agent configurations referencing an MCP source that no longer exists, or attached to a server that fails to start, fail gracefully — the agent runtime continues to serve the remaining tools and surfaces the failure to the operator without taking the chat session down
- [ ] Each layer of the integration has automated coverage proving its contract — the encrypted persistence layer, the client-side connection lifecycle for both transports, the sandbox spawn path, the idle-TTL reaper, the resolver's substitution behavior on MCP-shaped overrides, the tool-name-spacing logic, and the inspector's tool-list / tool-call round-trip
- [ ] The Settings MCP section, the simplified inspector, and the Studio MCPs tab all meet the M04/M06 design-language quality bar without alignment-flight rework
- [ ] An MCP-protocol version is pinned in code with an explicit upgrade path documented; the integration capability-gates spec features so that running against a server announcing an older or differently-capabled handshake degrades cleanly rather than crashing

## Stakeholders

- **Primary user**: Solo developer/operator who wants to compose external capabilities (GitHub, Slack, filesystem servers, internal-tool MCPs) into the-one's agents without writing those tools by hand, and who wants confidence that secrets are stored safely and that local servers can't read host secrets they shouldn't see
- **Future-platform user**: The same operator on macOS or Windows once the desktop-app form factor lands — no Linux-only assumptions in the sandbox layer or the spawn semantics should leak into their experience
- **Future agents**: Specialized agents the operator configures with curated MCP attachments — a coding agent attached to a filesystem MCP and a GitHub MCP, a research agent attached to a web-search MCP, a private-life agent attached to a personal-calendar MCP — each carrying its own substituted identity where appropriate
- **MCP server authors / community**: This mission's wire-shape compliance against the current spec is a contract with everyone shipping MCP servers; spec drift between this mission and a server author's reference implementation is the failure mode to design against

## Constraints

- **`MCPClient` exception-translation contract is a cross-flight invariant**: `MCPClient.{connect, list_tools, call_tool}` raise EXACTLY one of `MCPVersionMismatch`, `MCPAuthRequired`, `MCPSandboxError` (stdio only), or `MCPConnectionError` (catchall). `MCPToolProvider.get_tools_for_agent` graceful-skips all four. Adding a fifth typed exception to this surface requires updating BOTH the translator and every consumer's match list — see `CLAUDE.md` "MCP Error Translation Contracts" for the canonical contract.
- **Spec compliance against a moving target**: pin the official MCP Python SDK at an **exact** version (`mcp==X.Y.Z`, not a compatible-release `~=` bound) and capture the targeted spec revision in a `_PINNED_PROTOCOL_VERSION` module constant. Document the pinned revision and the upgrade procedure in code comments. Capability-gate spec features so an interaction with a server announcing a different revision degrades rather than crashes. Avoid building hard dependencies on experimental primitives (Tasks, URL-mode elicitation, Icons) added to recent revisions
- **Single-key encryption reuse, not a parallel key**: MCP-source sensitive fields encrypt and decrypt through the same `Encryptor` instance and key file as LLM provider credentials. Key rotation rotates both surfaces in one pass; the masked-edit-form sentinel pattern is preserved across both
- **Sandboxing is OS-level, not container-based**: local MCP servers spawn into an OS-native sandbox (bubblewrap on Linux as the verified backend; macOS and Windows backends slot behind the same adapter interface as follow-up missions). Dev Containers, Docker, and any Docker-Desktop-requiring abstraction are explicitly out of scope for the sandbox layer — they compose poorly with the desktop-app long-term form factor and the platform-licensing reality on Mac and Windows
- **Sandbox adapter contract is paper-exercised against unshipped backends before locking**: the `MCPSandbox` adapter that Flight 3 lands ships with a Linux-only implementation, but its interface is validated against at least one paper exercise of macOS `sandbox-exec` and Windows `AppContainer` + Job Objects shapes during design — what guarantees each backend can give (network policy, FS scoping, resource caps, supervision) is not uniform, and writing the adapter Linux-shaped will force a rewrite when the second backend lands. The interface has minimum-required guarantees (env-allowlist, FS scope, network policy, process supervision) and explicit best-effort/optional capabilities; backends document which optional capabilities they implement
- **CI compatibility for the sandbox is verified before the backend lands**: the existing CI runs tests inside `mcr.microsoft.com/playwright/python:v1.58.0-jammy` without `--privileged`. Bubblewrap requires `CAP_SYS_ADMIN` or unprivileged-user-namespaces. Flight 3's first leg probes whether `bwrap` runs in the existing CI container with current privilege grants and either confirms compatibility or surfaces required CI changes — before committing to the bubblewrap backend
- **Subprocess environment is hardcoded-allowlist plus operator-defined env vars from the MCP source's encrypted config — nothing else passes through**: the existing 8-key allowlist (`PATH, HOME, USER, LOGNAME, LANG, LC_ALL, TERM, TZ`) governs MCP child processes; the MCP source's configured environment variables overlay this allowlist and are decrypted at spawn time. Nothing else from the host environment reaches the child
- **Idle-TTL reaper pattern, not on-demand**: local MCP server processes are kept warm across calls within an idle window then reaped, mirroring M05 F4's pty session reaper. Per-(agent, source) registry, single async reaper task, FastAPI lifespan integration. Default idle TTL configurable; the mechanism not optional
- **OAuth flows for remote servers ship end-to-end, not as a manual-paste fallback**: SSO-backed remote MCPs are the primary remote use case, so the operator MUST be able to complete an OAuth 2.1 + PKCE flow from the Settings UI — discovery via `WWW-Authenticate` / RFC 9728 protected-resource metadata, RFC 8707 Resource Indicators on auth and token requests, audience-bound tokens, refresh-token rotation, never-passthrough to upstream APIs. Manual bearer-token paste is NOT the supported v1 path; the full flow lands in this mission. Client registration follows the spec's priority order (pre-registration → Client ID Metadata Documents → Dynamic Client Registration → user-entered) with the resolution between auth-code and device-code shape decided in flight design
- **Tool-name collisions are resolved by stable namespacing, not by silent shadowing**: when two attached servers expose `read_file`, both remain callable from the agent under names the LLM can disambiguate. Namespacing scheme is per-flight design, not per-call ad hoc
- **Two-layer config / two-layer override extension, not a parallel system**: per-agent attach uses `AgentConfig.mcp_source_ids`; per-agent override uses an MCP-shaped extension of the existing `tool_overrides` shape (or a parallel keyed dict modeled on it — design choice). The resolver dispatch is the same Narrow/Substitute resolver M05 F2 landed
- **Inspector covers tools-list and tools-call only in this mission**: resources, prompts, sampling, completions, notifications, and the experimental Tasks primitive are explicitly deferred. The inspector's UI shape is designed so those surfaces can be added later without a rewrite
- **Agent-loop semantic changes are limited to a documented pause/resume primitive for human-in-the-loop signals (F5 amends this constraint)**: the agent step loop continues to dispatch by tool name; MCP tool calls are routed through a per-server provider that translates to JSON-RPC `tools/call` and renders the result content blocks back into the agent's tool-result string format. The continue-tool turn-keeping signal, the iteration cap, and the capability-gate fallback (no-tool-support providers running plain chat) are unchanged. **F5 amendment (2026-05-07)**: the original "no agent-loop semantic changes" constraint was wrong — F5's lazy-OAuth UX (login-required button surfaces in chat at first 401; modal opens consent flow; agent retries the original tool call after `auth_resolved`) requires a small pause-and-await-human primitive in the loop. F5 introduces ONE new tool-result type (`auth_required`) that the loop recognizes and treats as "yield to human, pause execution, await `auth_resolved` event from the WebSocket, then re-dispatch the same tool with the original arguments." The iteration cap, continue-tool signal, capability-gate fallback, and dispatch-by-tool-name are all unchanged. This is the only sanctioned loop-level extension; further pause/resume primitives need explicit mission-constraint amendment
- **Cross-platform-ready architecture, Linux-verified for now**: sandbox layer, process spawn, IPC framing, signal handling — all behind a clear abstraction with no Linux-only assumptions in MCP-specific code. macOS and Windows verification are explicit follow-on work
- **Preserve M01-M06 functionality**: chat persistence, agent CRUD, provider management, the Built-in Tools admin section, browser tests, the deploy pipeline, and the design language all continue working
- **Python 3.11+, async throughout**: unchanged
- **Small-model friendly**: tool descriptions surfaced from MCP servers and connection-error messages must be navigable by 7B-class models; format error strings clearly, no clever exception types

## Open Questions

- **Encryption granularity at the storage layer**: encrypt the entire `mcp_sources.config` JSON blob as a single ciphertext (simplest, mirrors LLM-provider `api_key` exactly — but note that the LLM-provider precedent is a single dedicated column, NOT directly translatable to a free-form blob whose sensitive subset varies by transport), or segregate sensitive fields (env vars marked sensitive, tokens, headers) from non-sensitive ones (command, args, URL) so the non-sensitive parts remain searchable and renderable in admin UI without a decrypt round-trip. **Resolved in Flight 1 design — this decision is a precondition for Flight 2's connect path that reads decrypted env vars at spawn time, so it must commit at F1 design, not slip into F1 implementation discoveries**
- **Override surface shape**: extend `AgentConfig.tool_overrides` to host MCP-source-keyed entries (single dict, single resolver, name collision risk between built-in tool names and MCP source names), introduce a parallel `mcp_overrides` field on `AgentConfig` (clean separation, two resolver call sites), or carry overrides on a sibling table keyed by `(agent_id, mcp_source_id)`. Resolved in Flight 4 design
- **Tool-name namespacing scheme**: prefix every MCP tool with the MCP source name (`{source}__{tool}` or similar separator), expose tools under a flat namespace and resolve collisions only when they occur, or surface a per-agent rename surface so the operator chooses. The chosen scheme must remain readable to small LLMs and stable across server-side tool-list changes. Resolved in Flight 4 design
- **MCP source identity for the resolver**: today, `tool_configs` is keyed by tool name. MCP sources are keyed by ID. The resolver layer needs a consistent shape to compose the layers — extend the resolver to accept either-keying, normalize MCP sources by name at compose time, or restructure `tool_configs` to be ID-keyed too (with migration cost). Resolved in Flight 2 or 4 design
- **Sandbox profile defaults for local MCP servers**: read-only filesystem outside an explicit per-source writable scope, no network by default with an opt-in for servers that need outbound calls (fetch / search / API), or network-on-by-default with the operator narrowing per source. The default sets the trust model — picking the safer-by-default that keeps the common case (filesystem MCP, local DB MCP, sqlite MCP) usable. Resolved in Flight 3 design
- **Connection lifecycle binding**: connect to attached MCP servers eagerly at `AgentFactory.create()` time (slow agent build but immediate tool availability), connect lazily on first tool call (fast build, first-call latency surprises the LLM), or maintain a warm-pool with a parallel connection-during-build. Resolved in Flight 4 design
- **Unit-of-warming for the local-MCP process registry**: is the warm process keyed by `(agent, source)` (per-agent isolation, override-friendly, multiplies process count by agent count for shared sources) or by `source` (one warm process per registered MCP source, shared across agents until any agent's credential override forces a per-agent process)? The override case forces per-agent processes regardless; the no-override case is the real choice. The pty pattern from M05 F4 doesn't answer this — pty sessions are inherently per-agent. Resolved in Flight 4 design
- **OAuth flow shape**: full flow ships end-to-end (decided at the mission level — see Constraints). Open: device-code vs auth-code-with-loopback-redirect for the operator's consent step, and the client-registration path (pre-registered well-known clients per provider, Client ID Metadata Documents, or Dynamic Client Registration). Resolved in Flight 1 or 5 design
- **MCP source vs MCP attachment in the existing UI grammar**: are MCP sources first-class entities like LLM providers (`/api/mcp-sources` already exists, REST CRUD), peer to providers in the Settings nav, with the Studio MCPs tab attaching them to agents — and does the term "source" survive into the operator-facing UI, or does it become "MCP server" / "MCP" everywhere user-visible. Resolved in Flight 1 design
- **Reference server choice for tests and HAT**: depend on the `mcp-server-everything` npm package as a CI fixture (network-fetched at test time, slows CI, breaks under sandbox/network restrictions), ship an in-repo minimal stdio MCP server fixture written in Python (likely via FastMCP for low-boilerplate authoring — small but real maintenance burden), or both. Resolved in Flight 2 design
- **Agent-mode override UI for MCP credentials**: surface the MCP-source's configured env-var/header fields in the Studio MCPs tab as a "set per-agent override" affordance (mirroring the per-agent built-in-tool override panel), with the same `__MASKED__` sentinel for unchanged values. Resolved in Flight 6 design
- **Disabling individual tools within an attached MCP server**: agent-level allow/deny over the server's tool-list (mirror `enabled_tools` / `disabled_tools` shape per-attachment), or accept the entire server's surface as one. Resolved in Flight 4 or 6 design

## Known Issues

> Populated as flights surface them.

- [x] **`MCPClient.disconnect` teardown noise** — discovered in F2 L7 HAT; F5 L1 landed `_open_*_transport_stack` non-CM helpers + dispatcher rewrite to retire the warning under F4-pool-routed paths; **F6 Tier-1 HAT verified retirement on 2026-05-08** (caplog count = 0 across 3 agent builds, 2 tool calls, and 1 full lifespan shutdown_drain — including a uvicorn WatchFiles reload that exercised the per-entry `_evict` → worker `finally` → disconnect path under real bwrap subprocess teardown). F4's worker-task-per-entry pattern + L1's dispatcher-owned-stack mechanism work as designed against real subprocess teardown.

- [ ] **Server-side truncation of verbose tool results not surfaced to operator/agent** — discovered in F6.5 L4 HAT against live Cloudflare API MCP. Cloudflare's `mcp__CloudFlare_API__search` returns search results capped at some character/byte limit; the cut-off lands mid-string mid-property (e.g. `"/zones/{zone_id}/acm/custom_trust_store/{custom_origin_trust_store` — no closing quote, no closing brace) with no `pagination` / `truncated` / `has_more` indicator in the response payload. The agent receives the truncated JSON-fragment as-is, sees malformed JSON in tool-result, and either silently mishandles it or generates prose without a follow-up tool call. The-one's tool-result rendering layer has no truncation detection — codebase grep for `truncat|MAX_CHARS|2048|cap_chars` in `the_one/mcp/` and `the_one/agent/` returns 0 hits in production paths. **Mitigation candidates** (deferred, not in F6.5 scope): (a) detect malformed-JSON tool results and surface a "[possibly truncated by server]" hint to both agent + chat UI; (b) auto-retry with narrower search terms when the result string looks truncated; (c) add a max-result-length tool description hint per attached source. **Affects**: any verbose-output MCP server (Cloudflare, GitHub on long file lists, anything that batches). Not the-one-specific — this is the MCP spec's silence on pagination.
