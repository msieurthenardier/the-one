# Mission: Discord Connector Depth & Robustness

**Status**: planning

## Outcome

The Discord connector becomes the operator's daily-driver bot platform — robust enough to keep online across a working day, easy enough to set up that an operator with no internal knowledge of the-one's substrate can register a Discord application, attach it to one or more agents, scope which users/channels/servers/roles can drive which agent, and watch the agents participate in real conversations on the operator's Discord without ever needing to hand-edit JSON, look up Discord IDs externally, or guess at the system prompt the agent runs under. Every step of that workflow ships a Discord-shaped UX rather than the M10 generic-kv-config substrate: the connector type registers as "Discord" in the connector-type registry and renders a Discord-shaped creation/edit form (bot token, intents, optional guild scoping, invite-URL helpers); the allowlist editors are searchable dropdowns populated from the live bot's view of the users, channels, servers, and roles it can actually reach, not free-form chip inputs; the per-attached-agent UI on the Connectors screen surfaces username / server / channel / role terminology (rather than the substrate's "peer / group" generic terms) and lets the operator detach an agent from the connector without leaving for Studio; the platform-side slash commands (`/agents`, `/talk_to`, `/whoami`, `/new`, `/reset`, `/help`) are end-to-end validated against the real Discord bot with ephemeral responses where appropriate; peer attribution flows from the gateway all the way through to the Chat UI so the operator can see WHICH Discord user said WHAT in the unified history; and the agent decides whether to respond to a given channel message via an explicit policy — auto-respond when @mentioned, otherwise use a lightweight inference pre-step to decide whether the message warrants engagement — rather than the M10-shipped "auto-relay every reply" blanket behavior which makes the bot too chatty in active channels. The methodology improvements from M10's debrief land here too: the operator-editable per-account system-prompt directive surface, the account-keyed pool primitive that replaces F8's sentinel-wrapper footgun, the audit-log inspector for routing decisions, real-traffic HATs replacing M10's stub-validated criteria. The end state — verified by a Chrome-driven repeatable HAT script that the agent runs autonomously while the operator is logged into Discord — is a Discord connector the operator trusts to leave running, and a workflow the operator can repeat from scratch for a new bot in under fifteen minutes without consulting documentation or source.

## Context

M10 (Bi-directional Communication Connectors) landed F1-F8 over six months and shipped a working Discord connector — but the operator's framing at debrief was unambiguous: *"we did not fully test all of the criteria and its clear we have gaps, this flight and mission put most of the pieces together but its far from shippable."* The M10 debrief documents the substrate-vs-shippable distinction: roughly 21 of 27 mission criteria met-or-substantially-met, with 4 criteria explicitly deferred to a follow-on Discord-depth mission and 7 criteria only HAT-validated against the happy path. F9 (second connector) and F10 (cross-connector hardening) were operator-deferred mid-mission after F8 HAT, with the explicit rationale that Discord's depth requirements exceeded the original flight plan and the follow-on mission would address Discord first before any second connector landed.

This is that follow-on mission. The scope is bounded by what M10 left undone PLUS the operator-surfaced polish list that emerged during F8 L11 HAT and the daily-driver use that has been happening since F8 landed. Specifically:

- **The substrate is fixed.** The connector plugin contract, the encrypted-credentials pipeline, the dispatcher 12-step, the ACL resolver, the routing engine, the command surface, the lifecycle pool, the two-visibility-layer message model — all of these are sound architectural primitives that survived F8 against a real Discord gateway. This mission does NOT re-litigate them. It extends, polishes, and validates them against real Discord traffic.
- **Discord-shaped UX is the dominant deliverable.** M10 generalized everything to the connector substrate; this mission re-specializes the user-facing surfaces (creation form, allowlist editor, connector detail page, Chat UI attribution) to speak Discord — usernames, servers, channels, roles, invite URLs — without breaking the substrate's connector-agnostic shape underneath. Future connectors continue to inherit the substrate; their own Discord-shaped equivalents are additive on top.
- **Live-traffic HAT replaces stub validation.** M10's deferral list includes "live-traffic multi-agent routing HAT," "real-platform DM pairing HAT," and "rate-limiting + backpressure live-load HAT." This mission delivers them — and the methodology improvement that makes them sustainable: a Chrome-driven HAT script (browser MCP available; operator logs into Discord; the agent drives Discord round-trips through the browser DOM and observes both the platform-visible side and the operator-console side). The intent is that future Discord-touching flights run the same HAT script as a fast regression gate rather than reconstructing a manual HAT walk from scratch.
- **The "what is pairing for?" question is on the table.** Pairing is the unknown-sender gate — a pre-shared one-time code that a stranger DMing the bot must include as `PAIR <code> <message>` to get past the allowlist and become an approved peer. It's correctly architected as a connector-agnostic primitive, but in the Discord context it competes with a more Discord-native flow: when an unknown user DMs the bot, surface a notification in the Chat UI and let the operator approve them with one click, rather than the operator having to share a code out-of-band. This mission resolves whether pairing stays (clarified through better onboarding UX), is replaced (Discord-native approval flow), or runs alongside the new flow as a fallback.
- **Mentions-aware response policy is a new behavioral primitive.** F8 L11 Fix #4 made auto-relay the default — every plaintext agent reply auto-posts to the platform — which was the right call for solving the "Sonnet 4.7 ignores the MUST-call-tool directive" problem at HAT but makes the bot too chatty in active multi-user channels. The Discord-daily-driver use case needs a more discriminating policy: when the bot is `@mentioned`, auto-respond (the user explicitly asked); otherwise the agent runs an inference pre-step ("does this message warrant a response?") and stays silent unless the answer is yes. The policy must be configurable per agent and per channel so the operator can set "this agent always responds in this channel" or "this agent only responds when @mentioned anywhere."

The success of this mission is what M10's debrief called the missing posture: **shippable.** Not "the substrate works"; not "Discord landed for the happy path"; not "we have 23/27 criteria with caveats." A Discord connector the operator runs as their daily driver, and a repeatable verification artifact (the Chrome HAT script) that proves it stays that way.

## Success Criteria

- [ ] The existing `'discord'` connector-type registration (M10 F8) grows a Discord-shaped UI surface on top of the substrate's connector-type contract: selecting Discord in the connector-account creation flow takes the operator into a Discord-shaped form (bot token field with masked-edit, intents selector with safe defaults, optional guild scoping, invite-URL helper) rather than the generic kv-config form; the substrate's connector-type six-layer checklist (Pydantic Literal, registry, schema CHECK constraint, API gating, frontend badges/tokens, default-config layer) is the contract the Discord-shaped surface satisfies; non-secret typed fields (intents, guild scoping) land in `account.config` rather than `account.secrets` per the existing encryption-boundary discipline
- [ ] Every Discord-touching user-facing surface speaks Discord vocabulary (username, server, channel, role) where the substrate uses generic vocabulary (peer, group); the generic vocabulary remains in code for connector-agnostic plumbing, but no Discord-using operator sees the word "peer" in the UI on a Discord connector
- [ ] The allowlist editor for a Discord connector account (account-scope and per-agent overlay) replaces M10's free-form chip-list with searchable dropdowns sourced from the live bot's view of the Discord users, channels, servers, and roles it can actually reach; the operator types to filter and selects from real entries rather than pasting in IDs from external Discord-developer-mode lookups; entries that the bot can no longer see (user left server, channel deleted, bot kicked) are flagged in the editor with a stale-entry indicator
- [ ] The routing-rules editor for multi-agent Discord accounts uses the same searchable-dropdown data source as the allowlist editor — channel selection and per-(channel, user) overrides surface real Discord channels and usernames, not free-form text; the M10 debrief's "operator typed `#channel-name`, got 'No agents available'" failure mode is structurally prevented
- [ ] Multi-user routing is end-to-end validated against a real Discord server with at least three distinct users sending messages through the same channel — each user resolves to the correct (peer-scoped, agent-scoped) session and the response correctness is observable from the operator console; the F6 per-user ACL overlays exercised under real traffic confirm the M10 structural tests
- [ ] Multi-channel routing is end-to-end validated against a real Discord server with at least three distinct channels each defaulting to a different agent via the routing-rules editor; channel-scoped agent overrides are exercised; the M10 debrief's "real-traffic multi-agent routing HAT" deferral is resolved
- [ ] Multi-peer / multi-agent routing — multiple agents attached to one Discord connector account, multiple users sending to the same connector — is end-to-end validated against real Discord traffic, including the per-(agent, peer) ACL precedent from F6 and the peer-issued `/talk_to <agent>` override from F7
- [ ] The pairing question is resolved: either the pairing flow stays and ships better onboarding UX so an operator (and the peers they want to grant access to) can self-serve it, OR it is replaced by a Discord-native approval flow (unknown DM surfaces in the Chat UI as a pending approval; one-click approve moves the peer into the allowlist), OR both run alongside with a documented precedence; the resolution is HAT-validated against a real Discord DM from an unpaired account
- [ ] From the Connectors screen (Studio or Admin — wherever connector accounts surface), the operator can detach an attached agent from a Discord connector account without navigating to Studio's agent editor; the detach action revokes the agent's access immediately, persists across restart, and the connector account's agent-list updates without a page reload
- [ ] All six platform-side slash commands (`/agents`, `/talk_to`, `/whoami`, `/new`, `/reset`, `/help`) are end-to-end validated against the real Discord bot — invoked from a real Discord client, returning correctly to the invoking user, with per-(agent, peer) permission gating exercised; responses that should be ephemeral (only the invoker sees them) are ephemeral; responses that should be visible to the channel are visible; the M10 debrief's "did not exhaustively exercise each command" deferral is resolved
- [ ] The end-to-end HAT for this mission ships as a Chrome-driven repeatable script the agent can run autonomously while the operator is logged into Discord — the agent drives the Discord web UI through the browser MCP, observes the bot's responses on the platform side, observes the unified history on the operator-console side, and produces a pass/fail report against the criteria above; the script lives in the repository (not as a one-time HAT walk) so future Discord-touching flights run it as a regression gate
- [ ] The mentions-aware response policy is implemented as a new pre-step in the inbound dispatcher: when the bot is `@mentioned` in a channel message, auto-respond; otherwise an inference pre-step ("would this message benefit from an agent response?") decides whether to engage; the inference is configurable per agent and per channel (always-respond, mentioned-only, inference, never-respond modes); DMs and threads default to always-respond (continuing the M10 default); the policy composes cleanly with the F7 routing engine and the F8 auto-relay
- [ ] Peer-name attribution flows from the Discord gateway through the dispatcher, the session storage, the message broadcast, and into the Chat UI — the operator opening a connector-attached session sees `discord-username: message` in the platform-visible side of the unified history, not anonymous "peer message" entries; the M10 debrief's Bug C (peer_name data-model gap, 6 surfaces) is resolved
- [ ] The system-prompt directive that the connector layer injects into a connector-attached agent's effective system prompt is operator-editable per connector account, with a per-account override surface in the Discord connector detail page; the default directive is visible in the same surface so the operator understands what the agent runs under without needing to read source; the M10 debrief's "Three hard-coded constants in agent/config.py:54-93" critical action item is closed
- [ ] The lifecycle pool keying for connector accounts is refactored from M10 F8's sentinel-wrapper (`acquire("__connector__", account_id)`) to an account-keyed primitive at the connector layer; the per-agent-keyed pool stays as MCP-only territory; the API surface no longer presents `pool_acquire(agent_name, account_id)` as a footgun to connector authors; the M10 debrief's "F1 pool keying needs proper refactor" critical action item is closed
- [ ] An audit-log inspector surface (Chat UI or Studio — wherever the routing decision is most useful to the operator) renders the `session_metadata["routing"]` records that F7 populates, so the operator can see why each session routed to which agent; the inspector is connector-agnostic but exercised against Discord in this mission
- [ ] Outbound rate-limiting and backpressure behave correctly under live load — Discord's per-route and per-bot global rate limits are respected, 429 responses produce graceful backoff rather than tool-failure cascades, and the bot stays responsive to inbound traffic while outbound is queued; the M10 mission criterion #23 (rate limiting + backpressure live-load HAT) is resolved
- [ ] An operator who has never used the-one before, given the README and access to a fresh Discord developer portal, can register a bot, create a Discord connector account in the-one, attach it to an agent, allowlist a user/channel, and exchange messages on Discord in under fifteen minutes; this is the operational definition of "easy to use" and is measured by an actual walkthrough at mission completion
- [ ] The Discord connector survives a full working day of operator daily-driver use without operator intervention (no manual restarts, no token re-decryption issues, no stuck sessions, no silently-dropped inbound) — observed at least once during this mission before the mission is declared completed; this is the operational definition of "robust" and is measured by an actual full-day run at mission completion

## Stakeholders

**Primary**: the operator (single-user local tool) — runs the Discord bot as a daily driver, needs the workflow to be self-serve and the bot to stay online without supervision.

**Secondary**: peers on the operator's Discord servers — interact with the bot through normal Discord conventions (mentions, slash commands, DMs); their experience must feel like talking to a coherent participant, not an over-eager bot that responds to every message in active channels.

**Tertiary**: future connector authors — the Discord-shaped UX patterns introduced here (typed creation form per connector, live-data discoverable dropdowns, platform-vocabulary terminology) become the reference shape for the second connector when it eventually lands; the substrate must accommodate these patterns generically so adding e.g. Slack inherits the polish.

## Constraints

- The agent loop (`agent/core.py`, `agent/factory.py`) is NOT modified. Mentions-aware response policy lives in the connector dispatcher's pre-step, not in the agent loop. The same constraint that bound M10 binds this mission. **Clarification**: `agent/config.py`'s `compose_system_prompt` IS in scope — M10 F4 L3 already modified it to inject the connector directive, and this mission's operator-editable-directive surface extends that same composition site. The constraint forbids loop-logic changes, not composition-time configuration extensions.
- The substrate established in M10 F1-F7 (connector plugin contract, encrypted credentials, dispatcher 12-step, ACL resolver, routing engine, command surface, lifecycle pool, two-visibility-layer message model) is fixed; this mission extends but does not re-architect it. Connector-substrate refactors (pool-keying primitive, system-prompt-directive surface) are in scope; substrate-shape changes are not.
- The Single-User Local Tool security posture is preserved. No auth added to the-one's own routes. The Discord bot token remains under the existing Fernet encryption pipeline.
- The mentions-aware inference pre-step does NOT use a separate LLM provider configured for the connector. It uses the same provider stack as the rest of the-one (the agent's configured LLM, or a project-wide default that points at an existing-provider row — to be resolved at flight planning). It does not introduce a new credential type or a new pool. **Clarification**: a new non-secret configuration field that selects which existing provider runs the inference step (per-account or project-default) IS permitted — that's configuration shape, not a new credential or pool.
- Discord-specific UX must NOT close design space for the second connector. The dropdown-based allowlist editor must work generically against any connector that can enumerate its discoverable entities (users, channels, etc.) — Discord's `ChannelMessageToolDiscovery` shape is the source of inspiration but the abstraction lives at the substrate layer, with Discord supplying the data. **Vocabulary substitution discipline**: the connector-agnostic API stays "peer / channel / group" at the Protocol and storage layers; Discord-specific vocabulary (username / server / channel / role) is substituted at the Discord plugin's translate layer (`_discord_translate.py` precedent) and at the Discord-shaped UI surfaces. Other connectors get their own vocabulary substitution; the substrate's neutral vocabulary stays intact.
- The named `agents.md` project conventions established in M10 (`encryptor-parameter-receive-but-not-consume`, `cross-subsystem-pattern-premise-revalidation`, `prompt-discipline-needs-mechanical-fallback`, `mechanical-fallback-prompt-truth-pairing`, `lifespan-wiring-same-leg-as-installation`, `atomic-leg-pattern`, `per-axis-tri-state-override`, `optional-plugin-hook-via-getattr-sentinel`) apply throughout. Flight planning may add to this list; it does not lower the bar.
- Webhook-driven platforms remain explicitly out of scope. The mentions-aware inference, the discoverable-dropdown contract, and the audit-log inspector must accommodate webhook-driven shapes in their abstractions so they slot in additively, but no webhook code lands in this mission.
- Voice / video / non-text modalities remain out of scope (M10 constraint inherited).
- The `THE_ONE_TEST_MODE` and other test-only env-var seam constraint from M10 applies — connector test seams use code-side stubs and dependency injection, not env-var-driven runtime branching.
- The end-to-end HAT validation lives in the repository as a committed, reviewed, lint-passing code artifact (treated as production code). **Driver choice is a capability, not a requirement**: Chrome MCP is available and is the *preferred* visualization surface for the operator-facing side, but if Discord's web-client bot-detection makes browser automation unreliable, the HAT script may use `discord.py` as a second-bot driver (the agent runs as bot A, the HAT script runs as bot B on the same test guild) with Chrome MCP used for screenshot/evidence capture only. Resolve the driver shape at the HAT-script flight. If the script grows screenshot evidence at debrief time, those screenshots remain gitignored per the user-global "test snapshots not committed" rule.

## Environment Requirements

- Development: existing the-one dev environment (Docker container or local Python 3.11+, both already supported via `Makefile` / `pip install -e .`); browser MCP available via the existing chrome-devtools MCP server registration.
- Runtime: outbound network access to Discord's Gateway WebSocket + REST API (M10 constraint inherited).
- External accounts: the operator MUST have at least one Discord application + bot user with the intents the M10 F8 Discord plugin requires (Message Content, Guild Members, Guild Presences if presence is needed); a Discord server the bot can be invited to; at least three distinct Discord users (the operator + two others, or three burner accounts) available to validate multi-user routing; at least three channels in the test server.
- Tooling: no new system dependencies. `discord.py 2.4.x` remains pinned. Browser MCP usage assumes the chrome-devtools MCP server is registered and the operator can be logged into Discord in the browser session the agent drives.

## Open Questions

These resolve during flight planning; answers go in the relevant flight artifact's Design Decisions section.

- [ ] **Pairing resolution — keep, replace, or both?** Three viable resolutions: (a) **keep** the `PAIR <code>` text-prefix flow and improve onboarding UX (a "share this pairing code" button in the Studio connector detail; a Chat UI prompt when an unpaired user DMs with paired-message guidance); (b) **replace** with a Discord-native approval flow (unknown-sender DM surfaces in the Chat UI as a pending approval banner; one-click approve moves the peer into the allowlist and replies to the peer with a confirmation); (c) **both** — replace as the default Discord flow but keep `PAIR <code>` as a fallback for out-of-band approval (e.g. the operator wants to pre-approve a stranger). Default unless redirected: (c) — Discord-native as the primary, text-prefix as fallback, with the substrate's pairing primitive unchanged so other connectors can choose their own UX. Resolve during the pairing flight.
- [ ] **Mentions-aware inference — what model, what prompt?** The inference pre-step ("would this message benefit from an agent response?") needs an LLM call. Three viable shapes: (a) reuse the attached agent's configured LLM provider with a tight system prompt and `temperature=0`; (b) use a project-wide default "inference model" that points at an existing provider row (cheaper / faster small model for the inference step, larger model for the actual response); (c) hard-code a rule-based heuristic (mention → respond; question-mark + no other speakers in last N messages → respond; otherwise no) with no LLM call. Default unless redirected: (a) with a per-agent / per-account override to (b) for agents that pin a heavy-and-expensive provider; the rule-based shape is rejected because Discord conversation patterns are too diverse for a static heuristic. **This OQ must be resolved JOINTLY with OQs 11 (does inference gate `step()` or just outbound?) and 3 (granularity/modes) at F5's planning phase, not separately across leg sequencing — they are one design decision with three surfaces.**
- [ ] **Mentions-aware modes — granularity?** Per agent? Per channel? Per (agent, channel)? Proposed modes: `always-respond`, `mentioned-only`, `inference` (default), `never-respond`. Per (agent, channel) overrides composed from a per-agent default. DMs and threads default to `always-respond` regardless of channel default. Resolve during the mentions-aware response policy flight.
- [ ] **Discoverable-dropdown freshness — when does the bot's view of users/channels/servers/roles get cached, refreshed, invalidated?** Three viable shapes: (a) **fetch on dropdown open** — the dropdown queries Discord live every time the operator clicks it (simple, slowest, hits rate limits if the operator opens it often); (b) **periodic background refresh** — the connector account maintains a cached view, refreshed every N minutes while the bot is online (fast UI, but stale entries possible); (c) **gateway-event-driven** — Discord pushes guild_member_add / channel_create / role_create events through the gateway and the cache updates incrementally (most accurate, most complex). Default unless redirected: (b) with a manual "Refresh" button in the dropdown for operator override, and a stale-entry indicator. Resolve at flight planning.
- [ ] **Searchable dropdown UI shape** — typeahead with results list (combobox), virtualized list for large servers (>1000 members), grouped sections (channels by category, members by role), or simple `<datalist>`-driven typeahead? Default unless redirected: combobox with grouped sections, typeahead filter, virtualization for >100 entries, paged fetch for >1000. Resolve at flight planning.
- [ ] **Per-account system-prompt directive surface** — full free-text editor, structured fields (one field per directive, with a "raw mode" escape hatch), or a templated picker (operator chooses one of N preset directives + a free-text override)? Default unless redirected: full free-text editor with the default directive shown as placeholder/help; the operator can copy-paste it as a starting point. Resolve at flight planning.
- [ ] **Detach-from-Connectors-screen UI** — does the detach action live on the connector account's detail page (a row per attached agent with a detach button), on the Connectors grid (an expanded row showing attached agents with detach affordances), or both? Default unless redirected: on the connector account's detail page only, with the Connectors grid surfacing the attached-agent count and linking to the detail. Resolve at flight planning.
- [ ] **Audit-log inspector location** — Chat UI per-session panel, Studio connector account detail page, both, or a new top-level Admin view? Default unless redirected: Chat UI per-session panel as the primary surface (it's where the operator already lives when debugging routing), with the Studio detail page linking to it. Resolve at flight planning.
- [ ] **Rate-limiting live-load HAT shape** — synthetic load script that pushes >Discord's rate limit deliberately to observe backoff behavior, or production-realistic load (operator + N peers in a busy channel for an hour)? Default unless redirected: both — synthetic for deterministic regression-testable HAT, production-realistic for the "operator survives a working day" criterion. Resolve at flight planning.
- [ ] **Chrome-driven HAT script — how parameterized?** Single-bot single-server single-operator-account assumption, or generalized to N-bots N-servers N-operators? Default unless redirected: single-bot single-server with the Discord server fixtures committed (a known test guild structure), three distinct operator accounts (the operator + two burners) configured at HAT-run time. Resolve at the HAT-script flight.
- [ ] **Mentions-aware inference + auto-relay interaction** — does the inference pre-step decide whether to *invoke* the agent at all (no inference → agent never sees the message), or does the agent always see the message and the inference decides whether to *send back* to the platform? Default unless redirected: the inference decides whether the agent runs `step()` at all — non-engagement is also non-context, which mirrors how humans skim a busy channel. The agent's context is preserved for the next mentioned message via the unified session history (so it sees what was said even on turns it didn't respond to). Resolve carefully at the mentions-aware flight.
- [ ] **Test-throughput regression from M10** — should this mission include a leg specifically to investigate and address the 14.4 → 12.5 t/s regression M10 debrief flagged, or roll it into routine-maintenance separately? Default unless redirected: separate — `/routine-maintenance` runs first (per M10 action item) and reports findings; if a structural fix is identified that's scoped within a mission flight, fold it in, otherwise out of scope.
- [ ] **Slash command Discord-native autocomplete** — does this mission upgrade text-prefix to Discord-native slash-command registration (per F7's "additive future enhancement" framing), or stay on text-prefix with HAT validation? F8 L9 already shipped per-guild slash-command registration via the F7 CommandHandler Protocol — so the work mostly exists. The open question is whether autocomplete + structured args + ephemeral-where-appropriate are all in scope for this mission or just "verify they work end-to-end." Default unless redirected: in scope — slash commands should feel platform-native, not text-prefix-with-a-slash. Resolve at the slash-command verification flight.

## Known Issues

Emergent blockers and issues discovered during execution. Add items here as flights surface problems that affect the broader mission — things not anticipated during planning but visible at the mission level.

- [ ] **M10 codification dependency**: The constraints section binds this mission to five M10-debrief-recommended conventions (`encryptor-parameter-receive-but-not-consume`, `cross-subsystem-pattern-premise-revalidation`, `prompt-discipline-needs-mechanical-fallback`, `mechanical-fallback-prompt-truth-pairing`, `lifespan-wiring-same-leg-as-installation`) plus the `atomic-leg-pattern` Architect addition. The M10 mission-debrief action item to codify these in `the_one/agents.md` was scheduled "before follow-on Discord-depth mission planning." Verify the codification is done before F1 planning, OR treat F1's first checklist item as completing the codification.

- [ ] **F2 pool refactor — public-API decision**: F2 must commit at planning whether to remove `pool_acquire` from `connectors/_pool.py`'s public API (breaking the test seam at `_inbound.py` and updating `tools/connector_send.py` lockstep) or only deprecate it. Removal is preferred (eliminates footgun); deprecation keeps the footgun in service of test-seam stability. Resolve at F2 planning.

- [ ] **F3 discoverable-entities hook — Protocol shape**: F3 must commit at planning to either (a) **Protocol widening** — every `ConnectorPlugin` must implement `enumerate_discoverable_entities(account, encryptor)` even if it returns an empty payload; (b) **optional-plugin-hook-via-getattr-sentinel** (M10 convention) — connectors that can't enumerate just don't surface dropdowns. Default unless redirected: (b), consistent with M10's established hook-extension pattern. Also resolve: one hook returning a structured `DiscoverableEntities` value, or per-axis hooks (one per peers/channels/guilds/roles). Default unless redirected: one hook with a structured return.

- [ ] **F5 dispatcher pipeline position**: F5 must commit at planning where in the canonical 12-step inbound dispatcher (`connectors/_inbound.py:55-103`) the mentions-aware inference pre-step lands. Three options: (a) before routing (step 7) — inference decides whether to pick an agent at all; (b) between routing and `agent.step()` (between steps 7 and 12) — agent picked, inference gates `step()`; (c) after `step()` — agent runs, inference gates outbound. Each has different audit-log shape and routing-engine implications. Composes with OQs 11 + 2.
