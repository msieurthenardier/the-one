## Pre-Flight

### Design Decisions

**Per-row nullable columns on `chat_sessions`, not a join table**

- **Choice**: Add five nullable columns to `chat_sessions`: `platform TEXT NULL`, `connector_account_id TEXT NULL`, `channel_id TEXT NULL`, `thread_id TEXT NULL`, `peer_id TEXT NULL`. Plus `session_metadata TEXT NULL` (JSON; F7 piggyback). Plus `last_inbound_at TEXT NULL` (ISO-format string, populated on every inbound; consulted by the continuation-window query so we don't conflate "session was updated" with "platform-side activity"). Add a **non-unique** partial index `idx_chat_sessions_external_key ON chat_sessions(platform, connector_account_id, channel_id, COALESCE(thread_id, '')) WHERE platform IS NOT NULL`.
- **Rationale**: A connector session has exactly one external key by definition (one external conversation → one session); 1:1 fits naturally as columns on the row, not a join table. Join table would be more normalized but the mission has no 1:N case in scope (cross-posting one session to multiple external locations is not a goal). Per-row columns also make the Chat UI query (F5) trivially correct: `SELECT * FROM chat_sessions ORDER BY updated_at DESC` returns everything the operator wants to see, including the connector-keyed sessions, with no JOIN. Non-connector sessions have NULL in all six new columns — sparseness is acceptable; SQLite stores NULLs compactly.
- **Trade-off**: The `chat_sessions` row grows by seven nullable columns. Storage cost is negligible. The non-unique index allows multiple historical rows per external key (intentional — old superseded sessions stay queryable in the Chat UI); the resolver's lookup is "most recent matching row by `updated_at DESC LIMIT 1`, check if within continuation window." If a future flight needs true uniqueness on the external key (e.g. to enforce "only one active connector session per external key at a time"), it can add a unique partial index with a `is_active = 1` discriminator column at that point.

**Session-key shape: `(platform, connector_account_id, channel_id, thread_id)` — peer_id stored, not in key; threads distinct**

- **Choice**: The canonical lookup key for resolving an `InboundEnvelope` to a `chat_sessions` row is the 4-tuple `(platform, connector_account_id, channel_id, thread_id)`. `peer_id` is captured on the row for audit and display but is NOT part of the lookup key. Threads (when `envelope.thread_id is not None`) get distinct sessions from their parent channel.
- **Rationale**: Mismatched-conversation failure mode ("bot confused two distinct conversations") is worse than lost-context failure mode ("bot lost broader channel context"). Threads on Discord and Slack are deliberately scoped sub-conversations — collapsing them into the parent channel would mean the bot treats unrelated thread discussions as continuations of the channel chat. Per-thread isolation matches the platform's UX and lets the agent's context window stay focused on the thread topic. For DMs, the `channel_id` itself uniquely identifies the bot-peer pair (Discord DMs are 1:1, Slack DMs are scoped), so `peer_id` redundancy is irrelevant for lookup. For shared guild channels with multiple peers, the default is "one session per channel" (the bot has one conversation with the channel; peers contribute to it collectively). Per-peer-isolated sessions in a shared channel would be a different product decision (peer-scoped bots vs. channel-scoped bots) — YAGNI for v1; mission does not require it.
- **Trade-off**: An operator who wants per-peer-isolated sessions in a shared channel will be unable to get them without a future mission. A `peer_scope: 'channel' | 'peer'` field on `connector_accounts` could be added later; the resolver would consult it and use a wider key (`channel_id, peer_id` instead of just `channel_id`) when peer-scoped. Today's `peer_id` column on `chat_sessions` is the audit trail that makes future migration to peer-scoped sessions cheap — the historical attribution is already there. No design space is closed.

**Continuation window: 24h default; configurable per-account; stale-supersede creates new row, preserves old**

- **Choice**: Add `session_continuation_seconds INTEGER NULL` to `connector_accounts` (sibling to F2's `idle_timeout_seconds`). Validator: `1 ≤ value ≤ 604800` (7-day upper bound catches ms-vs-s typos). Resolver lookup: most recent row matching `(platform, connector_account_id, channel_id, thread_id)` ordered by `updated_at DESC`. If found AND `now - last_inbound_at < session_continuation_seconds (resolved)` → reuse that row. Otherwise (no match, OR stale match) → INSERT a new `chat_sessions` row with the external key columns set and `last_inbound_at = now`. The old row is preserved untouched — it remains queryable in the Chat UI as a historical session for the same external location.
- **Rationale**: 24h default mirrors the mission's stated default and common bot-platform convention (Discord/Slack bots typically treat a 24h gap as a fresh conversation). Configurability matters more than the specific number. Per-account is the right scope because the operator may want short windows for chat-bot-style accounts (interactive turns) and long windows for assistant-style accounts (multi-day reasoning). The validator's pattern is verbatim from F2's `idle_timeout_seconds` — same range, same null-uses-default semantics, same admin form treatment.
- **Stale-supersede preserves the old row** instead of mutating it because: (a) the old session's message history is potentially long and valuable (operator may want to read it later); (b) mutating-in-place would lose the audit trail of when the "fresh start" happened; (c) NULLing the external key on the old row would orphan it from "connector sessions for this account" filters in F5's Chat UI. Preservation costs one row per supersede event; over a year of daily superseded sessions that's ~365 rows per (account, channel) — negligible.
- **Trade-off**: An operator browsing connector sessions in Chat UI will see multiple rows per external location ("Discord #engineering — May 17", "Discord #engineering — May 16", ...) once supersedes accumulate. This is correct behavior — each is its own conversation. F5's UI should group / collapse / sort them sensibly, but that's F5's concern, not F3's. Resolution: F5 leg planning treats the external-key columns as a grouping discriminator if needed.

**Resolution order for `session_continuation_seconds`: per-account value → env var → default**

- **Choice**: A free function `_resolve_continuation_seconds(override: int | None = None) -> int` resolves: explicit `override` (account's field value) if not None → `THE_ONE_SESSION_CONTINUATION_SECONDS` env var if set + parseable → `_DEFAULT_SESSION_CONTINUATION_SECONDS = 86400`. Mirrors `connectors/_pool.py:_resolve_ttl_seconds()`'s shape exactly (architect-refined in F2). Env var is read at call time (`live-read-across-lazy-resolver-boundary` convention).
- **Rationale**: Resolver shape parallel with F2's pool TTL resolver makes the codebase visibly self-similar. The pool resolver takes `int | None` not `ConnectorAccount`; the session-continuation resolver does the same — the resolver is ignorant of which model field drives the override.
- **Trade-off**: Two resolvers with parallel shapes living in different modules (`_pool.py` and the new session-resolution module). If a third "configurable lifetime" surfaces later, a shared resolver primitive may be worth extracting. Flagged as a recommendation only if it materializes.

**`last_activity` per-inbound-acquire — RATIFY (F1 debrief carry-forward)**

- **Choice**: The inbound dispatcher calls `await pool.acquire((agent_name, account_id))` for every inbound envelope. Pool's `acquire()` already touches `entry.last_activity = time.monotonic()` on every successful return (`connectors/_pool.py:479`). The dispatcher does NOT cache the `ConnectorClient` reference outside the pool — every inbound goes through `acquire`. No new pool API (no `touch_activity(key)`).
- **Rationale**: The F1 Known Issue (`the_one/agents.md:344`) flagged that Flight 3 must ratify or amend the per-acquire-touch contract. Ratifying is the simpler decision: the only consumer of `last_activity` is the reaper, and the only signal that "this gateway is being used" the pool can observe is `acquire` calls. Per-inbound `acquire` is cheap for warm entries (lock + dict-lookup + activity-touch + client-return). The alternative ("cache the client once, only re-acquire on connection failure") would create exactly the premature-eviction failure mode the Known Issue warned about. Ratifying matches the MCP pool's discovery that whoever needs the client should ask the pool every time.
- **Trade-off**: Per-inbound lock contention on `_lock` (the module-level pool lock) — but the work under the lock is microseconds, and platform inbound rate is bounded by the platform (Discord ~50 events/sec/bot, Slack much lower). Not a meaningful concern.
- **Action**: Remove or update the Flight 3 ratification entry in `the_one/agents.md:338-345` Known Issues to reflect that this flight ratified the contract; cite this flight + the dispatcher's `acquire`-call site as the contract anchor.

**Eviction trigger for `session_continuation_seconds` change — NONE (F2 debrief carry-forward)**

- **Choice**: Changing `session_continuation_seconds` via PUT on a connector account triggers NO pool eviction. The PUT path's eviction-on-secrets-change logic (F2 leg 2) is unchanged; the new field is excluded from the eviction trigger.
- **Rationale**: Pool entries represent the warm gateway connection (with cached decrypted credentials inside the `ConnectorClient`). They are about transport, not about session-routing policy. `session_continuation_seconds` is consulted by the resolver at inbound-dispatch time — it is NOT cached in the pool entry, NOT cached in the client, NOT material to any in-flight pool state. A change to this field takes effect on the next inbound after the PUT commits, with no need to invalidate anything in memory.
- **Trade-off**: An in-flight inbound that has already entered the resolver but not yet completed the lookup may use the OLD value if the PUT lands mid-resolution. Worst case: one inbound makes a session-reuse-vs-fresh decision with the stale value. The operator's mental model on a continuation-window change is "takes effect next session," which this delivers — the in-flight-inbound race is invisible to the operator because they cannot observe sub-millisecond ordering. F2's eviction-on-secrets-change logic is unchanged; this design decision documents the explicit non-trigger so the reader sees it called out.

**`visibility: str | None = None` on `Message`; codec round-trip via `d.get` pattern**

- **Choice**: Add `visibility: str | None = None` to `the_one/llm/base.py:Message` dataclass. Permitted values (enforced at the dispatcher / construction-site level, NOT at dataclass-construction time — the dataclass is permissive on string contents per the existing project pattern): `None` and `"operator"`. Codec changes:
  - `message_to_dict` (`the_one/db/codec.py:54-63`): add `if msg.visibility is not None: d["visibility"] = msg.visibility` after the existing optional-field serializations.
  - `message_from_dict` (`the_one/db/codec.py:66-94`): pass `visibility=d.get("visibility")` to the `Message(...)` constructor (defaults to None when absent — back-compat with all pre-F3 session rows).
  - `messages_to_ui_events` (`the_one/db/codec.py:107-172`): for every emitted event dict where the source `Message.visibility is not None`, add `event["visibility"] = msg.visibility`. When `visibility is None`, the key is absent (frontends treat absent === platform-visible). Existing parent-message-id / tool-call-grouping logic is untouched.
- **Rationale**: Single-field addition with default `None` is structurally non-disruptive — only 1 production call site constructs `Message(...)` directly (`db/codec.py:88` deserialization); all other construction goes through the classmethod helpers (`Message.system`, `.user`, `.assistant`, `.tool`), none of which need signature changes (operator-tagged messages will be created by F5's operator-input path with an explicit `Message.user(content, visibility="operator")` call; F3 itself doesn't construct operator-visibility messages outside tests). The codec's `d.get("visibility")` pattern mirrors F5 L3's `metadata=tr.get("metadata")` pattern at the same file (`codec.py:79`) — same back-compat shape, same convention.
- **Trade-off**: The dataclass is permissive on string contents (no `Literal["operator"]` constraint), so a typo like `visibility="opperator"` would persist silently. Mitigation: the dispatcher and the F4 platform-send tool are the ONLY production code paths that set visibility; their construction sites use module-level constants (`OPERATOR_VISIBILITY = "operator"`) referenced from a single point. Test coverage in legs 2 and 6 asserts the constant matches across the few sites. A `Literal` constraint can be added later if drift is observed; this matches the project's general permissive-dataclass + strict-construction-site pattern.

**Concurrent-inbound serialization: per-`session_id` `asyncio.Lock` (with documented F5-reconciliation gap)**

- **Choice**: A module-level `_session_locks: defaultdict[str, asyncio.Lock] = defaultdict(asyncio.Lock)` lives in the dispatcher module. `dispatch_inbound` acquires `_session_locks[session_id]` before driving `agent.step()` and releases after persisting the agent's reply. The lock dict grows monotonically with session count; entries are NOT cleaned up (the dict is in-memory, dies with the process). For Flight 3's stub-driven test suite this is irrelevant; for production with thousands of sessions over months, memory growth is bounded by `~100 bytes/lock × N_sessions` — measurable but not concerning.
- **Rationale**: Concurrent inbounds on the same `chat_sessions` row would create parallel `agent.step()` calls reading and appending to the same message history — a race that produces silently wrong agent state (interleaved tool calls, lost context). Per-session serialization is the simplest correct answer. The lock is held for the duration of the agent's turn (potentially several seconds for LLM round-trips + tool calls); concurrent inbounds for the same session queue. This is correct behavior — a bot in #engineering processing multiple peers' messages should produce one ordered turn after another, not interleaved chaos.
- **Trade-off — memory growth**: flagged for Flight 10 (hardening). Mitigation options if growth matters: `WeakValueDictionary` (locks GC'd when no holders), TTL-based cleanup, or a bounded LRU cache. None are needed for v1. Documented in the leg artifact + flight log so F10 has the context.
- **Trade-off — second-lock-on-same-session (architect-surfaced, F5-owned)**: The WebSocket handler at `interfaces/web/app.py:201,252` already serializes per-session via `Session.processing_lock` (attached to an in-memory `Session` instance in `app.py`'s private `_sessions` dict). F3's dispatcher cannot reach `Session.processing_lock` without breaking `app.py` encapsulation OR refactoring `Session` to a neutral module. **For F3 alone this is not yet a problem** because F3 only ships the dispatcher path; the WS operator-input path does not yet touch connector-attached sessions (the operator-typing-into-a-connector-attached-session UX lands in F5). F3 makes the deliberate choice to keep `_session_locks` and `Session.processing_lock` SEPARATE and FLAGS this as an Open Question for F5 leg planning. F5 must reconcile: either (a) route operator-typed messages on connector-attached sessions through F3's `dispatch_inbound` shape (with `visibility="operator"` set at the entry point) so `_session_locks[session_id]` is the sole serialization primitive, OR (b) refactor `Session` out of `app.py` so `Session.processing_lock` is shared. Option (a) is leaner. F3 writes this concern into the mission's Known Issues so F5's planner inherits it explicitly. **This is structurally analogous to F1 deferring `last_activity` ratification to F3** — a downstream flight owns the reconciliation, the upstream flight documents the carry-forward.

Two-pass planning grep convention (codified post-F2) applies: leg 1 must enumerate **both** the head-version assertion sites AND the column-set assertion sites for `chat_sessions` AND `connector_accounts`.

- **Choice**: No optional `uat-and-alignment` leg in this flight.

- **Leg 3 — `session-key-resolver`**:
  - New module `the_one/connectors/_session.py` (private; not part of the public connector SDK). Pure functions, no side effects:
    - `envelope_to_lookup_key(envelope: InboundEnvelope) -> tuple[str, str, str, str | None]` — extracts `(platform, account_id, channel_id, thread_id)` from the envelope. The "lookup key" is the 4-tuple; `peer_id` is NOT part of it.
    - `_resolve_continuation_seconds(override: int | None = None) -> int` — resolves the continuation window with order: explicit override → env var `THE_ONE_SESSION_CONTINUATION_SECONDS` (read at call time) → `_DEFAULT_SESSION_CONTINUATION_SECONDS = 86400`. Mirrors `connectors/_pool.py:_resolve_ttl_seconds` shape.
    - `async def resolve_session(envelope: InboundEnvelope, account: ConnectorAccount, repo: ChatSessionRepository, *, agent_name: str, plugin: ConnectorPlugin) -> ChatSession` — the resolver:
      1. Compute lookup key from envelope.
      2. Query `repo.find_most_recent_by_external_key(*lookup_key) -> ChatSession | None` (new repository method added in this leg).
      3. If found AND `(now - parsed(last_inbound_at)) < _resolve_continuation_seconds(override=account.session_continuation_seconds)` → return found. **Datetime parsing is explicit** (`datetime.fromisoformat(row.last_inbound_at)` on the read side; `_now_iso()` style on the write side per `the_one/db/models.py:13`); do NOT rely on string `<` comparison of ISO timestamps.
      4. Else: build a title by calling `getattr(plugin, "display_channel", None)` — if the attribute exists, invoke `plugin.display_channel(envelope)` inside a `try / except Exception` and fall back to `envelope.channel_id` on any failure or empty-string return. Create new ChatSession with the external-key columns + `agent_name=agent_name` + `last_inbound_at=now` + the derived title, persist via `repo.create(...)`, return new.
  - **`display_channel` is an OPTIONAL hook, NOT a Protocol-widening** (architect-revised). The resolver accesses it via `getattr(plugin, "display_channel", None)` with the sentinel-None default; if `None`, fall back to `envelope.channel_id`. The `ConnectorPlugin` Protocol in `connectors/base.py` is NOT modified. Document `display_channel` in `connectors/README.md` as the first of an emerging "optional hook" convention (F4's outbound-send extension on `ConnectorClient` will use the same pattern). Rationale: F1's Protocol-widening discussion explicitly framed `ConnectorPlugin` as widenable in `base.py:177-184`, but for an OPTIONAL hook that not every plugin needs to provide, the `getattr` pattern is cleaner — it doesn't force every connector author to satisfy a method whose return value has a sensible default at the call site. The Stub plugin can still implement it; it's just no longer required by the structural contract.
  - `the_one/db/repositories.py`: add `ChatSessionRepository.find_most_recent_by_external_key(platform, connector_account_id, channel_id, thread_id) -> ChatSession | None`. SQL: `SELECT * FROM chat_sessions WHERE platform = ? AND connector_account_id = ? AND channel_id = ? AND COALESCE(thread_id, '') = COALESCE(?, '') ORDER BY updated_at DESC LIMIT 1`. The COALESCE handles NULL thread_id matching (SQLite's NULL-distinct semantics on the index expression mean we have to mirror the COALESCE on the query side).
  - Test (all pure-function except the repository query): envelope → lookup key extraction; resolver with no existing match → new row created with all fields populated; resolver with match within window → existing row returned; resolver with match outside window → new row created, old preserved untouched; `_resolve_continuation_seconds` override beats env var beats default; env var read at call time (monkeypatch changes resolution without process restart); `display_channel` fallback when hook is missing (StubPlugin without the method → resolver falls back to `envelope.channel_id`); `display_channel` exception → resolver catches and falls back (no propagation).

### Adaptation Criteria

**Divert if**:
- The SQLite version on container fails to support expression indexes (`COALESCE(thread_id, '')` in the partial index) — fall back to two indexes (one with thread_id IS NULL, one with thread_id IS NOT NULL) or move uniqueness enforcement to application code with a non-expression index.
- The Message dataclass turns out to be frozen / slots-restricted in some path the recon missed (Pydantic round-trip layer, JSON Schema generation, etc.) — surface and decide whether to extend the codec layer or work around the frozen-ness with a sidecar.
