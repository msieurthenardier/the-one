# Squawk 0435: the unit tier has no per-test timeout

**Status**: completed
**Type**: servicing
**Severity**: routine
**Reported**: 2026-11-26
**Completed**: 2026-11-26

## Report

The `Makefile` `test-unit` target passes `-n $(UNIT_WORKERS) --dist load -v --tb=short` and no `--timeout`. `pyproject.toml` `addopts` sets none either. A single hung test therefore runs until the whole-tier watchdog (`TEST_TIMEOUT`, 1200 s by default) kills the process group. The run then reports "killed at 98%" instead of a failed test with a stack. This happened twice in Mission 37 Flight 2 (squawk 0434). CLAUDE.md already asks every autonomous pytest run to pass a timeout; the canonical target does not.

## Evidence
- The `Makefile` `test-unit` recipe shows no `--timeout`. `pytest-timeout>=2.4` is already a dev dependency.
- The Flight 2 debrief run hit the 3600 s kill with 0 FAILED lines.

## Corrective Action
`Makefile`: added `UNIT_TEST_TIMEOUT ?= 120` (overridable, e.g. `make test-unit UNIT_TEST_TIMEOUT=300`) and `--timeout $(UNIT_TEST_TIMEOUT)` to the `test-unit` recipe. `make gate` calls `make test-unit`, so it inherits it. 120 s is about 10x the slowest legitimate test seen under heavy load (12 s; 7.6 s on a clean host) yet far below the 1200 s tier watchdog. pytest-timeout's default `signal` method works under xdist workers: the timeout failures below print the full Python stack of the hung test plus all threads, so `--timeout-method` was left at the default. No docs state the `test-unit` flag list in a way that is now wrong (`the_one/agents.md` and `CLAUDE.md` mention only `-n $(UNIT_WORKERS) --dist load`, still true). CLAUDE.md line 129 could optionally mention `UNIT_TEST_TIMEOUT`; not edited (out of scope). CI does not run `make test-unit`: `ci/tasks/test.yml` runs its own `pytest tests/ --timeout=300` (and the Windows and bwrap tasks pass `--timeout=300`), so CI already has a per-test timeout and was left unchanged.
