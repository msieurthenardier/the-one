# Behavior Test: Workbench Navigation — rail, routes, history, leave guard

**Slug**: `workbench-navigation`
**Status**: active
**Created**: 2026-10-01
**Updated**: 2026-10-02 (M25 F3: list and detail shell, steps 3–8 and 10)
**Last Run**: 2026-10-01-21-03-48 — pass (28/28; Dark + Light)

## Intent

Verify the Mission 25 workbench navigation contract end-to-end against a live instance with seeded data: the left rail's four destinations (Chats, Agents, Library, Settings) each show their own list or navigation column (since Mission 25 Flight 3: the Agents list, the grouped Library list, the grouped Settings nav); opening items pushes real browser-history entries so Back and Forward step between them; the rail returns to each destination's last-open item; legacy `#admin/…` and `#studio/…` deep links redirect to the current routes; and a dirty editor is protected by ONE unsaved-changes dialog whether the operator leaves through the rail or through the browser's Back button, with Stay preserving the edit, the URL and focus, and Continue discarding the edit. A behavior test (not only the Playwright suite) because the observables are the rendered rail and dialog, the address bar and the real history stack of a real browser, across multi-step navigation flows. This is the behavior gate for Mission 25 Flight 2 (Shell and Router). The data-independent rail smoke is `shell-navigation-smoke`; this spec needs seeded data and is not read-only. It runs in both themes (see Variants).

## Preconditions

- The **instance under test** is a **dedicated dev instance**: a non-default port AND a scratch data directory, together, with dev mode on, e.g. `THE_ONE_PORT=8485 THE_ONE_DATA_DIR=/tmp/the-one-wbnav-scratch THE_ONE_DEV_MODE=true make up` (create the credential first with `THE_ONE_DATA_DIR=/tmp/the-one-wbnav-scratch the-one rotate-api-credential`). Never port 8484 and never the operator's default data directory (CLAUDE.md "Behavior-test credential convention" safety rule). The orchestrator states the actual base URL (`{base}`, default `http://127.0.0.1:8485`) and scratch directory at run time; both apply to every step. Probe: `GET {base}/api/live` returns HTTP 200 immediately before the run, and `GET {base}/api/providers/types` (with the credential) lists the `mock` type.
- A browser apparatus (goldfinch MCP) is attached and can open tabs to that origin.
- **Credential**: read `<scratch>/api-credential` verbatim and send it as `Authorization: Bearer <credential>` on every API call in the setup and teardown rows. For the browser, mint a handoff URL with `POST {base}/api/session/handoff` and navigate to the URL it returns (single-use; the session cookie then covers reloads and same-context navigation — mint again only for a fresh context or tab).
- The instance holds no agent, provider or knowledge base named with the prefix `wbnav-`; if a prior partial run left some, delete them before step 1.
- **Evidence and apparatus notes.**
  - Goldfinch screenshots have been unavailable on some hosts ("display surface not available for capture"). When a screenshot fails, the sanctioned evidence is `printToPDF`, the accessibility tree (`readAxTree`) and computed-style evals; the report states which path was used. Visual claims (theme flip, rail wash) rest on computed styles when pixels are unavailable.
  - Goldfinch cannot observe the `:focus-visible` ring. Every focus check in this spec asserts **`document.activeElement` identity** (tag, `data-testid` and/or `id`) via an eval, never a visible ring.
  - Hash changes made by clicking do not reload the page; a "cold" load means navigate to the URL and then reload, and confirm with `performance.getEntriesByType('navigation')[0].type === 'reload'`.
  - History is read from `location.hash` after each Back/Forward (the apparatus's `goBack`/`goForward` or `history.back()`), allowing ~700ms to settle.
  - **Never add a full-document load or any other history-altering probe that the steps do not call for**, especially between steps 10 and 13. A cross-document entry behind the editor turns step 13's Back into a document unload. The app's `beforeunload` guard handles that case, not the in-app dialog. One such probe forced a re-run in the first run.
  - The accessibility-tree dumps may omit `aria-current` and text-field values. Read those via a DOM eval alongside the rendered-state evidence.
  - Count the unsaved-changes dialog with `document.querySelectorAll('dialog[open]').length`. It is a native `<dialog>` element, and visibility queries on `[role=dialog]` disagree across apparatus.
  - Report only rendered error banners, where `offsetParent !== null` and the text is non-empty. Settings › Knowledge indexing and the KB detail page keep hidden templates and empty per-field error slots in the DOM.
- Run-tab environment: prefer an unoccluded/foregrounded window.

## Observables Required

- browser (rendered rail, section navigation, editor and dialog state; `location.hash`; `document.activeElement` identity; computed styles — measured via goldfinch MCP)
- http (setup and teardown API calls, and the saved-value check — measured via curl in the shell)

## Variants

- **Theme.** Run the whole step table twice: once with the theme explicitly **Light** and once explicitly **Dark**, switching through Settings › Appearance **before step 2** of each variant. The theme control is a radiogroup: click its Light or Dark option, then confirm `aria-checked="true"` on that option and `data-theme` on the document. Record the operator's original option, which is the `aria-checked` option, before the first variant's switch. Restore it after the last variant, in step 16. Re-seed (step 1) and tear down (step 16) per variant, or reuse the seed and only re-run steps 2-15, as long as no `wbnav-` leftovers remain at the end.
  - In **Dark**: `data-theme="dark"`, the body and rail grounds are dark, the current rail link shows its violet wash and ring, and the "Unsaved changes" dialog's text and its "Stay"/"Continue" buttons are legible against the dialog ground.
  - In **Light**: the same elements render on a light ground with legible dark text.
  - All route, history, dialog and focus expectations are identical in both themes. Evidence is computed colours for the rail, body and dialog surfaces (plus PDF/AX tree when screenshots are unavailable); the report says which path was used.
