## Summary

6 / 8 checkpoints passed. 2 failed (steps 5 and 6); 0 inconclusive.

The surface works end to end for reading and for one propagation mode: an agent
reads its own configuration with **no secret material** in the response
(steps 4, 8 — the projection exposes only name/description/system_prompt/model/
provider{name,type}/retention/tool-lists/kb-names, never an api_key, bearer,

The failures (5, 6) converge on one real defect, isolated by two follow-on
diagnostic probes: **a `next_session` revision does not reach an
already-open conversation when it is reopened** — not on an in-app rejoin, and
not on a full hard browser reload — even though a brand-new conversation reads
the current stored prompt correctly.

**Diagnostic probes (D, E) — not spec steps.** After step 8, to separate a real
propagation bug from execution/spec artifacts, the Orchestrator edited the
STORED `system_prompt` out-of-band via `PUT /api/agents/bt-agent` so it ended
with a third sentinel, **NARWHAL** (simulating an operator Studio edit;
stored=NARWHAL, live-in-memory=WALRUS):
- **D1** (no rejoin, existing conversation): reply ended WALRUS.
- **D2** (in-app view-switch rejoin, same session): reply ended WALRUS.
- **D3** (full hard browser reload, `ignoreCache`, fresh WebSocket + `join`, same session): reply ended WALRUS. A fresh `GET` confirmed the store still held NARWHAL throughout.
- **E** (brand-NEW conversation, session b2bb53419923): first reply ended **NARWHAL**.

**Ruling out the history-poisoning alternative.** One might argue the model was
imitating an in-history tool-result sentinel rather than reading the live prompt.
Step 5 refutes this: there, the PELICAN instruction was present in the
conversation history (step-2 tool result) yet the reply carried **no** sentinel
at all — the model followed the *live* system prompt (still the original,
un-revised prompt), not the history. So the consistent reading across step 5 and
D1–D3 is that the existing conversation's **in-memory agent is not rebuilt from
the stored row on rejoin/reload**; the model faithfully follows whatever live
prompt that agent still holds.

**Diagnosis.** `next_session` propagation is correct for genuinely new
conversations (E) and `next_turn` is correct within an open conversation (step 7),
but reopening an already-open conversation does **not** rebuild its agent from the
stored prompt — contradicting flight DD7's premise that "`next_session` costs
nothing because `_get_or_restore_session` always rebuilds from the current agent
row." The `_restore_session` code (`app.py:1054`) reads as if it rebuilds `.agent`
on every join; empirically, for an already-cached session it does not take effect.
Root cause not pinned from source reading alone (the join handler and
`_restore_session` look correct on the page); pinning it needs server-side
instrumentation. Whether the cause is pre-existing (independent of this flight)
or an interaction with Leg 3's in-place `messages[0]` mutation is unresolved.

**Disposition**: deferred to the operator (see flight log Anomaly A12). The leg
is NOT marked landed on this criterion; next_turn, new-conversation propagation,
and the secret-free read are all verified.
