## Pre-Flight

### Objective

Bring the Chat area to the design-language quality bar through three coordinated workstreams: (a) **structural refactor** — split `chat.js` from 782 LOC into a coordinator + pure-helper sub-modules under `App.chat.{...}` and lift duplicated CSS into a shared component library under `@layer components`; (b) **rendering capability** — hand-roll a small markdown library at `js/markdown.js` (`App.markdown.parse` / `App.markdown.render`) with a tokenize-then-AST-then-DOM pipeline that ships an extensible CommonMark subset and never uses `innerHTML`; (c) **streaming** — extend `LLMProvider` with an optional async-iterator `stream()` method, wire the four providers (Anthropic, OpenAI, Ollama, mock), broadcast `assistant_chunk` WS events from `_process_and_broadcast`, and progressively append on the client (with a final markdown re-render on `done`). ### Design Decisions

**Hand-rolled markdown library at `js/markdown.js`, registered as `App.markdown`**: tokenize-then-parse-then-render pipeline with explicit AST node types (`paragraph`, `heading`, `codeBlock`, `blockquote`, `list`, `listItem`, `text`, `emphasis`, `strong`, `code`, `link`, `lineBreak`, `hardBreak`, `hr`). Renderer constructs DOM via `document.createElement` + `textContent`; never `innerHTML`. Initial subset is CommonMark-conformant for the documented constructs; nested-emphasis ambiguity (`***bold-italic***`) handled per the CommonMark "left/right flanking delimiter run" algorithm OR documented as non-recursive in v1 — the test corpus locks in whichever choice is made. Extension contract: new node type + parser case + renderer branch + test cases land together.
- Rationale: Snarkdown + Marked both look attractive but introduce a supply-chain dependency and box us in to their AST shape. The user explicitly chose hand-rolled for extension flexibility. ~300-500 LOC is well within the project's vanilla-JS-no-frameworks line.
- Trade-off: edge cases (nested emphasis, link parens in URL, list-item lazy continuation, code-fence variants) take more care than `vendor-and-trust`. Mitigated by the CommonMark-subset test corpus committed to the repo (parametrized Playwright tests, ~50-80 input/expected-DOM pairs) — anything that lands without a corresponding test is rejected.

**Renderer constructs DOM, never uses `innerHTML`**: every node is built via `document.createElement(...)`, with `textContent` for leaf text. This makes XSS-safety a structural property of the library, not a runtime policy. A future contributor cannot accidentally introduce an XSS hole by setting `innerHTML` on a sub-tree because the renderer doesn't accept HTML strings as input — only AST nodes.
- Rationale: chat receives untrusted LLM output every message. The simplest defensible posture is "no innerHTML anywhere in the markdown pipeline."
- Trade-off: slightly more code than `el.innerHTML = renderedHtmlString`. The win is that we never have to maintain an HTML allowlist sanitizer.

**`chat.js` splits via `App.chat.{...}` namespace + helper sub-modules; orchestrator stays in `chat.js`**: pure-helper functions (date bucketing, welcome canvas rendering, message-bubble construction, telemetry overlay rendering, thinking-indicator construction) move to dedicated files at `static/js/areas/chat/{welcome,history-buckets,message-bubble,telemetry-overlay,thinking-indicator}.js`. Each helper file is its own IIFE that attaches to `App.chat.{name}`. The main `chat.js` becomes the orchestrator: holds closure state (`currentSessionId`, `ws`, `sessions`, `pendingJoinId`, `currentAgentName`, DOM refs), wires the WS lifecycle, calls into `App.chat.{...}` for rendering. `index.html` loads helpers BEFORE `chat.js`. Target: chat.js drops from 782 → ~400 LOC; no behavioural change.
- Rationale: the project has no bundler. Module concatenation isn't an option; concat-by-script-tag-order is the established pattern (see `theme.js`, `icons.js`, `app.js`). The split between "stateful coordinator" and "pure helpers" is the right architectural boundary — closure state must stay in one place; rendering can live wherever it's called from.
- Trade-off: the `App.chat` namespace will be visible globally (any code can call `App.chat.renderWelcome(...)`). Acceptable: same scope as `App.icons`, `App.theme`, etc. Helpers are NOT lifecycle-bearing — they take inputs and return DOM nodes or DocumentFragments. Document the contract in `agents.md`.

**Shared component CSS lifted into `components.css` `@layer components`; per-area CSS shrinks**: families promoted — `.list-item` + `.list-item-delete` + `:focus-within` reveal; `.field-row` + `.field-input` + `.field-textarea` + `.field-select` + the select-arrow data-URL SVG; `.section-title` + `// PREFIX` `::before`; `.btn-outlined-cyan` + `.btn-filled-cyan` + `.btn-muted-destructive`; `.chip` + `.chip-remove`; `.empty-state`. Per-area CSS keeps overrides ONLY for genuine differences (e.g., `.area-studio .list-item.confirm-delete` is a studio-specific state that doesn't make sense as a base). Utility classes for display toggling — `.is-hidden`, `.u-flex`, `.u-block` — land in the previously-empty `@layer utilities`, finally giving that layer a purpose.
- Rationale: F3 debrief flagged 313 per-area selectors with substantial duplication; F2 debrief flagged the `// PREFIX` consolidation explicitly. F4 absorbs both with a coherent shared-primitives lift.
- Trade-off: per-area class names need to migrate (`.session-item` → `.list-item.session-item-extra`-style). This is a real touch-everything migration but shrinks each per-area CSS file 30-50%. Behaviour is preserved (existing tests pass). Update `agents.md` design-system section with the new vocabulary.

**Streaming protocol: chunks-only via WS with a `done` terminator**: `LLMProvider.stream(...)` is an OPTIONAL async-iterator method on the base class. Default implementation calls `complete()` and yields one final `StreamChunk` (forward-compat for providers that haven't yet been wired or won't be). Streaming-aware providers (Anthropic, OpenAI, Ollama, mock) implement actual streaming. Server `_process_and_broadcast` consumes the iterator; per chunk, broadcasts `{type: "assistant_chunk", content: <new-tokens>}`; on completion, broadcasts the existing `{type: "done"}`. Non-streaming providers continue to emit `{type: "assistant", content: <full>}` + `done` (current behaviour). Client: receives `assistant_chunk` events, accumulates into an in-progress assistant bubble (`textContent`); on `done`, if a streaming bubble is in flight, swaps its content for the markdown-rendered version of the accumulated text.
- Rationale: chunks-only is leaner than chunks-plus-final and matches the LLM-API native shape (Anthropic / OpenAI / Ollama all yield deltas, not cumulative text). The client already accumulates for the in-progress bubble, so synthesizing the final from chunks costs nothing. Backward-compatible: the existing non-streaming code path is unchanged.
- Trade-off: a future provider that emits cumulative text (rare) would need a `chunk.is_delta: bool` discriminator. Document the convention as `content` is *new tokens since the last chunk*; if a provider yields cumulative, it converts to deltas before yielding.

**Markdown rendering scope: assistant messages only**: user messages stay `textContent` (user typed it; markdown there would be confusing if they used `**` literally). Tool messages stay `textContent` (preserves `> tool(args)` format + tool output verbatim). System messages stay `textContent` (short status). Welcome canvas guidance text is constructed from JS with explicit `<a>` nodes — unchanged by F4.
- Rationale: markdown rendering is value-add for LLM-emitted text. User input doesn't have the same "long, structured output" problem. Tool output is structured by the tool itself; rendering it through markdown could distort intentional formatting. System messages are short status / error strings; rendering them through markdown would be over-engineering.
- Trade-off: a future use case (e.g., "user pastes markdown they want rendered") is not supported. Acceptable; revisit if surfaced.

**Streaming-during-markdown: append textContent during stream; swap to markdown render on `done`**: avoids re-parsing the markdown on every chunk (which would either flicker or misrender partial markdown — `**bold` mid-token has no end). The in-progress bubble shows plain accumulated text during streaming; on `done`, the accumulated text is rendered as markdown and swapped in.
- Rationale: simplest correct approach. Mid-stream markdown rendering is fundamentally underdefined (partial syntax has no canonical semantics); the workarounds (incremental parser with re-render on each chunk) are heavy and fragile.
- Trade-off: a "click-to-copy" or "click-to-stop" affordance during streaming uses the textContent representation. Acceptable.

**Mock provider streaming knob**: `stream_chunks: list[str]` config key (default `[]`); paired with the existing `delay_ms` (interpreted per-chunk during streaming). When `stream_chunks` is set, `stream()` yields each chunk with a `delay_ms` wait between. When unset, `stream()` falls back to the default-implementation behaviour (calls `complete()`, yields one chunk). Deterministic E2E coverage of the streaming path.
- Rationale: the mock provider's purpose is exactly this kind of test fixture. Adding the knob is ~10 lines.
- Trade-off: none.

**HAT as the final required leg**: F4 is heavily visual (markdown rendering across themes, code-block aesthetic, the streamed-text feel) AND structural (chat.js split, shared component lift). Both deserve a real-time pacing pass with the user.
- Rationale: F2/F3 precedent; the F3 debrief lessons-learned note "discovery-via-HAT can absorb scope" remains operative. Apply the F3-lesson scope guardrails: when the user surfaces "while we're here..." additions during HAT, weigh divert-to-F5 explicitly.
- Trade-off: ~1 hour of synchronous user time. Worth it.

### Technical Approach

The flight orders work to keep the regression net intact at every leg-end:

```
01 chat-component-split ──► 02 shared-components-lift ──► 03 markdown-library ──► 04 streaming-infrastructure ──► 05 markdown-streaming-integration ──► 06 hat-and-comprehensive-review
       (refactor)                  (refactor)                  (new lib)              (server + client foundation)         (wire-up)                     (interactive final)
```

### Adaptation Criteria

**Divert if**:
- The chat.js split surfaces a closure-state coupling that can't cleanly cross a sub-module boundary — pause, propose a different cut, get user agreement before continuing.
- Hand-rolled markdown's nested-emphasis algorithm proves to be more than ~100 LOC — escalate: either accept the cost, or reduce subset (e.g., make nested emphasis non-recursive in v1, document accordingly).
- A streaming provider's SDK shape is incompatible with the `AsyncIterator[StreamChunk]` contract (e.g., callbacks-only) — wrap with a small adapter, but if the wrap is ugly, defer that provider to a follow-up flight and ship the rest.
- The shared component CSS migration uncovers an area-specific override that's load-bearing (e.g., a `.session-item` rule that admin.js depends on transitively) — narrow the lift surface and document the residual divergence.
- Existing browser tests start failing in non-obvious ways during the chat.js split — STOP, root-cause before continuing. The split is supposed to be behaviour-preserving.

**Acceptable variations**:
- chat helper sub-module file names + count (5 ± 2 files; the split boundary is what matters).
- Specific class names for shared components (`.list-item` vs `.app-list-item` vs `.c-list-item`) as long as documented.
- Markdown library extension surface (`App.markdown.extend(NodeType, parserFn, renderFn)` vs direct AST registration) as long as documented and tested.
- Streaming chunk granularity (per-token vs per-event) — provider-determined; document what each provider yields.
- Whether `addOrUpdatePartialMsg` lives in chat.js or as `App.chat.appendChunk(text)` helper — implementation choice.
