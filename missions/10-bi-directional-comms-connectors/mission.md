# Mission: Bi-directional Communication Connectors

**Status**: active

## Outcome

GleepGlorp agents become reachable on the third-party communication platforms the operator already uses, and can reply on those same platforms — without forcing the operator to sit in front of the Chat UI or the CLI. The operator registers a connector account (a Discord bot, a Slack workspace app) from an Admin surface using the same encrypted-credentials, masked-edit, doctor-style-probe pattern that LLM providers and MCP sources already use; attaches that account to one or more agents through the Studio agent editor — mirroring the pattern Studio already uses for MCP attachment; and from that moment forward, when an authorized peer sends a message to the bot on the external platform, an agent session resumes (or is created on first contact) and replies on the same platform, in the same channel/thread/DM, as the same bot identity. The local Chat UI is the operator's private console into every connector-attached session: the operator sees the unified history (everything peers exchanged with the bot plus the operator's own private side-chat with the agent), can ask the agent questions about that conversation, can direct the agent to send specific messages back to the platform, and is shielded from accidental leakage in the other direction — operator-typed messages and the agent's responses to them stay in the local Chat UI and never propagate to the external platform unless the agent explicitly chooses to relay something via the platform-send mechanism. The agent loop itself remains untouched — connectors are a new I/O surface that sit beside the CLI and Web interfaces and drive `agent.step()` the same way the WebSocket handler does today, not a new agent kind. Two connectors land in this mission: Discord (persistent gateway WebSocket — the hardest case, and the one the operator most wants) and one second connector that re-uses every abstraction Discord exercises in order to prove the contract isn't accidentally Discord-shaped. The connector contract, the inbound-outbound adapter separation, the session-key normalization that binds external conversation identities to internal sessions, the two-visibility-layer model (platform channel + operator console), the platform-send tool that gates outbound, the DM-pairing security flow that gates unknown senders, the allowlist resolvers that the operator uses to scope which peers/groups can drive which agents, the per-(agent, account) idle-TTL reaper that mirrors the MCP pool, and the connection-probe diagnostics surface — all of these land as reusable infrastructure so that future connectors (WhatsApp, Twitter, Signal, Telegram, Matrix, iMessage, IRC, etc.) become additive plugins against a stable SDK rather than per-platform rewrites. Credentials never appear in plaintext outside the encryption boundary, the operator console never leaks to the platform, the agent loop is non-intrusively wrapped — if every connector account is disabled, the rest of the-one behaves exactly as it does today.

## Context

Today the only way to talk to a GleepGlorp agent is to open the web UI or run the CLI — both shells assume a single human operator sitting in front of a keyboard, with the WebSocket handler in `interfaces/web/app.py` as the canonical example of how an interface wraps `AgentFactory.create()` and `agent.step()`. There is no surface where an external service can deliver a message to an agent and receive a reply on the same external service. This blocks every workflow where the operator wants an agent to participate in conversations that are already happening somewhere else — Discord servers where a guild is collaborating, Slack workspaces where teammates expect responses in channel, DMs from peers who don't use GleepGlorp themselves.

The reference implementation the operator has explicitly named is openclaw (https://github.com/openclaw/openclaw). Openclaw ships connectors for ~20 platforms (Discord, Slack, WhatsApp, Telegram, Signal, iMessage, IRC, Matrix, Teams, Feishu, LINE, Mattermost, Nextcloud Talk, Nostr, Synology Chat, Tlon, Twitch, Zalo, WeChat, QQ, WebChat, Google Chat) on top of a `plugin-sdk/channel-contract` abstraction. The patterns visible in their Discord plugin source — `ChannelMessageActionAdapter` and `ChannelMessageToolDiscovery` contracts, `createChatChannelPlugin` factory, separate `outbound-adapter.ts` + `outbound-session-route.ts`, session-key normalization, account-scoped allowlists, pairing-prefix stripper for unknown senders, doctor-style probe adapter, per-channel runtime state — are the right shape to borrow. This mission will not copy openclaw code (different language, different runtime, different ergonomics) but will adopt the same architectural decomposition because it has already been validated against the long tail of platform-specific quirks.

The-one's M07 (MCP Integration) is the precedent for "external integration surface registered in Admin, attached in Studio, lifecycle-managed via per-(agent, source) pool with idle-TTL reaper, credentials encrypted under the existing Fernet key + rotation pipeline, masked in API responses with the `__MASKED__` sentinel, graceful-failure-isolated so a broken external service doesn't take the chat session down." Every one of those patterns transfers. What does NOT transfer from M07: bubblewrap sandboxing (third-party APIs are already sandboxed by the provider — there is no local subprocess to isolate), stdio-vs-streamable-HTTP transport dispatch (each platform has its own protocol — Discord Gateway WebSocket, Slack Socket Mode WebSocket, REST POSTs for sending — and there is no benefit to a unifying transport layer), and MCP protocol-version pinning (each platform manages its own API versioning).

The Twitter/WhatsApp shape is materially different from the Discord/Slack shape — Twitter and WhatsApp are webhook-driven, stateless request-response, and require a publicly addressable HTTPS endpoint registered with the platform. The-one runs locally by default; surfacing a public webhook URL is an operational concern (tunneling, reverse proxy, etc.) that materially expands the mission's surface area beyond what's needed to validate the connector contract. This mission therefore lands the two persistent-connection cases (Discord + one other persistent-connection platform), proves the contract on them, and leaves webhook-driven platforms as the canonical follow-on shape — additive plugins against the same SDK, with the public-endpoint operational story handled separately when the operator needs it.

The Single-User Local Tool security posture (SECURITY-MODEL.md) is preserved: no auth on the-one's own routes is added, the connector layer does not introduce a server-mode network surface inside the-one beyond what's necessary to maintain outbound platform connections, and untrusted-inbound-message handling uses the pairing + allowlist pattern to gate which external peers can drive an agent. A Discord bot token grants posting rights to a Discord server the operator controls; the trust boundary the operator has to reason about is whoever sends messages to that bot, not the network.

## Success Criteria

- [ ] An operator can register, edit, and remove connector accounts (a Discord bot identity, a Slack workspace app identity) through an Admin surface that follows the existing design language and the existing LLM-providers / MCP-sources patterns, with all sensitive fields (bot tokens, signing secrets, app credentials) persisted under the same encryption pipeline that already protects LLM and MCP credentials
- [ ] At least two connector implementations ship in this mission, both built against a single connector-plugin contract that is the only file any future connector author needs to satisfy; at least one of the two uses a persistent connection (gateway WebSocket or socket-mode WebSocket) so that the contract is exercised against the persistent-connection failure modes (reconnect, heartbeat, idle reaper) and not only against trivially-stateless HTTP
- [ ] When an authorized peer sends a message to the bot on the external platform, an agent session is resumed (or, on first contact, created) and the agent's reply is delivered back on the same platform, in the same conversational location (channel / thread / DM), as the same bot identity — round-tripping through the existing `agent.step()` loop without modifying it
- [ ] Unknown senders contacting a connector-attached agent are gated by a pairing or allowlist mechanism that the operator controls from the connector's Admin or Studio surface; an unknown sender's message does not reach the agent loop until the operator has approved that sender, and approval state survives a restart of the-one
- [ ] The mapping between external-conversation identity (platform + account + channel + thread + peer) and internal `chat_sessions` row is stable and reversible — the same external conversation always resolves to the same session across restarts, and the internal session can be inspected from the Chat UI (the operator can open Chat and see the conversation the bot has been having on Discord)
- [ ] A connector account can be attached to any number of agents through the Studio agent editor, using the same UI shape that Studio already uses for MCP attachment; an inbound message on the platform routes to exactly one of the attached agents per the operator-configured routing rules; the agent's tool registry is unchanged whether or not a connector is attached
- [ ] Per-connector-account override of credentials is supported through the same resolver pattern the built-in tools and MCP sources use today, so an operator can have one connector account globally defined and multiple agents using their own substituted credentials without duplicating the connector-account definition
- [ ] A doctor-style probe accessible from each connector account's Admin detail page verifies the connection lifecycle (token validity, expected permissions, reachability of the platform's API and gateway endpoints), surfaces the result in the same diagnostic shape M07's MCP inspector established, and runs without dispatching any messages to peers
- [ ] Persistent connections are managed by a per-(agent, connector-account) lifecycle pool with idle-TTL reaping and transparent respawn on next use, integrated into the FastAPI lifespan so the connection tree is drained on shutdown; this mirrors the M07 MCP pool's shape so a future maintenance review can compare them side-by-side
- [ ] Failures isolated to the connector layer (platform API outage, token revoked, gateway disconnect that exceeds reconnect budget) do not take the chat session down — the affected connector account surfaces a degraded status in its Admin detail page, the agent runtime continues to serve the remaining connectors and the rest of its tool registry, and the operator can re-enable the connector without restarting the-one
- [ ] Credentials never appear in plaintext outside the encryption boundary — not in API responses, not in logs, not in the doctor-probe output, not in connector connection-state inspection panes — and the existing edit-form `__MASKED__` sentinel pattern is preserved so an operator can re-save a connector account without retyping its secrets
- [ ] When the operator opens Chat for an agent that has connector-attached sessions, those sessions are listed alongside the Chat-UI-native sessions; opening one shows the full unified conversation history — both the platform-visible exchange (peer messages + agent's platform replies) AND any operator-console exchange (the operator's private messages to the agent + the agent's replies to the operator) — in a single timeline, with clear visual distinction so the operator can see at a glance which messages were visible to peers on the external platform versus which stayed local
- [ ] A connector-attached session has two visibility layers feeding the same agent context: (i) the **platform channel** — peer-visible messages exchanged on the external platform; (ii) the **operator console** — the local Chat UI, where the operator can talk privately to the agent about the platform conversation. Messages the operator types in the Chat UI on a connector-attached session, and the agent's replies to those operator messages, DO NOT propagate to the external platform — peers see nothing of the operator console. The agent's responses to operator messages stay in the operator console by default
- [ ] The agent has context awareness across both visibility layers — when answering operator questions in the operator console, it can reference what was said on the platform channel; when responding to platform inbound, it benefits from any direction the operator gave in the operator console; the two are not separate context windows
- [ ] The platform-send capability is a **built-in tool** registered alongside the other 19 built-ins (filesystem, shell, web, etc.) — operator-enableable / operator-disableable from the Admin built-in-tools surface using the existing two-layer resolver pattern. When enabled, the tool is auto-available to any agent attached to a connector account (without requiring the agent to invoke `search_tools` first); when disabled, no agent on the system can send to any platform — making "disabled platform-send" a deliberate operational state, not an oversight
- [ ] When the platform-send tool is disabled but a connector account is otherwise wired up, inbound platform messages are still received, persisted to the session, and visible to the operator in Chat — the agent has access to the message as context and may respond in the operator console — but no mechanism exists to send anything back to the platform. From the peer's perspective the bot is silent; from the operator's perspective the inbound flow is intact. Re-enabling the tool restores outbound without re-configuring the connector account or restarting any session. This dual state is a deliberate test case proving the inbound and outbound paths are decoupled
- [ ] The platform-send tool can only target connector accounts the calling agent is currently attached to, and within those accounts, only conversation locations the agent has access to per the same allowlist/ACL resolution that governs inbound routing — an agent cannot use the tool to post arbitrarily anywhere on the platform just because it has a Discord bot token in scope
- [ ] Each connector-attached session has a defined lifecycle that determines when an inbound message continues the existing session versus starts a fresh one; the mechanism is consistent across connectors (same lifecycle model applies to Discord, Slack, and any future connector), surfaces from the connector account's Admin detail page as a configurable parameter, and is overridable by an explicit operator action (a platform-side command from peers, or a "start new session" action from the Chat UI)
- [ ] A connector account can have any number of agents attached to it; inbound messages route to a specific agent through a layered scheme — first an operator-configured default-routing rule (e.g. per-channel or per-DM defaults), then a peer-issued command on the platform that overrides the default within the peer's permissions; the routing decision is logged in the session metadata so the operator can see why each session went to which agent
- [ ] A platform-side command surface lets peers on the external platform invoke a small, well-defined set of commands — at minimum: list agents the peer is permitted to invoke, switch to a different agent within permissions, identify which agent is currently responding, start a new session, and discover available commands; commands are gated by per-(agent, peer) and per-(agent, group/channel) permissions configured by the operator, mirroring and composing with the connector-account-level allowlist so an unauthorized peer cannot enumerate agents they cannot use
- [ ] The command surface is implemented as a connector-agnostic primitive — adding a new connector inherits the full command set without re-implementing the parser, the permission checks, or the help text; per-connector deviations (platform-native slash commands vs. text-prefix parsing) sit behind the same abstraction and produce the same observable behavior to the operator
- [ ] Each layer of the integration has automated coverage proving its contract — the encrypted persistence layer for connector accounts, the connector-plugin contract on at least one stub implementation, the session-key-normalization round-trip, the pairing/allowlist gating, the resolver's substitution behavior on connector-shaped overrides, the lifecycle pool's reaper and reconnect paths, the doctor probe's success and failure paths
- [ ] The Admin connector-account surface, the Studio connector-attach surface, the doctor probe, and the in-Chat connector-session view all meet the M04/M06 design-language quality bar without alignment-flight rework
- [ ] A second connector lands behind the same plugin contract and adds no new files outside its own directory and the registration site — establishing by example that adding a third (WhatsApp / Twitter / Signal / Telegram / Matrix / iMessage / IRC / Teams / etc.) is contained additive work against a stable SDK

## Stakeholders

**Primary**: the operator (single-user local tool) — wants their agents to participate in conversations on platforms where their peers already are, without sitting in front of the Chat UI.

**Secondary**: future connector authors (potentially the operator themselves, in subsequent missions) — want a contract stable enough that adding a new platform is a containable amount of work, not a fork of the runtime.

**Tertiary**: peers on the external platforms — should experience the agent as a coherent participant in their conversation (replies appear in the right place, in the right thread, from the right identity) without leaking the-one's internals (tool-call traces, system prompts, internal session IDs).

## Constraints

- The agent loop in `agent/core.py` and `agent/factory.py` is **not** modified by this mission. Connectors are an I/O surface that drives `agent.step()` the same way the existing WebSocket handler at `interfaces/web/app.py` does. If a connector requires an agent-loop change to function, that is a signal that the connector design is wrong.
- The Single-User Local Tool security posture is preserved. No authentication is added to the-one's own HTTP routes. The connector layer does not open inbound network ports inside the-one beyond what is required to maintain outbound platform connections (Discord Gateway and Slack Socket Mode are outbound WebSockets from the-one's perspective — no public endpoint needed).
- Credentials are encrypted under the **existing** Fernet key + rotation pipeline. This mission does not introduce a second encryption scheme. Adding a new credential type follows the M07 precedent of extending the rotation transaction to cover the new corpus, preserving the **encryption-rotation invariant** documented in `agents.md` (single-pass crash-safe transaction across all encrypted corpora, atomic key-file replacement via `os.replace`, no plaintext-only mid-state on disk).
- The connector plugin contract is the only file a future connector author needs to satisfy. New connectors do not modify the agent loop, the tool registry, the LLM layer, the MCP layer, the database schema (beyond per-connector configuration rows), or any pre-existing connector. Cross-connector coupling is the signal that the contract is too narrow and needs to be lifted before the next connector lands.
- The per-(agent, connector-account) lifecycle pool follows the **worker-task-per-entry** pattern established in `the_one/mcp/_pool.py` (one owning task per pool entry, cancel-scopes never crossing task boundaries). This is a non-negotiable structural constraint: M07 surfaced anyio cross-task `CancelScope.__aexit__` failures whenever this pattern was violated, and the resolution is the precedent this mission inherits.
- Wire-protocol clients use **maintained SDKs with pinned versions**, following the M07 precedent of pinning the `mcp` SDK to a specific protocol revision. The agents.md "no agent framework — written from scratch" stance applies to the agent loop and tool registry, NOT to wire-protocol clients. Discord (e.g. discord.py) and Slack (e.g. slack-sdk) clients are SDK-based; the connector plugin contract on top of them is hand-rolled.
- The mission follows the named **agents.md project conventions** without re-litigating them: `trust-the-runtime`, `canonical-import + convenience-re-export`, `structural-Protocol-satisfaction`, `verbatim-message-equality`, `gated-debug-instrumentation`, `host-side-bench-drift-detection`, `live-read-across-lazy-resolver-boundary`, `container-test-entrypoints-reach-via-make`, and `landmark-elements-over-aria-roles`. Flight planning may add mission-specific conventions; it does not lower the bar on these.
- Webhook-driven platforms requiring a publicly addressable HTTPS endpoint are explicitly **out of scope** for this mission. The reasons are operational, not architectural — the public-endpoint story (tunneling, reverse proxy, port exposure) is a separable concern that should not gate landing the persistent-connection cases. The connector plugin contract MUST accommodate webhook-driven platforms in its shape so they slot in additively later; this mission MUST NOT close design space that webhook plugins will need.
- This mission does NOT add voice, video, or non-text modalities. Attachments (images, files) at the platform level may be received and forwarded to the agent as the agent's tool-driven file-handling already supports, but native voice/video transcription, screen sharing, and similar are out of scope and remain future-mission work.
- `THE_ONE_TEST_MODE` and any other test-only env-var seam MUST NOT appear in `Dockerfile`, `docker-compose.yml`, or container entrypoints. Connector test seams use the same project-wide pattern as the `mock` LLM provider — code-side stubs and dependency injection in tests, never env-var-driven runtime branching in production paths.
- **Message visibility is stored as a field on the canonical `Message` dataclass** (`the_one/llm/base.py`), defaulting to `None` for non-connector sessions (renders as platform-visible / no-tag). This keeps the agent's unified-context-in-prompt trivially correct (the LLM sees one history; visibility is metadata, not a separate channel), keeps `messages_to_ui_events` in `the_one/db/codec.py` a one-line projection extension, and avoids a parallel-storage path that would diverge from the LLM-facing Message shape. Non-connector callers see byte-identical behavior.
- **F10 search_tools baseline carve-out is deliberate, narrow, and documented.** The F10 baseline that `search_tools` and `continue` are the only schemas visible at session start MUST remain the rule for tools the agent discovers on its own. The platform-send built-in is an explicit exception: when a connector account is attached AND the platform-send tool is operator-enabled, its schema is pre-loaded into the session's visible schemas at construction time. The exception is documented at the F10 invariant assertion site (`agent/core.py` and any test that asserts the strict baseline) so it does not read as drift later. No other tool gets auto-availability through this mission.
- **System-prompt composition learns a connector-aware extension point.** `the_one/agent/config.py` currently composes the agent's effective system prompt as a single string. This mission adds a per-construction composition step that, when a connector is attached, injects either "to reply to peers on the platform, call send_to_platform_channel" (tool enabled) or "the platform-send capability is currently disabled by the operator; your replies in this session reach the operator only, not the platform — do not pretend to have sent to the platform" (tool disabled). Non-connector sessions see byte-identical prompts.

## Environment Requirements

- Development: existing the-one dev environment (Docker container or local Python 3.11+, both already supported via `Makefile` / `pip install -e .`).
- Runtime: outbound network access to platform APIs (Discord Gateway + REST, Slack Socket Mode + Web API). No inbound port exposure required by either Discord or Slack in their persistent-connection modes.
- External accounts: the operator MUST have a Discord application + bot user with the required intents (Message Content intent, Guild Members intent if member resolution is needed), and a Slack workspace with an app installed in Socket Mode with the relevant `*:read` and `*:write` scopes. These accounts are operator-provisioned; the-one does not register on the operator's behalf.
- Tooling: no new system dependencies beyond what M07 already pulls in (the Python ecosystem covers Discord and Slack client libraries; the choice between maintained client SDKs vs. hand-rolled HTTP/WebSocket clients is a flight-level design decision).

## Open Questions

These resolve during flight planning; the answers go in the relevant flight artifact's Design Decisions section.

- [ ] **Session-key normalization shape**. What is the canonical form of the key that binds (platform, account, channel, thread, peer) → `chat_sessions.id`? Specifically: do threads collapse into their parent channel, or do they get distinct sessions? Do DMs from the same peer across two Discord servers share a session or split? Does a guild-channel session share with the same peer's DM session? The wrong call here is the kind of mistake that surfaces six months later as "why is my Discord agent confused about which conversation it's in"; the right call needs flight-level investigation against Discord and Slack semantics before any code lands. **Note**: the implementation mechanism is settled — a schema migration following the v8/v9/v10 pattern in `db/schema.py`, adding either a `chat_session_external_keys` join table or platform-keyed columns on `chat_sessions`. The question is the shape of the key, not whether a migration happens.
- [ ] **Session lifecycle — when does an inbound message continue vs start fresh?** Three viable models: (a) **forever-persistent** — same key always resolves to the same session, indefinitely (natural "bot remembers you" semantics; risks context-window bloat and stale-context bias over months); (b) **idle-timeout** — same key within N hours of last activity continues; after N hours, the next inbound message starts a new session (matches human "this is a new conversation" intuition; needs a defensible default for N); (c) **explicit command** — never time out; rely on a platform-side `/reset` or `/new` command from peers and an explicit "start new session" action from the operator in the Chat UI. **Default unless redirected**: hybrid — idle-timeout with a default of 24h, configurable per-agent or per-connector-account from the Admin detail page, AND a platform-side reset command, AND an operator-driven "start new session" action from the Chat UI. The 24h default mirrors common bot-platform conventions; the configurability matters more than the specific number. Resolve the exact default and the command syntax during flight planning.
- [ ] **Multi-agent routing — default rules + peer command override + permissions**. When two or more agents are attached to one connector account, a single inbound message must route to one agent. Three layers compose: (i) **operator-configured default routing** — per-channel, per-DM, per-thread, or per-(account, peer) rules that say "in the absence of a peer command, this conversation goes to agent X"; (ii) **peer-issued command override** — `/talk-to <agent>` switches the conversation's active agent within the peer's permissions; (iii) **per-(agent, peer) and per-(agent, group/channel) permissions** that gate both default-routing eligibility and command-issued switching. The implementation mechanism for permissions is settled — extend the allowlist resolver established for connector-account-level allowlists down one scope level to per-agent ACLs. The questions to resolve at flight planning: what's the default-routing-rule schema (one rule per channel? rule precedence when multiple match?), what's the exact command vocabulary (`/talk-to`, `/agents`, `/whoami`, `/reset`, `/new`, `/help` are the proposed minimum), and how does an attached agent that is unreachable (revoked permission, disabled) surface to the peer (silent default to a fallback, or explicit error message)?
- [ ] **Shape of the platform-send mechanism**. The agent needs an explicit way to push a message to the platform from a connector-attached session (so the operator console doesn't write through automatically, and so the agent can deliberately respond to peers when it chooses to). Three viable shapes: (a) **a tool** — e.g. `send_to_platform_channel(target, content)` — fits the existing tool-registry model cleanly, surfaces in the per-response tool-call trace for free, and lets the agent decide when to invoke it; (b) **a structured response envelope** — the agent emits text wrapped in a marker the connector layer parses out, e.g. `[[platform-send: #engineering]] Hi team, ...`; (c) **default routing by trigger source** — agent's raw text reply auto-routes to whichever channel the most recent inbound came from (operator console or platform), with a tool only for cross-channel sends. **Default unless redirected**: (a), the tool shape — it's the most explicit, it composes with the existing tool surface (search_tools, per-response trace, narrow/substitute resolver overrides for connector-target restrictions), and it makes the "operator console is local-only" invariant easy to enforce mechanically (no platform-send tool call → no platform message). The tool is auto-available on connector-attached sessions only; non-connector sessions don't see it.
- [ ] **Default vs. directed platform reply on platform-inbound**. When a peer messages the bot, does the agent's raw text reply automatically go to the platform (matching the convention that a peer expects a response when they ask a question), or must the agent always invoke the platform-send tool to reply? Auto-reply is simpler for the natural case but blurs the "tool-mediated outbound" invariant if the platform-send is supposed to be the only path. **Default unless redirected**: tool-only for outbound — every platform message originates from an explicit tool call, including replies to peer-initiated conversations. This keeps the model symmetric (the operator console is local by default; the platform is silent by default; the only way bytes reach a peer is via a deliberate tool call) and makes the audit trace one-to-one with what peers saw. Confirm at flight planning; the trade-off is whether the agent system prompt needs an explicit "you must call send_to_platform_channel to reply to peers" instruction.
- [ ] **Command-surface implementation — platform-native vs. text-prefix**. Discord and Slack both support platform-native slash commands (registered via Interactions API / app manifest, autocomplete, type-safe arguments) AND parse plain text. Platform-native is better UX but requires per-platform registration, version-bumping when the command set changes, and per-platform-specific argument schemas. Text-prefix (e.g. `!agents foo`, `@bot agents`) is portable and zero-registration but has worse discovery and no autocomplete. **Default unless redirected**: text-prefix parsing for v1, with the command surface abstracted so platform-native slash-command registration can land additively as a future enhancement on a per-connector basis without touching the agnostic command primitive. Confirm during the flight that introduces the command surface.
- [ ] **Pause/resume semantics for connector-driven sessions**. The agent's pause state (`Agent._deferred_tool_calls`, `_remaining_iterations`) is in-memory only, and the existing `_resume_paused_session` in `interfaces/web/app.py` is WebSocket-bound. When a connector-driven session triggers `MCPAuthRequired` mid-reply, the connector layer has no equivalent resume driver. **Default unless redirected**: connector-attached agents that hit a tool requiring OAuth fail that tool with a clear-to-the-LLM error envelope; the operator resolves the auth in the Chat UI (which DOES support pause/resume), and subsequent connector-inbound messages continue normally. This keeps the mission contained; adding a connector-side resume driver is a candidate follow-on mission, not a Flight 7 deliverable.
- [ ] **Second connector choice**. Slack (Socket Mode WebSocket — close enough to Discord to share patterns, different enough to surface accidental Discord-coupling) is the default plan, but Signal (libsignal client, end-to-end encrypted) or Matrix (federated, well-documented protocol, no app review process) are also viable. Each has different ergonomics for the operator and different stress-tests of the contract. Resolve during the flight that introduces the second connector. **Note**: if Slack, the two-token shape (xapp-* app-level token for Socket Mode connection + xoxb-* bot token for Web API) is heavier than Discord's single-bot-token model and the connector-account schema MUST accommodate multi-credential accounts in the contract — not as a Slack-special-case.
- [ ] **Reply correspondence — edits and deletes**. When an agent reply has been delivered to the platform and the agent then edits or retracts that reply in a later turn, does the connector edit/delete the platform-side message, post a correction message, or do nothing? The "do nothing" answer is the simplest and likely the right one for this mission, but the design must account for it.
- [ ] **Outbound rate limiting and backpressure**. Discord enforces per-route and per-bot global rate limits; Slack enforces per-method tiers. When the agent generates output faster than the platform will accept it, does the connector queue, drop, summarize, or pause the agent? Resolve at the flight that builds the outbound adapter.
- [ ] **Identity model — bot vs. user**. Discord and Slack expect the agent to act as a bot user. The bot has a fixed identity; it cannot impersonate the operator. Confirm during flight planning whether this is sufficient or whether some workflows require user-token mode (Slack's xoxp tokens, Discord's user-token mode which is against ToS — likely a hard no).
- [ ] **Connector-type coordination tax**. agents.md documents a six-layer checklist for adding a new LLM provider type (Pydantic `Literal`, registry, schema CHECK constraint, API gating, frontend badges/tokens, default-config layer). The connector contract introduces an analogous tax. Flight 1 establishes the parallel checklist and writes it into `agents.md` as part of the contract's documented surface — closing M07 debrief's still-open "promote architectural conventions to CLAUDE.md/agents.md" action item for the connector-type case.
- [ ] **Reference-implementation pattern study**. Before the connector-plugin contract flight finalizes its shape, do a focused read of openclaw's `plugin-sdk/channel-contract` and `plugin-sdk/channel-core` (TypeScript) to inventory which abstractions they exposed, which they regretted, and which would translate to the-one's Python idioms. This is the "borrow without copying" step.

## Known Issues

Emergent blockers and issues discovered during execution. Add items here as flights surface problems that affect the broader mission — things not anticipated during planning but visible at the mission level.

- [ ] **Inherited from M07**: `the_one/mcp/_pool.py` has open test-isolation debt (a `_shutting_down` flag that can leak between tests when the pool is exercised under the test runner's shared event loop). The new connector pool is structurally equivalent to `_pool.py`. Flight 1 SHOULD decide whether to share a common worker-pool primitive (paying down M07's debt in passing) or build a parallel implementation that leaves the debt deferred. The decision goes in Flight 1's Design Decisions; either is defensible but the choice must be made deliberately.
- [x] **Per-session lock unification (surfaced in Flight 3 planning, owned by Flight 5)**: Flight 3's inbound dispatcher uses a module-level `_session_locks: defaultdict[str, asyncio.Lock]` in `connectors/_inbound.py` to serialize concurrent inbounds for the same `chat_sessions` row. The WebSocket handler at `interfaces/web/app.py:201,252` already serializes operator-typed messages per session via `Session.processing_lock` (attached to in-memory `Session` instances in `app.py`'s private `_sessions` dict). For Flight 3 alone these locks don't compete (the WS path doesn't yet touch connector-attached sessions). **Flight 5 MUST reconcile** before operator-typing into a connector-attached session ships, otherwise a race between an inbound and an operator-typed message on the same session will produce interleaved `agent.step()` calls and silently corrupt the session's message history. Options for F5 leg planning: (a) route the WS operator-input path through the connector dispatcher (with `visibility="operator"` set at entry) so `_session_locks[session_id]` is the sole serialization primitive, or (b) refactor `Session` out of `app.py` to a neutral module so `Session.processing_lock` is shared between WS and dispatcher.

- [x] **Live-broadcast WS-typed visibility-tagging asymmetry (surfaced in Flight 5 debrief, owned by Flight 6)**: F5's storage-edge shim at `interfaces/web/app.py:_process_and_broadcast` tags `Message.visibility = OPERATOR_VISIBILITY` AFTER `agent.step()` runs — correct for persistence and refresh-render, but the live broadcast at `app.py:817-819` (the raw dict event emitted BEFORE `agent.step`) does not yet carry the visibility key. Operator-typed messages on connector-attached sessions appear unmarked until refresh. The render-side channel is already wired (JS reads `data.visibility` through `addMsg`, `buildToolMsg`, the streaming-bubble closure). The dispatcher path closes the gap naturally because its broadcast fires AFTER tagging. **Flight 6 closes** via a pre-step injection of `"visibility": OPERATOR_VISIBILITY` into the dict-literal `user_event` at `app.py:817-819` when `session.platform is not None`, mirroring the codec's projection rule at `db/codec.py:173-176`. Severity: Important (UX), not Critical. Closed by Flight 6 Leg 6 — operator-typed messages on connector-attached sessions now carry visibility=operator at live broadcast time; refresh path is unchanged.
