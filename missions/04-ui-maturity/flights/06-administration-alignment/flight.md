# Flight: Administration Alignment

**Status**: in-flight
**Mission**: [UI Maturity](../../mission.md)

## Contributing to Criteria

- [ ] Each functional area (Chat, Studio, Administration) reflects the established design language and meets a quality bar suitable for showing to external developers without apology *(F6 brings the final area — Administration — onto the F4/F5 design system; closes the alignment trio)*
- [ ] Common interaction patterns (creating a new entity, editing, confirming destructive actions, displaying empty states) behave consistently across all areas *(F6 makes provider CRUD inherit studio's canonical shape: tile grid + entity editor + `[Back] [Cancel] [Save] [Test]` cluster + Danger Zone delete + `App.confirmDialog` dirty gate; resolves the F5 debrief's editor-Delete migration question)*
- [ ] Critical user flows (start a new chat, create and configure an agent, add and verify a provider) progress without dead-ends, unexplained errors, or unclear next steps *(provider create flow gets restructured end-to-end with the same `[Back] [Cancel] [Create] [Test]` action cluster as agent create)*
- [ ] Navigation state (current area and active sub-view, including selected entity) is reflected in the URL and survives page refresh *(hash routing extends to `#admin/{category}[/{provider-id|new}]` — category, selected provider, and create mode all survive refresh)*
- [ ] Automated browser tests cover the critical user flows and fail on regression, runnable both locally and in CI *(provider tile grid + page-header + dirty-state modal + hash-routing for provider detail get explicit browser tests; existing provider-CRUD test adapts to the new selectors and renamed `+ New Provider` button)*

### Open Questions

- [ ] **Combined System page default** — should `#admin` redirect to `#admin/system` (the F5-style "first category is default" pattern) or to `#admin/providers` (the more-frequently-used destination)? The current behavior is `#admin` → `#admin/general` (which is going away). Default position: `#admin/system`. Aligns with F5 precedent (`#studio` → `#studio/agents` — agents being the primary content but listed first); for admin the order is System → Providers (with System first as the simpler "what's configured" surface), so first-listed-is-default keeps consistency. Backward compatibility: `#admin/general` defensively redirects to `#admin/system` in `hydrateState`.

- [ ] **Provider editor: sections vs. tabs?** Studio's agent editor uses a 3-tab idiom (General / Knowledge / Tools) because each tab is a distinct entity-type facet. Provider editor's content is more linear: connection config → test result → discovered models → danger zone. Tabs would force "Connection" / "Models" / "Danger Zone" as tabs, which is artificial since they're sequential, not alternative facets. **Default position**: single-page with `.editor-section` blocks (Connection, Models, Danger Zone) — same shape as studio's General tab content (Identity / LLM Configuration / System Prompt / Behavior / Advanced / Danger Zone). The `App.tabs` helper stays unused for F6; it remains available for future surfaces. Re-evaluate during HAT if linear flow feels cramped.

- [ ] **Provider URL identity: id or slug?** Provider names are user-supplied and may contain spaces/punctuation; `id` is a stable UUID and URL-safe. Default: use `id` (matches the existing data shape on `data-id`). URL: `#admin/providers/{provider_id}`. Encoding via `encodeURIComponent` is defensive but unnecessary for UUIDs. The hard-link survives a name change (id is stable; name is not). The provider-grid tile carries `data-id` already (admin.js:367), so the migration is selector-stable.

- [ ] **`#admin/providers/new` for create vs. modal?** Studio uses URL-distinct create mode (`#studio/agents/new`-equivalent via `_createMode` + serializeState returning `'agents'` since create has no name yet). - [ ] **Editor Delete → `App.confirmDelete` migration scope (F5 debrief Recommendation 5)** — F5 deferred the studio agent editor Delete migration to F6 design-time. F6 adds a third destructive surface (provider editor Delete). Three options:

### Design Decisions

**Two-category sidebar (System merges General; LLM Providers stays)**: collapse the three-category list to two. The General category's read-only paths/server/concourse env-var displays move into the System page as a new "Environment" section above the existing Appearance + Encryption sections. The sidebar shows a `.section-nav` with two items: System, LLM Providers. URL contract: `#admin` redirects to `#admin/system`; `#admin/system` shows the combined page; `#admin/providers` shows the tile grid; `#admin/general` redirects to `#admin/system` for backward compat (one-line in `hydrateState`).
- Rationale: matches the user's explicit direction. General was a thin read-only env-var dump; merging into System collapses two pages of mixed-density content into one denser System page. Reduces sidebar surface area to two real destinations.
- Trade-off: System page becomes longer (three sections — Environment, Appearance, Encryption — scrolling). Acceptable; modern web apps have tall pages.

**Sidebar migrates to canonical `.section-nav`**: `admin-category-list` + `admin-category-item` rules in `admin.css` get deleted; admin's sidebar renders via the F5 `App.layout.renderSectionNav` helper (renamed from `App.studio.renderSectionNav`). Studio's existing call-site updates to the new namespace; one-line change. The `aria-current` + roving tabindex contract is preserved verbatim.
- Rationale: F5 invented the `.section-nav` primitive explicitly anticipating F6. The F5 design decision text said "admin's category nav at admin.js's left rail is the obvious F6 consumer" (flight.md:235). F6 fulfills that.
- Trade-off: studio.js + agents.md reference `App.studio.renderSectionNav` — the rename is a small breaking change for the namespace string. Mitigated by single-grep migration.

**Provider tile grid replaces the row-based card list (with `.entity-tile` breaking rename)**: LLM Providers section renders a CSS-grid (`grid-template-columns: repeat(auto-fill, minmax(280px, 1fr))`) of `<button class="entity-tile provider-tile" data-testid="provider-card" data-id="{id}">` tiles. Each tile shows provider name (large bold via `.entity-tile-name`), type badge (existing colored badge — `.entity-tile-badge` for the canonical position; `.admin-provider-badge--{type}` composition for color), base_url snippet (mono caption via `.entity-tile-meta`, truncate-ellipsis). Click → `#admin/providers/{id}` (the editor). Keyboard: tile is a `<button>` with native Enter/Space activation; Tab cycles tiles. NO per-tile delete X-button; NO inline `[Edit][Delete]` action cluster. **Studio markup migrates to canonical names in the same leg**: `.agent-tile`/`.agent-tile-grid`/`.agent-tile-name`/`.agent-tile-description`/`.agent-tile-meta` rules in `components.css` rename in place to `.entity-tile`/`.entity-tile-grid`/etc. (no composition aliases retained); studio's `agents-grid.js`-equivalent + agent-editor JS modules update markup strings to emit canonical class names; the 5 test files referencing the old selectors (see Open Questions) get bulk-updated in this leg.
- Rationale: matches studio post-F5-HAT exactly (tile grid as the inventory canonical shape; destruction centralized in the detail editor's Danger Zone). F5 debrief Lesson 1 ("Multi-affordance destruction without justification") explicitly informed this. Breaking renames now per user direction — keeps the vocabulary simple.
- Trade-off: deleting a provider now requires two clicks (tile → editor → Danger Zone Delete + confirm) vs. the current one-and-confirm. Acceptable; provider deletion is rare and benefits from the explicit "look at the entity you're about to delete" step. The agent-usage check (currently in `handleProviderDelete`) moves to the Danger Zone Delete handler unchanged. Test sweep is bounded (5 files, ~12 selectors total).

**Page-header with title + `+ New Provider` button (canonical `.page-header` lift, breaking rename)**: lift `.studio-page-header` / `.studio-page-title` / `.new-agent-btn` from `studio.css` into `components.css` as canonical `.page-header` / `.page-title` / `.new-entity-btn` AND **rename studio markup to use the canonical names directly** (no composition aliases). The legacy class names cease to exist. Admin's System and LLM Providers pages each render a `.page-header` with `<h1 class="page-title">{Page Name}</h1>`; the LLM Providers page's `.page-header` adds `<button class="btn-outlined-cyan new-entity-btn" data-testid="new-provider-btn">{square-pen icon} New Provider</button>` on the right. Same `square-pen` icon, same `.btn-outlined-cyan` composition, same right-aligned-via-`margin-left: auto` layout as chat's `.new-chat-header`. Studio JS modules update their markup strings to emit the canonical names; per-area `studio.css` rules for these classes (currently lines 9-12) get deleted.
- Rationale: matches the user's explicit direction (breaking renames now). Three areas use the same page-header + primary-action pattern; canonical names with no aliases keeps the vocabulary simple and scan-friendly.
- Trade-off: studio markup-string edits are slightly bigger than alias-keeping, but no tests reference these class names so the sweep is bounded.

**Provider editor: linear sections (NOT tabs)**: the provider detail page is a single scrolling editor with three `.editor-section` blocks: Connection (name, type, base_url, api_key + eye toggle), Models (auto-fetch on edit-mount; shows Ollama lifecycle panel for `ollama` type, read-only model list for others), and Danger Zone (Delete Provider button — edit mode only). Above these sections sits an `.editor-header` with provider name as title, `{type} · {base_url}` as subtitle (when editing); plus a `.form-actions` cluster with `[← Back] [Cancel] [Save|Create] [Test]` (Test only enabled when an `id` exists — i.e., disabled in create-before-first-save).
- Rationale: linear content favors sections over tabs (per Open Question above). Mirrors studio's General tab structure (which is itself a linear section list of `.editor-section` blocks).
- Trade-off: longer single-page scroll vs. tabbed compartmentalization. Acceptable; a single provider's full surface fits in one viewport on most screens.

**Action cluster mirrors studio: `[← Back] [Cancel] [Save|Create] [Test]`**: top-right of the editor inside `.editor-header` (using `.form-actions` for layout). Save uses `.btn-filled-cyan`; Cancel + Test + Back use `.btn-outlined-cyan`. Save is disabled when `!dirty` (edit) or `!valid` (create); Cancel is paired with Save's enabled state via `checkDirty()` (F5 HAT precedent). Test is enabled when the editor has a saved provider id (i.e., always in edit mode; disabled in create-before-first-save). Save label switches to "Create" in create mode; on POST 201, the URL upgrades from `#admin/providers/new` to `#admin/providers/{id}` and the editor switches to edit mode (Test enables).
- Rationale: matches the user's explicit direction. Same cluster, same disabled-state semantics, same mode-aware Save label as studio.
- Trade-off: in create mode, the user sees a Test button they can't click until first save. Mitigated by the disabled state communicating "save first to test."

**Hash routing extension to `#admin/{category}[/{provider-id|new}]`**: `serializeState()` returns `'system'` (when on System), `'providers'` (when on LLM Providers grid), `'providers/new'` (when in create mode), or `'providers/{id}'` (when editing a specific provider). `hydrateState(sub)` parses defensively: `null` / unknown → `'system'`; `'general'` (legacy) → `'system'`; `'system'` / `'providers'` map directly; `'providers/new'` enters create mode; `'providers/{id}'` selects + opens editor (with hydrate-vs-fetch race protection — pending-id branch in `serializeState` mirrors studio's `_pendingSelectName` pattern). Refresh on every URL returns the user to the exact view.
- Rationale: matches the user's "hard links" direction; mirrors F5's hash-routing extension contract. The F3 router's serialize-after-hydrate path performs the `#admin` → `#admin/system` and `#admin/general` → `#admin/system` redirects for free; F6 does NOT add new redirect logic.
- Trade-off: extends admin's hash-routing complexity from 1-level (category) to 2-level (category / provider-id|new). Bounded; matches studio's complexity.

**Editor Delete migrates to `App.confirmDelete` (resolves F5 debrief Recommendation 5)**: both the studio agent editor's `Delete Agent` button (at `studio.js:512-542`) AND the new provider editor's `Delete Provider` button consume `App.confirmDelete(btn, onConfirm, {confirmLabel: 'Confirm Delete?'})`. The chat session-item delete continues using the helper too. Helper has three permanent consumers; canonical destructive-confirm pattern across the app.
- Rationale: F5 debrief Key Learning 3 — helpers earn standardization at ≥2 consumers; F6 brings the count to 3 permanently and removes divergence between editors.
- Trade-off: one studio edit (agent editor swaps inline two-step for `App.confirmDelete` call). Test churn: assert the new helper applies `.confirm-delete` instead of `.delete-btn.confirm`; verify `confirmLabel` is honored (capital-D "Confirm Delete?" preserved). One-line per call site.

**Combined System page sections: Environment / Appearance / Encryption**: the merged System page renders three `.editor-section` blocks. **Environment** carries the existing read-only env-var-derived rows (Paths section = data_dir + workspace_dir; Server section = host + port; Concourse CI section = concourse_target + concourse_pipeline) — visually grouped via `.section-title` subheadings within the Environment section. **Appearance** keeps the existing theme toggle (`App.theme.renderToggle`). **Encryption** keeps the existing rotate flow (two-click confirm + flash messages). The existing "Settings are configured via environment variables" note moves into the Environment section.
- Rationale: collapses two pages of similar-density content into a single page. The user explicitly asked for this.
- Trade-off: System page is longer (three top-level sections + three Environment subsections). Acceptable; the alternative (separate pages) is the status quo F6 is removing.

**Provider editor `.danger-zone` section pattern (lift from studio)**: the provider editor's bottom section (edit mode only) renders `<div class="editor-section danger-zone"><div class="section-title danger-zone-title">Danger Zone</div><button class="btn-muted-destructive delete-btn" data-testid="delete-provider-btn">Delete Provider</button></div>`. Lift the `.danger-zone` + `.danger-zone-title` rules from `studio.css` to `components.css` so admin and studio share canonical Danger Zone styling.
- Rationale: matches the user's explicit direction. Single canonical Danger Zone primitive across editors.
- Trade-off: small CSS migration; no behavior change.

**Ollama lifecycle panel (pull search, load/unload/delete, VRAM) carries forward unchanged inside the Models section**: the existing `renderOllamaModels` + `wireOllamaActions` + `ollamaAction` + pull-search + pull-progress + pull-cancel surface (admin.js:789-1204, ~415 LOC) moves into `static/js/areas/admin/provider-models.js` as a sub-module under the new `App.admin.renderProviderModels` namespace. No behavior change; selectors stay (`.admin-pf-pull-*`, `.admin-pf-model-*`, `.admin-pf-vram-*`); CSS rules stay in `admin.css` for the per-area pull/lifecycle visuals (these are admin-specific and don't earn lifting unless a future area needs the same UI). The Models section header gets a `.section-title` "Models" heading consistent with the rest of the editor.
- Rationale: low-risk preservation of feature-rich existing behavior. Lifting Ollama-specific styling to `components.css` would require a generic-but-empty primitive elsewhere; not earned today.
- Trade-off: ~415 LOC of admin-specific code stays admin-specific. Acceptable; the feature surface is admin-bounded.

**`App.layout.renderSectionNav` namespace lift**: rename `App.studio.renderSectionNav` (and `App.studio.updateActiveSection`) to `App.layout.renderSectionNav` (and `App.layout.updateActiveSection`). The helper itself is unchanged; only the namespace string moves. Both studio and admin consume the canonical helper.
