## NEW FINDING — the invalidation signature is counts-only (a live blind spot)

`studio.js:466-468` — `knowledgeItemsSignature(status)` is
`JSON.stringify(status.items) + '|' + status.chunks`. **Counts only.**

The re-fetch in this run fired **only because `delta.md` moved `indexed` 3→4 and
`chunks` 3→4.** `beta.md`'s edit changed no count and no chunk count (49→100
bytes, still one chunk). **Had only `beta.md` been edited, the signature would
have been identical and no `/items` re-fetch would have occurred at all** — except
by luck, if a 5-second tick landed inside an indexing transient that was here
~20 ms wide.

**So the edit half of checkpoint 8 rode entirely on the addition half's count
change.** The two halves are not independently proven.

**The two defects currently mask each other**, and that is the important part:
the blind spot is harmless *only* because the row renders nothing a content-only
change would alter. **Adding the per-row freshness field would immediately turn
the blind spot into a visible, reproducible staleness bug.**

**Therefore file as ONE leg, not two squawks** (the Validator's recommendation,
adopted): (i) add a per-row freshness signal — `/items` **already returns**
`indexed_at`, `content_hash`, `size_bytes` and `mtime` per item — and (ii) widen
the signature to something that moves on content change, e.g. folding per-item
`indexed_at`/`content_hash` in, or having `/status` expose a cheap
max-`indexed_at`.

are 24 / 2 / 1**, which is what the Executor's report used. Recorded so a future
