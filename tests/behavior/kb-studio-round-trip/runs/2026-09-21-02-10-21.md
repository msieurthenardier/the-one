## The voided run — an operational hazard finding in its own right

Run 1 passed checkpoints 1-7 and reached step 8, where the Executor found
`GET /status` returned **no `content_freshness` key at all** — absent, not null.
A documented sibling-of-`items` field missing entirely is a schema mismatch,
not a data-state fact, and that is what made it read as *wrong* rather than
*empty*.

Traced in about five minutes: `grep` found the implementation, its commit was
`e7fea7e` (2026-09-20 18:50), the server process had started **2026-09-19
14:11** — over 28 hours earlier. `the-one serve` has no `--reload`, so Python
changes need `make restart`. **Seven checkpoints had been judged against the
previous flight's backend.**

**Why it stayed invisible, which is the generalizable part**: static JS and CSS
are served from disk per request, so Leg 2b's `.confirm-lapsed` cue and Leg 2a's
rendered `kb-item-indexed-at` field were genuinely live and correct. Only the
Python was stale. **The run looked healthy because the half being observed was
the fresh half.** A partially-stale environment produces evidence that is
locally valid and globally meaningless.

Restart confirmed the diagnosis: `content_freshness` and
`folders[].skipped_dirs`/`skipped_entries` were absent thirty seconds before and
present thirty seconds after.

**Root cause is two-sided**, and both halves are recorded: the Orchestrator
verified the instance's data directory and state but never its build; and the
spec's own Preconditions are silent on it (defect #10).

**The app cannot currently answer "is this instance running the code I think it
is."** It exposes `settings.data_dir` and env vars — process config, not code
identity. The Executor's proposal: a `git_sha` or bundle-hash field on
`GET /api/info`, diffed once at apparatus-scan time against
`git rev-parse HEAD`. That converts a 90-minute detective exercise into a single
comparison. **Recorded as a product operability gap, not merely a spec gap.**

## Clauses that are correctly designed but were never stressed

**A future maintainer must not read these PASSes as proof the paths work.**

- **Step 7's positive degrade branch** ("if a degrade line is shown, it names a
  cause…") was **never exercised in either run**. Both runs only hit the
  negative branch. Two clean PASSes say nothing about whether the positive
  branch functions.
- **Step 6's ordering clause** was observational, not adversarial — 15 chunks
  rendered in the order the backend returned them. No scrambled response was
  ever fed to the frontend to confirm it *sorts* rather than *happens to agree*.
- **Step 10 does not prove "resumes rather than restarts".** Catching the stop
  at `indexed:0` means both behaviours yield identical post-restart state. A
  sharper design would snapshot which item ids and `content_hash`es were already
  `indexed` before the stop and assert those exact records survive untouched.

## Incidental findings — candidate squawks

1. **Same-named knowledge bases are indistinguishable in the inventory.** Two
   rows read `kb-studio-renamed —`, pixel-identical: no id, no creation date, no
   folder-path preview. The Executor had to open each and read the id from the
   URL to delete the right one. **Knowledge-base deletion is cascading and
   irreversible.** DD-17 made the *backend* collision-safe; the UI never got the
   equivalent treatment.
2. **The attach toggle is invisible to role-based accessibility queries.**
   `get_by_role("checkbox")` → 0 elements, though a real, functional
   `<input type="checkbox">` exists. Standard custom-switch markup, but this
   codebase audits colour contrast (`test_design_tokens_a11y.py`) and nothing
   audits custom form-control semantics.
3. **No build-identity endpoint** — see the voided-run section. The most
   actionable of the three.
4. Untested footgun: does `PUT /api/agents/{name}` 422 or silently ignore the
   server-derived `kb_tool_names` field if a caller forgets to strip it?
