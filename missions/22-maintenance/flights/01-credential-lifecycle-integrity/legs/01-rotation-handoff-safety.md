# Leg: rotation-handoff-safety

**Status**: completed
**Flight**: [Credential lifecycle integrity and observability](../flight.md)

## Objective
Make `POST /api/encryption/rotate` unable to strand any encrypted row on a key the process does not hold: stage the new key as an `encryption.key.next` sidecar before the DB commit, promote it after, self-heal a leftover sidecar at startup, log every outcome, and bring the two corpora the rotation currently misses (`tool_configs.secrets`, `agent_external_credentials.secret`) into the same transaction.

## Context

- **Flight Design Decision Q1 (two-phase sidecar)** is the spec for the handoff. This leg implements it exactly: stage → commit → install in memory → promote on disk; startup reconcile decides a leftover `.next` by probing ciphertext.
- **Scope addition (flight-log Decision D1):** while reading the route for this leg, two encrypted corpora were found outside the rotation transaction. `the_one/interfaces/web/api.py:rotate_encryption_key` re-encrypts five columns (`llm_providers.api_key`, `llm_providers.secrets`, `mcp_sources.secrets`, `connectors.secrets`, `agents.tool_overrides`/`mcp_overrides`). It never touches `tool_configs.secrets` (schema v32, M16 F08 L03 — `ToolConfigRepository` at `the_one/db/repositories.py:ToolConfigRepository` decrypts via the tolerant `_decrypt_secrets_blob`, so built-in tool API keys silently become `{}` after a rotation) or `agent_external_credentials.secret` (schema v36, M21 F03 — `AgentExternalCredentialRepository.load_all` decrypts strictly, so a rotation with any `ext_` credential present makes the next app start raise `InvalidToken` inside `lifespan`). Both are pattern-copies of the existing loops and are in this leg because the startup reconcile must enumerate every ciphertext corpus anyway — designing it around five when there are seven would bake the gap in.
- **Ordering fix that rides along:** today `encryptor.install_key(new_key)` (`api.py:5771`) runs after the awaited connector-pool eviction (step 4b, `api.py:~5732-5754`). Between `await conn.commit()` and `install_key` other requests can run and encrypt new rows under the *old* key, and evicted pool entries re-acquired in that window decrypt new-key rows with the old key. The new ordering installs the key in memory synchronously after the commit — no `await` between them — and evicts afterwards.
- **Pre-existing, not addressed here:** rows created by a concurrent request between step 1's SELECTs and step 4's UPDATEs are committed under the old key. Single-operator app, awaited-interleaving only; recorded in the flight log Anomalies for the debrief, not fixed in this leg.
- **Prior-leg learnings:** none (first leg). Squawk 0011 (PR #178) introduced `_write_key_atomic` (`the_one/encryption.py:13`) — the staging write reuses it unchanged.

## Implementation Guidance

1. **`the_one/encryption.py` — pending-key primitives (do this first; everything else builds on it).**
   - `def next_key_path(key_path: Path) -> Path: return key_path.with_name(key_path.name + ".next")`.
   - `Encryptor.__init__(self, key, key_path=None, pending_key: bytes | None = None)`. Keep `self._key`; add `self._pending_key`; call `self._rebuild()` at the end of `__init__`. `_rebuild()` sets `self._fernet` to `Fernet(key)` when no pending key, else `MultiFernet([Fernet(key), Fernet(pending)])` — **canonical first**, so `encrypt` uses the canonical key and `decrypt` accepts both. Add a read-only `pending_key` property and `key_for(ciphertext: str) -> Literal["pending", "canonical"] | None` (tries `Fernet(pending)` only when a pending key is set, then `Fernet(canonical)`; `InvalidToken` → next; `None` when neither decrypts — never raises on a missing pending key) so the reconcile never reaches into private attributes.
   - `stage_pending_key(self, new_key: bytes) -> Path`: requires `key_path` (raise `RuntimeError` like `rotate_key`); `_write_key_atomic(next_key_path(self._key_path), new_key)`; set `_pending_key`; `_rebuild()`; return the sidecar path.
   - `promote_pending_key(self, key: bytes | None = None) -> None`: `key = self._pending_key if key is None else key`; `RuntimeError` if both are `None`; `os.replace(next_path, key_path)`; then `install_key(key)`. The explicit argument exists because the route installs the key in memory **before** promoting (AC3) and `install_key` clears `_pending_key` — without it, the route's promote would call `install_key(None)` and crash on the happy path. `rotate_key` and the startup reconcile call it with no argument (pending still set). Let `OSError` propagate — the caller decides.
   - `discard_pending_key(self) -> None`: unlink the sidecar if present (`missing_ok=True`), clear `_pending_key`, `_rebuild()`.
   - `install_key(self, new_key)`: set `_key`, clear `_pending_key`, `_rebuild()` (existing contract: memory only, disk is the caller's job).
   - `resolve_pending_key(encryptor, samples: Iterable[str]) -> Literal["absent", "promoted", "discarded"]`: module-level, DB-free. If `encryptor.pending_key is None` → `"absent"`. Otherwise classify each sample with `encryptor.key_for(sample)`. Count `under_pending` / `under_canonical_only`. Decide: `under_pending > 0` → promote (WARNING if `under_canonical_only > 0`); `under_pending == 0 and under_canonical_only > 0` → discard; nothing decidable → promote. The promote and discard branches **perform the mutation** — call `encryptor.promote_pending_key()` / `encryptor.discard_pending_key()` respectively — before returning the string; this function is the reconcile's effector, not a pure classifier. Log the outcome at INFO with the counts. Use `logging.getLogger(__name__)` — the module has no logger today.
   - `get_encryptor`: after reading `key`, `nxt = next_key_path(key_path)`; `pending = nxt.read_bytes() if nxt.exists() else None`; pass it to `Encryptor`. Cache semantics unchanged.
   - `rotate_key(reencrypt)`: `new_key = Fernet.generate_key()`; `self.stage_pending_key(new_key)`; `try: reencrypt(self, Encryptor(new_key)) except: self.discard_pending_key(); raise`; `self.promote_pending_key()`. Note: while staged, `self` decrypts with both keys — harmless for the callback contract.
   - Harden `_write_key_atomic`: wrap the whole write / fsync / close / **`os.replace`** sequence in `try/except BaseException: os.unlink(tmp_path)` (suppress the unlink's own `OSError`; re-raise) so a failed staging write — including a failing final rename — leaves no `.tmp.*` sibling (AC1).

## Edge Cases
- **`.next` present and identical to `encryption.key`**: `resolve_pending_key` sees every sample decrypt under both → counts as `under_pending` → promote (a no-op replace). Fine; do not special-case.
- **`.next` present, DB has zero encrypted rows**: promote. The pending key becomes canonical; nothing was encrypted under the old key.
- **`.next` unreadable/corrupt (not a valid Fernet key)**: `Fernet(pending)` raises `ValueError` in `Encryptor.__init__`. `get_encryptor` must catch that, log a WARNING naming the sidecar path, and proceed with the canonical key only — the reconcile then sees `pending_key is None` → `"absent"`, and the corrupt file stays for the operator. Add a test.
- **Staging succeeds, commit succeeds, `install_key` runs, promote fails, then the process is killed before the operator restarts**: covered — reconcile promotes on the next start.
- **Windows**: `os.replace` over an existing file works on Windows; mode bits are a no-op (existing `skipif(os.name != "posix")` pattern for permission asserts).
- **CLI-only operator**: `the-one chat` constructs its store via `get_encryptor` with no web lifespan. With the reconcile added to `_run_cli` (step 4) it self-heals the same way; before that call runs, `get_encryptor` already decrypts under both keys, so reads never fail. The remaining documented window is a CLI process that was *already running* during a crashed rotation — it keeps encrypting under the canonical key until restarted.
- **Concurrent rotate calls**: not serialized today and not in scope; unchanged.
- **`agent_external_credentials` row whose `secret` fails strict decrypt**: rotation aborts with the `InvalidToken` surfacing as a 500 before any write — the same posture as a corrupt `api_key`. Do not swallow.
