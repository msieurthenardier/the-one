# Behavior Test: Discord Multi-Agent `/talk-to` Override Routing (F15)

**Slug**: `discord-multi-agent-routing`
**Status**: draft
**Created**: 2026-06-01
**Last Run**: never

## Intent

Verify that a Discord peer can redirect its own messages to a NAMED attached agent with the text-prefix `/talk-to <agent>` command, against real traffic (the one remaining facet of mission criterion #7 — multi-peer / multi-agent routing). The peer posts `/talk-to Connector Agent 2` into a channel; the command is parsed at dispatch **step 11** (`_parse_command(working_envelope.text)`) which runs BEFORE the policy/engagement gate at step 11.5 — so a plain `/talk-to …` post needs NO `@mention` to be processed (it is intercepted, never reaching the engagement gate) and produces a routing entry with `disposition == "command-intercepted"`. `_handle_talk_to` (`_commands.py:151`) joins multi-word names (`" ".join(args)` — the F14 Bug G fix, so "Connector Agent 2" resolves), checks the target is in `_permitted_agents(context)` (attached + ACL-admitting), then writes `session_metadata["routing_override"]`. The peer's NEXT `@mention` in that session then routes via the routing engine's **step 1 — override** (`_routing.py:resolve_routing`): it reads `session_metadata["routing_override"]` and, when it names an attached/admitting agent, returns `RoutingDecision(agent=override, scope="override", reason="override")` — BEFORE the rule-walk (step 2) and first-eligible (step 4). So the override beats a channel rule. `/new` (`_commands.py:198`) writes `session_metadata["ended_at"]`; the next inbound's `resolve_session` sees the sentinel and starts a FRESH session carrying no override (the re-runnable cleanup).

This needs a behavior test, not a unit test, because it exercises the live override path end-to-end: a real gateway event carrying a text-prefix command, the dispatcher intercepting it at step 11 before the engagement gate (no `@mention`, no LLM), the override written to live session metadata, and a SUBSEQUENT real `@mention` whose `agent.step` (LLM) routing decision is driven by `resolve_routing` reading that override out of session metadata — across two separate inbound dispatches sharing one session. No unit can stand in for "a command sets state that a later real inbound's routing reads." The routing entry's `scope`/`agent`/`reason` (read from the session detail) is itself the observable.

The sender is driven by the committed `tests/live/discord_hat/` multi-bot driver (the target connector runs with `ingest_bots=true`; a single burner bot posts `/talk-to` then an `@mention` per phase). A `[mixed-frame]` session-detail probe reads each new routing entry (`disposition`/`scope`/`agent`/`reason`) to distinguish a command-intercept, an override route, and an override-beats-rule route where the channel surface alone can't.

The OTHER #7 facets — multiple agents attached to one connector, multiple peers sending to the same connector, and the per-(agent, peer) ACL precedent — were already verified live in **L4** (PASS 4/4; see `discord-multi-user-routing`). This spec closes the `/talk-to` override facet; together L4 + L6 close #7.

## Preconditions

- the-one is running host-native; the connector worker is up; L1's stdout connector logging is active (so a failed routing/override step is diagnosable from the host log (`make logs`)).
- A dedicated test connector is configured with `ingest_bots=true`, `always_listen=false`, `dm_admission=all`, the test guild on the allowlist, and an account-scope `allowlist.channels` admitting the test channel (so the channel passes ACL; the override/routing then picks the agent).
- **Engagement mechanism:** every ROUTING-scenario message (the `@mention` after each `/talk-to`) `@mentions` the-one's bot. The mention path engages the agent deterministically (outcome=`mention`) with NO inference call — `is_mention` checks the bot's id in `message.mentions` independent of author. `always_listen=false`, so a NON-mention `@`-less post (other than a `/talk-to`/`/new` command) is `policy-silent` (no routing decision). The `/talk-to` and `/new` commands themselves need NO `@mention` — they are intercepted at step 11 BEFORE the engagement gate.
- At least two agents are attached to the test connector (the L4/L5 fixture: **Connector Agent 1** and **Connector Agent 2**), BOTH ACL-admitting all peers/channels (no overlays — restored after L4), so BOTH are valid `/talk-to` targets (`_permitted_agents` returns both).
- The test channel exists in the test guild (the L5 fixture: **test-channel-2**). The test SETS the connector's `config.routing` it needs at run time (Phase B) and RESTORES the connector's prior `config.routing` (captured before any change — `None` when no routing was configured) in a `finally`. Every connector PUT omits `secrets` so the bot token is preserved (`update_connector` at `api.py:2489` keeps `existing.secrets` when absent).
- A local Ollama inference provider is configured (so any inference path runs without external rate limits).
- The operator is logged into the-one's Chat UI in the Chrome MCP browser session, viewing the connector-attached session.
- The bot-peer-equivalence premise (L3) has been confirmed — a burner bot resolves to a peer identically to a human sender (so its `/talk-to` and `@mention` behave as a human peer's would).
- **Timing:** all phases must complete within the connector's `session_continuation_seconds` window so each phase's `@mention` lands in the SAME session the preceding `/talk-to` set the override on. At interactive HAT speed (a handful of fast command-intercepts + a few LLM steps, well under a minute total) this is comfortable; a stalled run that idles past the window would rotate the session mid-phase and drop the override.

Sequencing note: the `/talk-to` command (step 1/3/5) must precede the `@mention` (step 2/4/5) in the SAME session — the override it writes is read by the subsequent inbound's routing. Phase B (steps 3–4) sets a channel rule that the override must beat; Phase C (step 5) re-points the override while that rule is still set, isolating "override decided it" from "rule decided it." The restore + `/new` (step 7) run in a `finally` so a mid-test failure leaves the connector's routing unchanged and the override self-clears on the operator's next `/new`.

> **Committed counterpart:** `tests/live/discord_hat/test_multi_agent.py` (the `discord_hat`-marked test) is the machine-checked counterpart of steps 1–5 and 7: it captures the prior routing, drives Phase A (`/talk-to` intercept + override route to Agent 2), Phase B (override beats the ch2 → Agent 1 channel rule), and Phase C (dynamic re-override to Agent 1), then posts `/new` and restores the connector's prior `config.routing` in a `finally`. The Chrome-MCP attribution row (6) remains the human pass.

> **Disposition-vocabulary note (proven at L4 run time):** the dispositions are `stepped` | `command-intercepted` | `no-eligible` | `policy-silent`. A text-prefix command (`/talk-to`, `/new`) is intercepted at step 11 with NO LLM step → `disposition == "command-intercepted"` (carrying `intercept_source == "builtin"` for the built-in handlers), and it never reaches the engagement gate. An engaged `@mention` route is `stepped`. A routing entry is `{ts, agent, rule_index, scope, match, reason, disposition}`; an override route carries `scope == "override"` + `reason == "override"`. A `policy-silent` on an `@mention` step here indicates an engagement/mention MISS (the `@mention` didn't register), NOT a routing fault.

- Per-user ACL admit/deny differentiation — covered by `discord-multi-user-routing`; here both agents admit all peers/channels so the override, not the ACL gate, is the variable under test.
- `/talk-to` targeting a NON-permitted agent (not attached or ACL-denied) — the handler returns an error and does NOT set the override; not asserted here (both agents are permitted in this fixture).

- Slash-form vs text-prefix command parity (`/talk_to` underscore normalization) — substrate-tested; this spec uses the canonical text-prefix `/talk-to`.
- Wire-level gateway mechanics (intents, reconnect) — substrate-tested, not re-verified here.
