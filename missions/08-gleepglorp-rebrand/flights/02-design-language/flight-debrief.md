## Outcome Assessment

### Objectives Achieved

The flight delivered exactly what its objective stated: a deliberate aesthetic direction (glass + bezel + LED + motion) layered on top of the M04 token-driven design system, plus a live gallery infrastructure under `#admin/design-language` (dev-mode-gated) that future polish flights can sample against. Six legs landed:

- **Two autonomous scaffolding legs** (01 gallery-scaffold, 02 vocabulary-inventory) built the canvas: `GET /api/config` endpoint + boot-blocking client fetch + dev-mode-gated admin category + 9 section modules sampling every in-scope primitive
- **Three interactive vibe legs** (03 glass, 04 bezel + corner machining, 05 indicators + motion + interactive primitives pass) iterated the aesthetic with operator at the wheel
- **One mixed close leg** (06 retune-accent-api-and-alignment) executed the 10-step ordered close: token-mirror → grep sweep → WCAG audit → rebuild → playwright → snapshot regen → HAT → agents.md codification → stability re-run

Outcome: 12 new design tokens (6 glass + 3 bezel + 3 motion) committed to `tokens.css`; the V3b button family treatment applied to all 4 button primitives + app-picker; three new primitives extracted/added (`.checkbox-primary` lifted, `.indicator-led` new, `.telemetry-strip` gallery-only); ~75-line "Mission 08 F2 Design Language Layer" reference subsection added to `agents.md`. All reduced-preference fallbacks live at the token layer.

## What Went Well

- **Boot-blocking `/api/config` channel shipped as designed.** The architectural decision (over render-time gate or server-template injection) survived intact — init contract stayed synchronous, dev-mode gating reads `App.config.dev_mode` at `init()` time without race-checking, defensive `(config && typeof config === 'object')` check from design review made it to production. Forward-looking infrastructure: future config keys (feature flags, build channel, server-resolved settings) drop in without re-litigating the channel.
- **Per-section subdirectory pattern under `static/js/areas/admin/design-language/` vindicated by file sizes.** Largest section module is 122 lines (surfaces); smallest is 36 (tabs); total 721 LOC across 10 files. As a single file this would have been a 700-line module hostile to vibe-editing. The split also matched the existing `admin/` convention and gave each vibe leg a clean editing surface.
- **Design-review gate caught 3 high-severity API mismatches in Leg 02 BEFORE code was written**: `App.tabs.wire()` doesn't exist (canonical is `App.tabs(tablistEl, panelsEl, opts)`); `confirmLabel` is silently ignored (canonical is `confirmText`); markdown `<pre><code>` re-implementation conflicts with `App.markdown.render` (canonical retrofit). Citation Audit pattern (15 entries in Leg 02, 12 in Leg 01) verified every API and line-range claim mechanically against the branch. Continued to deliver as the highest-ROI control in the orchestrator protocol per Flight 1 debrief.
- **Vibe-leg cadence proved out.** The "2-4 options per micro-iteration" rhythm worked: operator picked among compact comparison strips, final token values committed at leg close, iteration trails were captured in flight log after the fact. Three vibe legs in a row didn't drift — each leg's leg artifact recorded its iteration sequence clearly, and the cumulative effect (glass + bezel + indicators+motion) composed without surprises.
- **Token-driven design system absorbed the new aesthetic layer without structural change.** 12 new tokens dropped into the existing `@layer tokens` structure; consumers compose `var(--glass-*)` / `var(--bezel-*)` / `var(--motion-*)` rather than encoding aesthetic details inline. No frameworks added, no hex literals leaking into component rules (all aesthetic values live in `tokens.css`).
- **Reduced-preference fallbacks at the token layer is the right architectural choice.** `@media (prefers-reduced-transparency: reduce)` and `@media (prefers-reduced-motion: reduce)` blocks override token values once, not per-rule across the codebase. Future primitives that compose `var(--glass-*)` or `var(--motion-*)` inherit the fallback automatically.
- **Asymmetric in/out transition pattern emerged organically and is load-bearing.** Base rule uses `--motion-base` (250ms slow); `:hover` rule overrides with `--motion-fast` (150ms fast). Browser reads the destination state's transition at the moment of state change → fast engagement, gentle disengagement. Established on 4 surfaces (`.entity-tile`, `.btn-outlined-primary`, `.btn-muted-destructive`, `.app-picker-button`) — transferable idiom now documented in `agents.md`.
- **Glass + `--panel-shadow-glow` substitution rule held precisely.** All 4 named consumers (`components.css:144, 421, 607` + `chat.css:155`) honored the "substitute, not composite" rule. No surface inadvertently stacked four shadow layers.
- **10-step ordered close in Leg 06 is template-worthy.** Each step's output is the next step's input: retune → mirror → grep → audit → rebuild → playwright → snapshot regen → HAT → docs → stability re-run. The "audit must be green BEFORE snapshot regen" gate is load-bearing — would have caught a non-AA-compliant snapshot capture. **Codify as the canonical aesthetic-flight close.**
- **Gallery as canonical aesthetic-spec surface is project-shaped.** The gallery is part of the running app; it can never drift from the actual primitives. Future polish flights can load `#admin/design-language` instead of re-deriving the design spec from CSS. **The most underrated architectural outcome of the flight.**
- **Operator HAT did its job.** 5 surfaces × 2 themes = 10 walkthroughs; no tactical fixes surfaced.

## What Could Be Improved

### Process

- **Leg 05 absorbed a fourth axis (interactive primitives) that should have been its own vibe leg.** The flight design said "aesthetic surface scope = chrome + interactive primitives (buttons, fields, selects, checkboxes)" — the scope was named. But the three vibe legs were sequenced **glass / chrome / indicators+motion** — those are *surface treatments*, not *primitive types*. The interactive-primitives pass had no natural home in that axis decomposition. Operator surfaced the gap mid-flight ("what about the buttons, checkboxes, fields, selectors, etc?"); Leg 05 absorbed it as a sub-iteration. This was a scope-correction, not scope-miss in flight design, but a **leg-allocation miss**: the vibe-leg axes should have been 4, not 3. **Recommendation**: future aesthetic flights should plan a fourth vibe leg dedicated to interactive primitives, sequenced AFTER indicators+motion so it benefits from the prior axes landing first.
- **Vibe-leg "are we still on-axis?" check-in is missing.** Leg 05's button vibe descended into an "Aqua rabbit hole" (operator's words: "ive gone down the rabbit hole of trying to reproduce this button rather than doing whats right for the UI"). The exploration ultimately sharpened the V3b choice (so net-positive in retrospect), but it consumed iteration cycles. **Recommendation**: after N iterations on the same micro-axis (suggest 5-6), the Flight Director should explicitly ask "is this still serving the flight objective, or are we exploring?" — a soft check-in that preserves operator agency while flagging the exploration→exhaustion boundary.
- **Variant-naming cleanup grep is brittle.** Each vibe leg's "remove temporary scaffolding" acceptance criterion specifies a leg-specific grep pattern (`glass-variant`, `bezel-variant`, `corner-variant`, `pullback-variant`, `indicator-led-variant`, `btn-aqua`, `btn-bounce`, `btn-body-g`, etc.). If a future vibe leg uses a different naming convention, the post-leg cleanup grep won't catch it. **Recommendation**: standardize a single variant-naming prefix convention across vibe legs (e.g., `.iter-*` or `--temp-iter-*`) so the post-leg cleanup grep is universal.

### Technical

- **Bug — `tokens-section.js:29-33` references undefined `--panel-radius-md` and `--panel-radius-lg` tokens.** Only `--panel-radius` (6px) and `--panel-radius-sm` (6px) are defined in `tokens.css`. `getComputedStyle(...).getPropertyValue('--panel-radius-md')` returns an empty string, so the gallery's radius swatches render as 0-radius squares with blank hex labels. **Silent visual degradation, ~3-line fix** — either define the missing tokens or change the array to `['--panel-radius', '--panel-radius-sm']`.
- **`--panel-radius-sm` now equals `--panel-radius` (both 6px) after Leg 04's R2 corner-machining retune.** The flight log notes the slot was preserved "in case operator wants to retune it lower later" — but until that retune happens, any rule using `--panel-radius-sm` is functionally identical to one using `--panel-radius`. There's no observable hierarchy. **Recommendation**: either retune `--panel-radius-sm` to 4px for actual differentiation, or remove the alias.
- **`--panel-shadow-glow` is now a dead token.** Grep across served CSS confirms zero consumers (substituted out at all 4 named sites). The token still exists in `tokens.css` and is referenced once in `agents.md` as historical context. **Recommendation**: a future maintenance pass should either rip the declarations and update agents.md to past tense, OR explicitly reserve the slot for a future "accent-glow active state" need with a comment. Don't let a polish flight quietly introduce a new consumer without a deliberate decision.
- **V3b button gradient image is duplicated literally across 4 selectors** (`.btn-outlined-primary`, `.btn-filled-primary`, `.btn-muted-destructive`, `.app-picker-button`). Same gradient stops verbatim. **Refactoring opportunity**: extract to a CSS custom property `--btn-v3-gradient` so a future retune touches one token instead of four rules. The duplication was an intentional avoidance during the vibe iteration (tokens locked late); now stable, it's paid debt.
- **The deferred LED applications for OAuth status and MCP source connection state are a real loose end.** The `.test-result-*::before` retrofit picked up the provider/agent/tool editor consumers automatically; OAuth status and MCP source connection state didn't auto-retrofit because they use different markup. Leg 05 marked them `[~]` deferred to Leg 06 HAT, which then deferred them further without an action item. **Recommendation**: Flight 3 (Admin Polish) touches the Provider editor which surfaces OAuth status; Flight 4 (Studio Polish) touches the MCP grid which surfaces source connection state. Add `<span class="indicator-led indicator-led--{status}">` markup at these consumer sites during those polish flights — the primitive is ready, just needs the wire-up.
- **Stale `-actual.png` / `-diff.png` snapshot artifacts persist across runs.** Snapshot directory carries ~12 stale comparison files from April runs that survive across regenerations. Doesn't affect correctness but inflates directory size (1.1MB raw vs ~540KB actual baselines) and confuses inspection. **Recommendation**: add a `make clean-snapshots` target (e.g., `rm -f tests/browser/__snapshots__/*-actual.png tests/browser/__snapshots__/*-diff.png`) or have the pixel suite auto-delete stale artifacts on regen.
- **No automated coverage of the boot-block `/api/config` failure modes.** The fetch handler at `app.js:227-249` has three branches (success-with-good-object, success-with-malformed-object, network-failure); none are exercised by automated tests. Pixel/snapshot suite implicitly verifies "boot works" but not "boot survives /api/config 500/timeout/malformed JSON." **Recommendation**: add a Playwright test that uses `page.route('**/api/config', ...)` to inject each failure mode and verify the app boots to chat. ~30 LOC, catches a class of "blank-screen on boot" bugs.
- **No automated coverage of `prefers-reduced-transparency` / `prefers-reduced-motion` token-level swaps.** Verification was DevTools-emulation-based. There's no test that asserts "when `prefers-reduced-transparency: reduce` matches, `getComputedStyle(...).getPropertyValue('--glass-blur')` returns `'0px'`." **Recommendation**: add 4 reduced-preference Playwright tests (2 themes × 2 preferences) that emulate the media query and assert the token-level swap fires. ~50 LOC, catches regressions where someone removes the `@media` block or breaks its specificity.
- **Missing WCAG parametrization for destructive button text-on-soft-danger-bg.** Leg 05's V3b retreatment put text directly on `--status-danger-bg-soft` (`.btn-muted-destructive`) — that pair isn't in the current parametrization list. **Recommendation**: add `(dark, fg, status_danger_bg_soft, 4.5)` and `(light, fg, status_danger_bg_soft, 4.5)` to `tests/browser/design_tokens.py`.

### Documentation

- **Asymmetric in/out transition pattern is buried in agents.md prose.** The pattern is load-bearing (4 surfaces use it) and non-obvious to someone reading a transition rule fresh. Currently a one-paragraph note inside the new Mission 08 F2 subsection. **Recommendation**: promote to its own short heading under `### Affordance patterns` (e.g., `**Asymmetric hover-in/hover-out timing**`) so a developer touching transition rules grep-finds it.
- **"Use `background-color` + `background-image`, never `background` shorthand" rule on glass surfaces isn't explicitly stated.** Inline note exists at one site (`.entity-tile` rule comment); needs to be a composition rule in the agents.md Mission 08 F2 subsection. **Recommendation**: add as composition rule #5 with one sentence — "never use the `background` shorthand on glass surfaces; the shorthand wipes the gleam image."
- **The 10-step ordered close for aesthetic flights deserves a flight-design template entry.** The dependency graph (retune → mirror → grep → audit → rebuild → playwright → regen → HAT → docs → stability) is reproducible across any flight that touches tokens + primitives + snapshots. **Recommendation**: codify in the mission-control `/flight` skill or in this project's `agents.md` as the canonical aesthetic-flight close.
- **Gallery-as-canonical-aesthetic-spec deserves a write-up.** Future polish flights would benefit from "load the gallery first, derive from CSS only when needed" guidance. **Recommendation**: short paragraph in `agents.md` calling out the gallery's role.

## Key Learnings

- **Vibe-leg cadence works for aesthetic flights when the axes are surface treatments, not primitive types.** Three vibe legs covering glass / chrome / indicators+motion was the right decomposition for *treatments*. The "interactive primitives" axis is orthogonal (it's a primitive-type bucket that needs ALL the treatments applied) and required its own leg-shaped vehicle. Future aesthetic flights: separate "treatment-vibe" legs from "primitive-coverage" legs.
- **The gallery as canonical aesthetic-spec surface compounds in value across flights.** Flight 1 had no gallery — it shipped tokens + assets + brand text without a single-page-canvas. Flight 2 built the gallery, used it as the vibe-iteration substrate, and now Flights 3+ have a permanent reference surface that can never drift from the actual primitives. **The gallery + propagation cadence is the architectural pattern; not the specific aesthetic values it carries.**
- **Token-layer fallbacks for `prefers-reduced-*` are the cleanest pattern.** One `@media` block in `tokens.css` overrides every consumer automatically. Future a11y media queries (e.g., `prefers-contrast`, `forced-colors`) should follow the same pattern.
- **Citation Audit + design-review-spawned Developer remain the highest-ROI control.** 3 runtime-fail bugs caught in Leg 02 design review (wrong `App.tabs` signature, wrong `App.confirmDialog` keys, markdown re-implementation collision). Same outcome as Flight 1 — pre-implementation API verification is structurally cheaper than post-implementation rework.
- **Operator HAT remains irreplaceable for aesthetic work.** Automated tests verify color contrast and structural correctness; they don't verify "does this feel like the right aesthetic?" HAT is the last-mile check. It caught nothing critical this flight, but the flight had no critical aesthetic issues to catch — that's the success signal, not a reason to remove HAT.
- **Vibe-leg alternative exploration is a design tool, not noise.** The Aqua rabbit hole sharpened the V3b choice. Future flights should plan for this rather than treat it as scope-creep — but a soft "are we still on-axis?" check-in mechanism would help bound exploration to the part where it pays off.
- **Light-theme aesthetic destinations are operator-driven, not pre-named.** Frosted-white was the planning hypothesis; silver-chrome with violet undertone was the operator's better answer. Don't pre-commit aesthetic destinations in flight design — frame them as starting hypotheses.

## Recommendations

1. **Plan a 4th vibe leg for interactive primitives in future aesthetic flights.** Sequenced after indicators+motion so it benefits from prior axes landing first. The Leg 05 scope-absorption was graceful but cost iteration cycles; future flights should allocate the vehicle explicitly.

2. **Codify the 10-step ordered close as a flight-design template** for any flight that touches tokens + primitives + snapshots. The dependency graph (retune → mirror → grep → audit → rebuild → playwright → regen → HAT → docs → stability) is reproducible and load-bearing — "audit must be green BEFORE snapshot regen" would have caught a non-AA-compliant snapshot capture.

3. **Fix the `tokens-section.js` undefined `--panel-radius-md`/`-lg` references** (`tokens-section.js:29-33`). Silent visual degradation in the gallery; ~3-line fix.

4. **Decide on `--panel-shadow-glow` and `--panel-radius-sm`.** Both are now dead/duplicate tokens. One-line decisions: rip-or-reserve each. Don't let polish flights quietly introduce new consumers without deliberate choices.

5. **Wire the deferred LED applications to OAuth status + MCP source connection state during Flight 3/4.** The primitive is ready; the consumer markup at these sites just needs `<span class="indicator-led indicator-led--{status}">` retrofit. Real loose end from this flight.
