# Mission: Built-In Tool System

**Status**: active

## Outcome

The-one's built-in tool surface is rebuilt around three focused capabilities — filesystem, execution, and web — each properly scoped, configurable at both the tool and agent level, and architected to work across Windows, macOS, and Linux. The self-modification surface (Concourse-driven deploy/rollback/restart, the methodology-aware tools, autopilot, and the runtime-tracking memory) is removed cleanly, along with its supporting prompt narrative. A new Tools section under Administration gives the operator tool-level control over which tools exist and how they behave: per-tool kill switches, per-tool config (path scope, size and timeout caps, URL/host scope, search backend), and clear feedback for connection-style operations. The studio agent editor reflects this tool-level state and lets agents override it per-tool — narrowing constraint values, never widening them. The configuration model is a two-layer composition (tool-level defaults + agent-level overrides) deliberately shaped to generalize beyond built-in tools: when MCP integration lands in a later mission, MCP servers will reuse this same pattern, with shared credentials at the tool level and per-agent identity substitution at the agent level. The remaining tools have automated coverage proving they behave correctly under both normal and constraint-violation conditions, and the platform abstraction layer makes future Windows and macOS support a swap of platform-specific helpers rather than a rewrite of every tool.

## Context

After Mission 04, the-one's UI is mature, but the built-in tool layer hasn't been revisited since the M01 foundation. Today there are 14 tools across six rough categories, and several of them encode assumptions that no longer match the project's direction:

- The original positioning ("self-modifying agent that can edit its own source, run tests, deploy itself, and roll back") is being parked. The agent is pivoting to a more general-purpose personal assistant; the deployment-loop tools (`self_deploy`, `rollback`, `restart`, `run_tests`) and the autopilot Concourse job that drove the loop are no longer the project's focus.
- The agent's persistent memory (`memory`), git wrapper (`git`), and methodology reader (`mission_control`) were built around the self-modification narrative. Without that narrative, they're either dead weight or better expressed through the general-purpose execution tool.
- The tools that *are* core to general-purpose use — filesystem, execution, web — have visible gaps: no in-place edit, no glob/grep, no path scoping, no output caps, no SSRF protection, no readability extraction, no multi-command shell sessions. The default system prompt still walks the agent through the self-modification workflow, which both leaks scope and primes the agent for the wrong set of behaviors.
- There is no tool-level configuration surface. Per-agent enable/disable exists in Studio (M02), but operators can't disable a tool everywhere or set tool-level defaults. The administration surface added in M03/M04 is the natural home for this.
- The configuration model needs to support a pattern that will generalize to MCPs in a future mission: tool-level shared defaults (the tool's own config, including any shared credentials), with per-agent overrides that can narrow constraint values *or* substitute identity values (an agent's own OAuth identity for a specific MCP, an agent-specific Slack workspace, etc.). M05's built-in tools only exercise the narrowing path, but the resolver and storage shape are designed for both from day one so MCP integration doesn't require restructuring.
- The runtime targets WSL today, but the long-term target is a desktop application running on Windows, macOS, or Linux. Path handling, shell selection, Python interpreter resolution, and pty semantics all diverge across these platforms; building cross-platform-aware now (before tool expansion) avoids a refactor against the new tool surface later.

This mission rebuilds the built-in tool layer around the three kept categories, removes the self-modification surface in one coordinated pass, and adds the operator-facing configuration surface that makes the new constraints usable.

## Success Criteria

- [ ] The agent's built-in tool surface is focused on filesystem, execution, and web; deployment, methodology-awareness, persistent-memory, and version-control tools are removed without breaking the agent runtime, the chat experience, or any M01-M04 capability
- [ ] The default system prompt reflects a general-purpose personal-assistant identity, free of self-modification, deployment, and methodology-reader instructions
- [ ] The autopilot scheduling surface is removed cleanly along with its supporting CI plumbing
- [ ] Filesystem tooling supports the full lifecycle — read, write, in-place edit, delete, move, directory creation, pattern-based file discovery, and content search — with predictable behavior under the resolved (tool-level + agent-level) constraints
- [ ] Execution tooling supports both one-shot command execution and multi-command interactive sessions, with sessions isolated from one another and from the agent's parent process environment
- [ ] Subprocesses launched by execution tooling never inherit the parent process's environment beyond a fixed minimal allowlist sufficient for standard tools to function; the agent has no path to read or carry through host secrets via subprocess inheritance
- [ ] Web tooling supports raw HTTP, reader-mode page retrieval, file download, and pluggable search; requests targeting internal-network, loopback, or cloud-metadata addresses are blocked by default with a clear opt-out path for advanced operators
- [ ] Each tool category enforces tool-level constraints — path scope, read-size caps, output caps, timeout caps, URL/host scope — that apply to all agents by default, and per-agent overrides can only narrow those constraint values, never widen them, with the narrowing invariant enforced at a single named resolution layer rather than ad-hoc in each tool
- [ ] The configuration model supports two override semantics at the agent level — narrowing (for constraint values) and substitution (for identity / shared-credential / KV values) — even though M05's built-in tools only exercise the narrowing path; the storage shape and resolver are designed to absorb the substitution case without restructuring when MCP integration arrives
- [ ] Existing agent configurations referencing removed tools load cleanly and continue functioning — stale tool names in `enabled_tools`/`disabled_tools` are silently stripped via schema migration with no operator-visible breakage
- [ ] The administration interface exposes a tool-management surface where each built-in tool can be enabled, disabled, and configured at the tool level, with verification controls (test buttons) for connection-style operations
- [ ] The studio agent editor reflects the tool-level state — tool-level-disabled tools are unavailable to all agents and visibly inaccessible in the per-agent toggle UI — and exposes the agent-level override surface for per-tool constraint narrowing
- [ ] Filesystem and execution tooling are architected for cross-platform support: platform-specific concerns (path semantics, shell selection, interpreter resolution, pty handling) are isolated behind a clear abstraction layer, and the implementation runs cleanly under the current Linux/WSL target without Linux-only assumptions in tool code
- [ ] Each kept tool has automated coverage proving it behaves correctly under happy-path use and under constraint-violation use (path-scope rejections, size-cap truncation, timeout caps, SSRF blocks, binary-file refusals)
- [ ] The new Tools admin section reflects the established design language and meets the M04 quality bar without alignment-flight rework

## Stakeholders

- **Primary user**: Solo developer/operator who interacts with the agent daily and wants confidence that the tool layer behaves predictably, with operator-controlled bounds rather than implicit-trust-the-prompt
- **Future-platform user**: The same operator on Windows/macOS once the desktop-app form factor lands — no Linux-specific tool behavior should leak into their experience
- **Future agents**: Specialized agents that the operator will configure with narrower tool scopes than the system default (research agent with GET-only web, scratchpad agent with home-only filesystem, etc.)

## Constraints

- **No frameworks beyond M01-M04 baseline**: FastAPI + WebSocket + vanilla JS + SQLite + httpx + Pydantic. No agent frameworks, no CSS frameworks, no JS frameworks
- **Subprocess environment is hardcoded-allowlist, not operator-configurable**: subprocesses always launch with a fixed allowlist (`PATH`, `HOME`, `USER`, `LOGNAME`, `LANG`, `LC_ALL`, `TERM`, `TZ`); no UI knob exposes broadening this. A future secrets-manager mission will inject named secrets on top of this baseline; explicitly out of scope for M05
- **SSRF protection is on by default and resolves-then-pins**: web tools refuse loopback, RFC1918, link-local, and cloud-metadata addresses; protection works by resolving hostnames via `ipaddress`-stdlib checks against blocked ranges *and* passing the resolved IP (not the hostname) to the HTTP client to defeat DNS-rebinding TOCTOU. The operator's opt-out shape is a curated allowlist of additional permitted hosts (e.g., `localhost:11434`, `192.168.1.50`) — protection stays in force for everything else; there is no full-disable toggle
- **Two-layer config model**: tool-level config (the tool's defaults, shared by all agents) lives in a new `tool_configs` SQLite table keyed by tool name with a JSON `config` blob, mirroring the existing `mcp_sources.config` / `llm_provider_configs.config` shape. Agent-level overrides live in a new optional `tool_overrides` field on `AgentConfig`, also keyed by tool name with a JSON delta blob. Name-level enable/disable continues to use the existing `enabled_tools`/`disabled_tools` shape on `AgentConfig`. The resolution layer composes the two layers per agent invocation
- **Override semantics are key-aware**: for constraint values (path scope, caps, URL scope, redirect/host policy, denylists), the agent-level override can only narrow; the resolver enforces this invariant. For identity / shared-credential / KV values, the agent-level override substitutes. M05's built-in tools only exercise narrowing — there are no agent-substitutable identity values yet — but the resolver's per-key semantic dispatch is in scope for M05 so the substitution path is testable and ready when MCP integration arrives
- **Pattern alignment with future MCPs**: the tool-level / agent-level pattern adopted here is the same pattern MCPs will use. An MCP server's shared credentials live at the tool level (every agent uses them); per-agent identity (an agent's own OAuth token, an agent-specific account ID) lives at the agent level via substitution. This is design intent, not a contract — but the storage shape and resolver should not preclude it
- **Cross-platform-ready architecture, Linux-verified for now**: tool code must not embed Linux-only assumptions (hardcoded `/bin/sh`, `python3`, POSIX-only path comparisons). Verification on Linux/WSL is sufficient for this mission; full Windows/macOS validation is a follow-up
- **Stubs untouched**: MCP and KB data models and UI shells stay as-is; this mission does not deepen them
- **Preserve M01-M04 functionality**: agent CRUD, provider management, chat persistence, design language, browser tests, deploy pipeline (minus autopilot) all continue working
- **Existing seams**: new admin section follows the M04 `App.layout.renderSectionNav` + `.entity-tile` + `.editor-section` canon; per-agent narrowing reuses the existing `enabled_tools`/`disabled_tools` shape on `AgentConfig`
- **Python 3.11+, async throughout**: unchanged
- **Small-model friendly**: tool descriptions and constraint-violation error messages must be navigable by 7B-class models; no clever exception types, just clear strings

## Environment Requirements

- Local Python 3.11+ with editable install (`pip install -e ".[all-llms,dev]"`)
- Docker and docker-compose (existing dev loop via `make rebuild`)
- Playwright Python binding for browser tests (M04 baseline)
- ruff for linting and formatting
- Concourse CI for the deploy pipeline (autopilot job removed during this mission; deploy/test jobs preserved)
- Verification surface: Linux/WSL only for this mission. Windows and macOS validation are explicitly future work

## Open Questions

- **Agent-level override shape**: a flat `tool_overrides: dict[str, dict]` field on `AgentConfig` (each tool's override JSON-shaped like the matching tool-level config but with narrow-or-substitute semantics per key), a typed Pydantic submodel per tool, or a sibling table keyed by `(agent_id, tool_name)`. Resolved in Flight 2 design
- **Resolver per-key semantic dispatch**: how the resolver knows which keys are narrowing-only vs substitutable — declared on each tool's config schema, declared on each config key explicitly, or by a registry the resolver consults. Resolved in Flight 2 design
- **Resolution-layer placement**: a new `ToolPolicyResolver` invoked by `AgentFactory.create()` for static enable/disable filtering plus a runtime-resolve hook called by tools that read constraint values (path scope, caps, URL scope), or a single resolver invoked at agent build that passes resolved policy into each tool instance. Resolved in Flight 2 design
- **Platform abstraction layout**: single `the_one/platform.py` module, a `the_one/platform/` package with `paths.py` / `shell.py` / `pty.py` submodules, or a thin shared helper inlined into `tools/` with no new top-level module. Resolved in Flight 2 design
- **Path-allowlist representation**: list of root paths (POSIX-canonicalized at write, platform-resolved at compare) vs a structured policy with include/exclude rules vs glob patterns. Resolved in Flight 3 design
- **Default path allowlist**: `~/.the-one` only? `~/.the-one` + a configurable workspace? `~` minus a denylist of system paths? What semantic role does the `/workspace` mount retain when self-modification is gone? Resolved in Flight 3 design
- **Interactive shell session lifecycle**: session addressing (per-agent, per-conversation, per-explicit-handle), TTL, max concurrent sessions per agent, what happens to a session when the agent's turn ends. Resolved in Flight 4 design
- **Search backend extensibility shape**: keep DDG-only with no abstraction, or land a one-method `SearchBackend` protocol now even though only DDG implements it. Resolved in Flight 5 design
- **Tools admin section placement**: peer to System / LLM Providers in the section nav, or nested under System. Resolved in Flight 6 design

Update Studio's `TOOL_CATEGORIES` (drop System banner, drop `run_tests` from Execution; later flights add the new tools). Audit and remove unit tests, AIAT tests (`tests/test_aiat.py::test_run_tests` etc.), and fixtures tied to the removed tools. Schema v7 migration that strips removed tool names from existing `enabled_tools`/`disabled_tools` JSON so stale agent configs load cleanly. Verify no remaining references in agent configs, prompts, docs, `agents.md`, or `CLAUDE.md`.

- [ ] Flight 2: **Cross-Platform Foundations & Policy Resolver** — Two coordinated deliverables: (a) the platform abstraction layer (paths, shell selection, Python interpreter resolution, temp-dir, user-dir, symlink-resolve helpers) as the seam every kept tool will go through; (b) the named `ToolPolicyResolver` (or chosen equivalent) that composes tool-level config with agent-level overrides and is the single place enforcing the narrow-or-substitute semantics per key. Land the new `tool_configs` SQLite table (tool-level) and the new `tool_overrides` field on `AgentConfig` (agent-level). The resolver supports both narrowing (constraint values: path scope, caps, URL scope) and substitution (identity / shared-credential / KV values) — built-in tools exercise only narrowing in this flight, but the substitution path is implemented and unit-tested using a fixture so it's ready for MCP reuse without rework. Migrate existing `read_file`, `write_file`, `list_dir`, `shell`, `python_exec`, `http_request`, `web_search` to use the platform layer; their constraint enforcement routes through the resolver even if the tool-level defaults match today's behavior. No new tools in this flight — pure scaffolding refactor with regression tests proving Linux behavior is unchanged. The seam is the precondition for Flights 3-5.

- [ ] Flight 3: **Filesystem Expansion & Constraints** — Add `edit_file`, `delete_file`, `move_file`, `mkdir`, `glob`, `grep`. Add tool-level path-scope allowlist + agent-level narrowing through the resolver, tool-level read-size cap (default 50MB) + agent-level narrowing, binary-file detection and refusal (null-byte sniff in first 8KB), symlink-escape detection (refuse symlinks that resolve outside the active path scope). Constraint-violation error messages standardized. Tests cover happy path and every constraint type.

- [ ] Flight 4: **Execution Expansion & Constraints (Unix pty scope)** — Harden `shell` and `python_exec` with the hardcoded-allowlist subprocess environment (enforced consistently across `shell`, `python_exec`, and the new pty session — verified by test), tool-level + agent-level output caps, tool-level + agent-level timeout caps, tool-level + agent-level command/path denylists, cwd scoping. Add an interactive shell session tool with isolated sessions per agent built on Unix `pty` (stdlib) behind a `PtySession` protocol; Windows `ConPTY` implementation is **explicitly deferred** to a future mission to avoid pulling in `pywinpty`/`winpty` dependencies. Tests cover happy path, every constraint, subprocess-env invariant, and session isolation. May split if interactive sessions grow beyond a single leg's worth of work.

- [ ] Flight 5: **Web Expansion & Constraints** — Add `fetch_url` (readability/markdown extraction), `download_file` (writes through the FS path scope). Add response-size cap, redirect cap (default 5, tool-level only), URL/host allowlist + denylist (tool-level + agent-level narrowing). Search-backend test button. Tests cover happy path, SSRF blocks (including DNS-rebinding case), cap behavior, redirect limits.
