## Orchestrator Notes

**The deeper finding (two independent agents concur).** gemma3:4b is a non-tool model
(`supports_tools=False`) that **improvises a fresh, syntactically-plausible-but-unspecified tool-call
serialization on essentially every turn** — Python-call (`shell("…")`) on the leg-05 run, JSON-array
(`[{"tool_name","query"}]`) here, plus bare `search_tools` and pseudo-Python on retries of the *same*
prompt. Recognizer-based recovery is therefore **whack-a-mole**: each fix adds one recognizer; each run
can surface a new shape. The leg-07 fix correctly closed the two shapes the leg-05 run exhibited; this
run exhibits a third/fourth. Adding the array shape + `tool_name`/`query` aliasing would pass *this*
spec but would not establish *reliability* — it just moves the boundary.

**`search_tools` discovery protocol** is a confound, not the root cause: the agent's system prompt
restricts the model to `search_tools`/`continue` until discovery runs, which visibly steers gemma to
emit `search_tools` calls (themselves in unrecognized formats). But every attempt failed at the same
recognizer layer regardless — and recovered calls dispatch against the *full* registry (`core.py:334`
`self.tools.get`), so the gate isn't a dispatch blocker. The protocol explains the model's confusion,
not the non-execution.

**Durable fixes are upstream of the recognizer** (Validator recommendations): constrain gemma's output
(grammar / JSON-schema-constrained decode via Ollama's structured-output), and/or do not advertise
tools to a `supports_tools=False` model, and/or front it with a small tool-capable model. Recovery is a
best-effort safety net, not a reliability guarantee for this model. **This challenges the flight's
recovery-only premise and the mission #105 criterion's "reliably executes tool calls" framing for
gemma — escalated to the operator for a strategic decision (do not keep patching recognizers).**
