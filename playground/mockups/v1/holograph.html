Sandbox semantics on Apple Silicon

• Researcher claude-opus-4.7 4,182 tokens · 14 turns started 14:38
Today · 14:38
F

I'm trying to get the MCP sandbox running on my M3 Pro under colima. The docker-compose sets cap_add: [SYS_ADMIN] and security_opt: [seccomp:unconfined]. Calling unshare -U inside the container still EPERMs.

Walk me through what the kernel is actually doing here.

R
Researcher· thinking 4.2s

Under colima, the actual kernel hosting your containers is the Lima VM's Linux kernel, not the macOS host. So when you ask for SYS_ADMIN + seccomp:unconfined, both grants reach the VM kernel correctly — those are not the issue.

The likely culprit is the Lima VM's kernel user-namespace policy. I'll check three things on your VM before we touch the container:

shell_session_start target=lima-default
$ limactl shell default cat /proc/sys/kernel/unprivileged_userns_clone 1
• ok0.31s56 bytes
shell_session_send session=#1
$ sysctl user.max_user_namespaces user.max_user_namespaces = 0
• ok0.08sfound the cause
R
Researcher

Found it. The Lima VM has user.max_user_namespaces = 0, which disables user-namespace creation entirely — SYS_ADMIN can't paper over that. Lima's default kernel config sets this; colima doesn't override it.

Two fixes, ordered by reversibility:

F

Give me the non-destructive one first.

R
Researcher

Edit the VM via limactl shell default sudo sysctl -w user.max_user_namespaces=15000. Persists only for the running VM — survives reboot only if you also append the line to /etc/sysctl.d/99-userns.conf.

Want me to fetch the Lima kernel-config docs to confirm this is still the recommended approach for v0.20+?
