2. `studio.js::startKnowledgePoll` (the L1-D2 poll) fetches **only `/status`**

The first clause says *status*; the second defines the observable as *a file

## FINDING 3 (from checkpoint 5) — apparatus boundary defeats "without operator action" claims

**Severity: methodology / spec. Not a product defect.**

The Executor's apparatus runs **each step as a separate Python process**, so the
browser page does not survive a step boundary; only the session cookie does, via
`storage_state`. Every step therefore begins with a **fresh mount**.

That is fatal to any Expected Result of the form "X happens **without operator
action**", because a fresh mount *is* the action. Step 5 demonstrates it exactly:
the items were already populated at t=2.3s, at mount, so the 81.6-second wait had
nothing left to prove. The Executor reported this itself rather than banking the
clean-looking result, and correctly declined to run a state-mutating experiment
on its own initiative.

**Affected steps in this spec**: 5 and, more importantly, **8** — which carries
the mission criterion *"additions, modifications, and deletions are reflected
without operator action or an app restart"*.

**Orchestrator decision for step 8**: it must be driven as **one continuous
script in a single process** — mount the detail view, then modify the fixture
files on disk, then wait the full window, then observe — with no process
boundary between the mount and the observation. Step 8 already mandates the file
changes, so this needs no extra state mutation and no throwaway knowledge base.
This is the only way the mission criterion is actually exercised rather than
assumed.

**Why step 5 is not re-run the same way**: closing its gap would need a fresh
*registration* event inside one process, which means either a throwaway second
knowledge base or an unregister/re-register — both mutating state that steps
14-18 depend on. The defect is already established twice over (step 3's direct
observation plus the source trace), so a third line of evidence is not worth the
state risk. Recorded as unexercised rather than manufactured.

**Carried to the debrief**: a spec asserting "without operator action" should say
which process/page continuity the claim requires, because an apparatus that
re-mounts per step will pass it vacuously. This is an authoring-guide point, not
a fault of this spec's author or this run's Executor.

## FINDING 1 — UPGRADED after checkpoint 8: root cause is the Flight Director's cache declaration

Checkpoint 8 **FAILED**, and it is the headline result of the run. Direct
observation now replaces the step-3 inference:

- One continuous process. Mount predates the disk change. 19 passive samples
  over 94.7 s, no click, no reload, no navigation.
- Backend correct: `policy.md` indexed **~1.85 s** after the write; `meeting.txt`
  re-indexed; the two untouched files kept their original timestamps.
- **Watcher genuinely fired** — 1.85 s against a pinned 15 s interval, so a
  walk-carried pass is ruled out by latency. `watch: watching`, `watch_error`
  null throughout. The pipeline is not at fault.
- **The items list never repainted.** Four rows at baseline, four at every
  sample. `policy.md` never appeared. `meeting.txt`'s row byte-identical.
- **The screen states two incompatible facts at once**: chips read `indexed: 4`
  and `Chunks: 4` while the list beneath shows three indexed files. Worse than a
  frozen page — the moving counters are exactly what would persuade an operator
  the view is current.

### Root cause — mine, and verified in the source comment

`knowledge-section.js:24-29` cites **L1-D2's Cache Declaration** as its reason:
"only status is fetched on an interval; items, chunks and source text are
fetched at the moment they are displayed." The Developer implemented my
specification exactly.

The error is a **category mistake in my own cache declaration**. Chunks and
source really are on-demand — fetched on a click, displayed on request. I
grouped the **items list** with them. But the items list is **displayed
continuously**, so "fetched at the moment it is displayed" collapses to "fetched
once at mount and never again". It belongs with *status*, not with chunks and
source. AC-13's wording then compounded it, saying "status" in one clause and
"a file becomes visible" in the next.

Two design-review cycles read AC-13 as a single claim. So did I.

### Remediation — a design decision, so leg work, not a squawk

Three options were on the table; recording why (b) wins:

- **(a) Poll `/items` too.** Simplest, and wrong for the reason L1-D2 excluded
  it: rebuilding the list every 5 s would destroy an open chunks/source panel
  and any scroll position.
- **(b) Let the status poll invalidate the items list when the counts change.**
  ✅ The poll already carries a cheap change signal — per-status counts plus the
  chunk count. When those differ from what the list was last rendered against,
  re-fetch `/items`. Preserves L1-D2's actual intent (do not rebuild on every
  tick) while eliminating the contradictory screen, and re-renders only when
  something really changed. Must preserve an open chunks/source panel across the
  re-render, which is the one piece of care it needs.
- **(c) Render a staleness cue plus a refresh affordance.** Weakest: tells the
  operator the screen is wrong instead of making it right.

Also fix in the same pass: `onFolderRegistered` is a dead callback — wire it, or
delete it and let (b) cover registration too, since a registration changes the
counts.

And re-word **AC-13** so its two halves name one surface.

## FINDING 7 (from checkpoint 11) — an attached row loses its tool name after an in-session save

**Severity: real, user-facing, display-only. Inside this flight's own code.**

**unattached placeholder** "attach to see the tool name" in place of its derived

again, and every `GET` carries `kb_tool_names` throughout, so **no data is lost**.

It is the mirror image of FINDING 1: there, stale chips looked live; here, live
data renders as a stale placeholder.

**Mechanism, traced rather than guessed.** `knowledge-tab.js:108` reads
`agent.kb_tool_names`, and its own comment at :148 names the failure mode — the
placeholder branch is reached for "an attached one the server didn't resolve
(**stale `kb_tool_names`**)". `PUT /api/agents/{name}` *does* return the field
(`return _agent_response(cfg, await _resolve_kb_tool_names(cfg))`), so the server
is not at fault. The post-save path refreshes through `loadAll()`, which fetches
`GET /api/agents` — **the list route, which by my own L2-D5 decision deliberately
omits `kb_tool_names`** to avoid an N+1 read. The re-render therefore runs off an
object that structurally cannot carry the field.

**So this is a second-order consequence of L2-D5**, which I wrote and justified on
cost grounds without tracing which render paths consume list objects. The
decision itself is still right — an N+1 on every page load to serve a field the
tile grid never uses would be worse. The gap is that nothing made the *editor*
re-read from the single-agent route after a save.

**Fix options** (for the same pass as FINDING 1): have the post-save path
re-select through the single-agent fetch that L3-D3 already added to `doSelect`,
or merge the PUT's own response — which already carries the field — into the
cached agent instead of discarding it in favour of the list object.

**Immediate consequence for this run**: steps 12 and 14 both require reading the
derived tool name **off the row**. Read immediately after a save, that reads the
placeholder, and step 14's assertion — comparing the displayed name against the
`disabled_tools` entry — would be meaningless. The Executor spotted this itself
and proposed reading from a freshly loaded page, stating which render each
reading came from. **Approved**; it is the correct call and preserves the
"read, never compute" rule that DD-3 exists to enforce.

## FINDING 8 (from checkpoint 15) — Studio saves overwrite from a stale cached snapshot

**Severity: real, pre-existing, affects every agent save. NOT a squawk — fails the
qualification gate on both design and blast radius.**

**Reproduced from the wire, twice, with a control that settled the framing.**

**B2 (Executor-initiated, after identifying that the Orchestrator's Part B could
not test what it claimed):** re-add a `disabled_tools` entry → open the editor so
it caches an object containing it → remove the entry **out-of-band** via the API
with the page still open and never reloaded → save an unrelated description
change. **The browser sent the removed entry back**, and the un-disable was
silently undone.

**CONTROL (Orchestrator-authorised, to settle the framing rather than guess):**
same sequence but changing **`max_iterations`** out-of-band instead — server held
`3`, the browser's payload carried `1`, and the GET afterwards read `1`.
**Clobbered.**

### What the control settles

- The correct framing is **"Studio saves overwrite from a cached object"** —
  ordinary last-write-wins on a stale editor snapshot.
- **DD-13's union is NOT at fault**, and **L3-D3's fresh-fetch is not the precise
  gap**. The union simply inherits whatever staleness the snapshot carries.
- The fix is scoped to **editor freshness** (re-fetch at save, or conflict
  detection), not to the union's source.

Without the control I would have "fixed" the union and left the real defect in
place, while believing a flight decision had failed.

### The refinement that matters for the fix

`max_iterations` was clobbered via a **rendered form control still displaying the
stale value**; `disabled_tools` was clobbered from the **cached object with no
control at all**. Two different carriers of the same staleness — so a fix that
only re-reads *form controls* would leave `disabled_tools` broken. Name this
explicitly in whatever vehicle takes it.

### Why it matters despite being generic

Every other field's clobber is **visible**: the operator can see `max_iterations`
revert. A `kb__` entry in `disabled_tools` is rendered by **no control anywhere**
in Studio — and since the API is the **only** un-disable path, the stale-tab
sequence is the *realistic* operator flow, not a contrived race. Generic
mechanism, uniquely invisible consequence.

### Disposition

Qualified against the squawk gate out loud: one coherent item ✅; verifiable ✅;
**no design decisions ❌** (the fix requires choosing between re-fetch-at-save,
optimistic concurrency with a version/ETag, or last-write-wins with a warning);
**bounded blast radius ❌** (every agent save, every field, all of Studio).

Fails two criteria → **not a squawk**. Raise to the operator as possible flight
work, alongside the `app.js::replaceSub` router anomaly. Pre-existing; this
flight did not introduce it, but this flight is what made it *observable* — by
adding a field the UI renders nowhere.

**Steps to re-author.**
- **9 and 10 are mutually unsatisfiable — reorder, do not reword.** Move the
  restart-resume step to the **end**: it is the most destructive and the only one
  whose side effects invalidate an earlier precondition.
- **5, 8 and 10 share the spec's most serious structural flaw** — each asserts
  state arriving *without operator action*, and each passes vacuously if the
  observer mounts fresh. The failing wording ("reopen the tab", "wait", "do not
  reload") describes **operator** behaviour and constrains the **apparatus** not at
  all. Re-author each as an explicit session-continuity requirement: *within a
  single uninterrupted page session, with no reload, re-navigation or re-mount
  between the trigger and the observation.* **Step 8 is the proof this works — it
  is the one that was mandated that way, and the only one of the three that found
  anything.**
- **6's ordering clause is unfalsifiable against the mandated fixture.** Fix the
  Preconditions, not the step: require one file comfortably exceeding the chunk
  size (3-4 KB) so it yields at least three chunks.
- **2 buries an action in the Expected Results column** — a verifier reading only
  that column to check assertions would perform a state mutation while doing so.
- **12 must say from which render** the tool name is read; the post-save
  placeholder was discovered only because step 11 happened to expose it.
- **4's safety warning is the template every destructive step deserves**: it names
  the wrong thing to do, says what would happen, and explains why the
  deterministic case was chosen. Step 17's delete-the-right-one hazard had to be
  supplied mid-run instead.

**The apparatus lesson.** The failure mode is *a spec that constrains the
operator's behaviour but not the observer's instrument*. "Do not reload" tells a
human what not to click; it says nothing to an executor whose every step is a
fresh process — and that executor will satisfy the letter while destroying the
thing being measured, then report a clean pass **in good faith**. Nothing looks
wrong. That is what makes it dangerous. Proposals:
- **Declare the observation frame per step as a first-class field**, beside the
  existing `Cache:` line — `Session: continuous-from-trigger` vs
  `fresh-mount-permitted`. Default to continuous whenever an Expected Result
  contains "without operator action", "without restarting", "still", "unchanged"
  or "do not reload".
- **Require the executor to state which frame it actually achieved**, every time.
  Not "did you comply" but "what did you do".
- **Add an apparatus-capability precondition**, so a spec depending on session
  continuity fails at READY rather than at step 8.
- **Treat "the instructed procedure cannot detect the named defect" as a
  reportable finding, not executor discretion.** It arose three times; twice the
  instructed procedure was structurally blind.

> **The generalisation: a negative assertion is only as strong as the observer's
> ability to have seen the positive.**

**Patterns across the run.** The surface is stale in one *specific* place, not
uniformly — narrowing that was only possible because the negative cases were
tested as deliberately as the positive ones. Invisibility is the amplifier, not
the mechanism. Two fields, two opposite correct strategies, one request.
Falsifying the *specific alternative* is what turned step 17 from a weak negative
into a real one.

**On its own performance**: one substantive error at step 10, comparing against a
remembered READY value rather than its own stored `before` capture. Rule adopted:
**diff against stored evidence, never against recollection** — worth putting in
the methodology, because "I remember reading X" is indistinguishable from an
observation at the point of writing a report. Two habits to keep: flush evidence
to disk as produced (two scripts died mid-run; only incrementally-written files
survived), and snapshot durable state **between** a destructive action and any
recovery step — the database copy between kill and restart is the single
observation that kept both step 9 and its variant honest.

### Validator closing

**19 verdicts, 18 pass, 1 fail. No inconclusives** — every step produced evidence
sufficient to judge, which is worth recording in itself: the apparatus never lost
an observation.

**The result in one line**: the knowledge-base machinery underneath the screen is
sound — watcher, indexer, crash recovery and the whole derived-tool-name design
held under direct attack. What fails is the **screen's freshness**.

All three properties the spec was written to defend held. Squawk 0050's `kb_ids`
wipe did not reproduce. DD-13's `disabled_tools` erasure did not reproduce, and
the wire capture proved the **mechanism** rather than the outcome. DD-17 is the
most solidly established property of the run — established entirely from
observable behaviour **without ever reading the derivation code**, as the spec
instructed.

**Spec-quality feedback.** Four of the seven READY concerns were one defect in
different clothes: *an Expected Result that a correct system passes and a broken
system also passes.* The Intent says these steps exist "because a specific defect
was found" — but a step only tests that defect if the fixture, timing and
apparatus can produce the state where it would show. Two general rules follow:

> **Every negative or timing assertion should name the observation that would
> falsify it.** Step 17 is the model. Written that way, the vacuity in steps 5, 6,
> 7 and 9 would have been visible at authoring time rather than run time.

> **A spec should state its initial condition, not just its action.** Steps 3, 5
> and 8 assert the same underlying behaviour, but only step 8 found the defect —
> because only step 8 ran in one process with the page mounted *before* the
> change. That was the Orchestrator's mandate, not the spec's text.

**The pattern of failure.** Four instances of knowledge-base state having no
faithful on-screen representation — and **three are decided behaviour, not bugs**,
which is what makes the aggregate worse than any part. Together they mean *the
operator's screen and the agent's actual configuration can disagree with nothing
on screen to indicate it.* Severity tracks visibility: every other affected field
has a form control, so its stale value is at least on screen.

**Crucially the surface is NOT uniformly stale** — step 14 proved the rename path
is fine on the in-session route, a genuine negative finding because the Executor
looked where the defect would have appeared. That narrows the diagnosis to the
post-save refresh path specifically, which is far more actionable than "the UI
caches badly".

**Filing note, adopted verbatim**: B2 must **not** be logged against DD-13 or the
knowledge-base work. It is an agent-editor save-path defect. *"Filing it under
DD-13 would send someone to change union logic that is working correctly."*

**On the evidence rules** (appended at spawn because this project's crew file
omits them): all three earned their place, and one was decisive.
- **Frame-aware `[mixed-frame]` judgment is the reason step 8 is a fail.** Both
  halves were present and disagreed. Without the rule that the user-facing
  observable is primary, a defensible reading was "the system works, the UI lags"
  — a pass.
- **Rendered-state precedence** mattered quietly but constantly; step 11's
  placeholder defect is visible *only* at the rendered level — DOM and API were
  both fine.
- **Evidence-for-pass** changed behaviour rather than verdicts: it forced opening
  every screenshot and re-parsing every JSON, which is how a dict-vs-list error
  and the 801-vs-800 count reconciliation were caught.

**Three additions proposed**, in priority order: a **falsification clause** for
negative assertions; an **initial-condition declaration** in the Executor's report
(three passes depended on a hard reload, which is materially weaker than
"correct"); and a routine **"mechanism vs. outcome" prompt** — *"what observation
distinguishes the two ways this could have passed?"* — since the step-13 wire
capture was the single best methodological decision of the run and should not
have depended on inspiration.

**On verifying the Orchestrator**: *"The value isn't in catching anyone — it's
that a verified correction and an asserted one are different objects in the run
log, and only the first survives someone re-reading it in six months."*
Corrections ran in both directions all run, and none of it was friction.

**Safety, final**: port 8484 and the operator's default data directory were
**never touched at any point in this run.**
