## Findings

### Spec defect #15 (new; same family as #7–#11) — step 12 → 13 sequencing
Step 9 mandates page continuity; step 12 sets `disabled_tools` via the **only** available path (a direct
API `PUT`, since Out of Scope states no UI exists); step 13 then tests an unrelated save from that
now-structurally-stale page. Step 13 therefore conflates two questions — "does DD-13's union logic work"
(yes) and "does an out-of-band change survive if the operator's tab was open beforehand and never
reloads" (no) — and answers only the second, while its Expected Results read as testing the first.

This is an emergent collision between two individually-correct requirements, not a step-13 authoring
mistake.

**Fix**, either: (a) insert an explicit fresh-load beat between steps 12 and 13, mirroring what 13-bis,
14, 16 and 17 all already do; or (b) reframe step 13's Expected Results to name the staleness-tolerant
claim it actually tests. **Option (a)'s corrected sequence was executed during this run as 13-bis and
passed**, so the fix is already empirically verified.

### Product finding — squawk candidate: Studio agent-editor save is last-writer-wins
> Studio agent-editor save is last-writer-wins with no staleness detection; an out-of-band config change
> made while a tab is open can be silently discarded by that tab's next unrelated save.

No version check, no conflict warning, no "this agent changed since you opened it" signal. Fields the tab
does not actively manage revert to the snapshot loaded at open time.

Why it is not a shrug: (1) it is a plausible real operator sequence — an operator may run a
`disabled_tools` `PUT` by script *precisely because no UI exists for that field*, while the agent sits
open in a tab from earlier work; (2) it is inconsistent with staleness patterns this codebase already
applies elsewhere (`if_version`-gated Artifact DB writes; the self-configuration restore path's documented
fail-closed-against-staleness behaviour).

Distinct from, and narrower than, a DD-13 regression.

### Apparatus finding — untracked pages spawn during error recovery
An unattributed second page (`…/research-assistant/general`, marker `null`) was found in the shared CDP
context during checkpoint 9, adjacent to the run's single most load-bearing evidence. Found by the
Orchestrator's independent verification; independently re-enumerated by the Validator; established as
**not** the Validator's (it used a separately launched browser). Most likely debris from the Executor's
failed first attach attempt, when a Playwright timeout aborted a script mid-navigation and orphaned the
page it had just navigated to. It did not taint the evidence — every artifact came from the marked page —
and it was closed at checkpoint 11.

**"Exactly one page" is an invariant nobody enforces; it was discovered by accident.** Before this
apparatus is trusted unattended, either each script should explicitly close every page it did not select,
or a single long-lived process should own page lifecycle across steps instead of each step reconnecting
and hoping.

## Closing Summaries

### Executor closing
The CDP-connect-to-detached-Chromium pattern worked, but has one real gap for unattended use: nothing
enforces single-page discipline — the stray page was debris from its own aborted script, and on an
unattended run nobody would have caught it until someone happened to inspect page count. Wants either
per-script cleanup of unselected pages, or one long-lived process owning page lifecycle.

The marker worked exactly as designed for falsifying continuity — cheap, reliable, destroyed by any real
reload. Its one weakness is silence: a lost marker looks identical to "page closed" or "wrong page
selected," so a supplementary page inventory was always needed to tell those apart. Once reloads became
legitimate, `performance.getEntriesByType('navigation')[0].type` was the better signal — browser-engine
ground truth, not fakeable by page script — and the spec should bake it in from the start rather than
leaving it to be improvised mid-run.

Hardest to perform faithfully: **step 6's ordering clause**. "Do not infer from code" made reading the JS
tempting-but-disallowed as evidence, forcing construction of a real network-intercept probe. A meaningfully
higher bar than most rows, which the spec does not flag — *an executor who simply read the source and
reported "it sorts" would have satisfied the letter of the row while violating its spirit.*

Step 9's custom toggle (checkbox visually hidden behind a `.tool-switch` sibling) broke a naive click and
cost one clean attempt, producing a recoverable exception inside a genuinely irreplaceable span. Step 10's
race was mechanically demanding but well-specified enough to win first try. Instance identity verification
via `/proc/<pid>/environ` before the stop and after the start was cheap insurance that paid for itself.

### Validator closing
The spec is close to `active`-ready: 17/18 on genuinely falsifiable evidence, and the one non-pass resolved
into a named, fixable sequencing gap rather than a system defect — a good outcome for a fifth re-authoring,
with the remaining issue narrow and well-understood rather than another open-ended rewrite.

Clauses that earned their place: step 9's continuity span (genuinely testable, and it caught real apparatus
debris); the 12/14/16/17 `disabled_tools` chain (each individually weak, but strong as a sequence —
especially 16's collision test, which a naive name-keyed implementation would have failed); and step 8's
rewritten three-part test, which is designed correctly now and would not have passed under the old
equality assertion.

Before `active`: fix the 12→13 sequencing gap directly, and capture the last-writer-wins finding as a
squawk candidate separate from the spec fix.

On process: independently re-deriving evidence caught nothing wrong this run, but the stray-page anomaly
showed its value — self-report alone would have left that unexplained.
