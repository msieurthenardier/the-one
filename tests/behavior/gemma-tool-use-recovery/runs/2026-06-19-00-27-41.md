## Orchestrator Notes

**Root cause — two independent, compounding real-world mismatches between the flight's fixture and live gemma3:4b** (both reproduced directly against the kernel + the dispatch path, not just inferred):

1. **Fence tag `tool_code` is unrecognized.** `the_one/llm/_toolcall_recovery.py:60`
   `_FENCE_TAGS_TO_PARSE = {"", "tool", "python", "py"}` — `tool_code` is **not** in the set.
   `recover_tool_calls("```tool_code\nshell(...)\n```")` returns `[]`; a control `` ```tool `` fence
   with the identical body recovers correctly. So recovery never fires for real gemma output.
   (`tool_code` is Gemma/Gemini's documented fenced-tool-call convention.)
2. **Positional call syntax is not bound to the tool's named parameter.** Real gemma emits
   `shell("echo …")` (positional), which the kernel parks under
   `arguments["__positional_args__"] = [...]` (a recorded leg-01 known limitation). Dispatch at
   `the_one/agent/core.py:334-335` does `self.tools.get("shell")` (full registry — the `search_tools`
   discovery gate is **not** a dispatch blocker, confirmed) then `tool.execute(**arguments)` →
   `ShellTool.execute(__positional_args__=[...])`, but `ShellTool` requires a named `command=` arg.
   So **even if `tool_code` were recognized**, the recovered call would error on argument binding and
   still write no canary. Nothing downstream maps `__positional_args__` → named params (`grep`
   confirms the sentinel is referenced only in `ollama_provider.py`, passed through verbatim).

**Why the flight's earlier tests went green but this failed**: the captured Flight-1 fixture and the
leg-04 live test both used the ` ```tool ` fence with a **keyword**-arg call (`get_weather(city='Paris')`).
The leg-04 live test additionally *forced* the ` ```tool ` label via a directive system prompt. Real
gemma3:4b in the natural agent flow uses ` ```tool_code ` + positional args — unrepresentative of the
fixture on **both** axes. The hermetic units and the directed live test could not catch this; the
end-to-end behavior test did. This is the behavior test working as intended.

**Scope implication**: fix (1) is a one-line kernel change inside `the_one/llm/` (in mission scope).
Fix (2) needs schema-aware positional→named mapping; the kernel is deliberately schema-less (DD1), so
the mapping must happen where a tool schema is available — the provider (no schema on the degraded
wire) or the agent dispatcher (`_execute_tool`), the latter touching `the_one/agent/core.py`, which the
mission scopes as "agent loop untouched." **This tension is an operator decision** — recorded in the
flight log; the leg does not land while the behavior test fails.
