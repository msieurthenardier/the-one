**Notes**:
- **`_require_agent_name` lives at module scope, NOT as a `Tool` method**: every session tool calls `_require_agent_name(self)` at the top of its `execute` to reject the introspection path (`agent_name=None`). The helper is a free function (not a method on `Tool` or a mixin) because the `Tool` ABC is a F2/F3 contract that should not grow F4-specific affordances — `agent_name`-required semantics are session-tool-specific, not a general tool concern. Free function in `the_one/tools/sessions.py` keeps the cross-cutting concern local to the four tools that need it. Returns the name on success; raises `ConstraintError` on `None` so the surrounding `try/except ConstraintError` envelope produces the documented `[error] [constraint] session tools require an agent context` text.
- **`agent_name=None` rejection happens INSIDE the try/except, not before**: every session tool wraps `_require_agent_name(self)` in the same `try` block as the rest of the work so the `ConstraintError` it raises flows through the same envelope as cwd refusals, denylist trips, and ownership refusals. Putting the check OUTSIDE the try would require duplicating the `[error] [constraint] ...` formatting at every call site — DRY-violating, and the leg-spec wording is exact.
- **`create_pty_session(cwd=canonical_cwd)` passes `Path`, NOT `str`**: L5a's signature is `create_pty_session(cwd: Path | None, shell: str | None)`. `_cwd_check` returns a canonical `Path` directly. The tool MUST NOT `str(canonical_cwd)`-coerce — the leg-spec call-out is explicit. (The L4 PythonExecTool DOES `str(Path.home())` at the call site because `_cwd_check`'s OLD signature accepted `str`; L4 stays as-is for now since its `run_python` consumer takes `str | Path`.)
- **`max_concurrent_sessions` race ACCEPTED for F4**: the `(count_for_agent, register)` sequence is NOT atomic under one lock acquisition. Concurrent `start` calls from a single agent (asyncio.gather) could each see `count < max` and all proceed past the cap. Decided acceptable for F4 because small-model agents in M05 do NOT pipeline tool calls — they emit one tool call per turn, await response, then emit the next. The cap is therefore a soft limit (operator-set guideline). For F6+ if/when an HTTP API exposes parallel agent invocations, the registry can grow a `register_if_under_cap()` helper that does count+insert under one lock acquisition. Documented in the leg-spec edge-cases section; pinned here as the F4 design decision.
- **`_truncate_output(output, b"", 0, exec_cfg)` for PTY**: deliberately passes `b""` for stderr because PTY merges stderr into stdout via the master fd — the `output` bytes already contain everything the agent should see. Passing non-empty stderr would inject the `\n[stderr]\n` marker into the agent's view of normal interleaved shell output — confusing. `returncode=0` is a fixed sentinel; the PTY layer doesn't surface a per-command return code (the agent observes shell errors via the output text itself, e.g. `bash: foo: command not found`). The `(output, b"", 0)` shape produces clean text + truncation marker on oversize, no `[stderr]` block, no `[exit code: N]` suffix.
- **`Send timed out after Ns` wording**: deliberately distinct from one-shot Shell's `Command timed out after Ns` and Python's `Timed out after Ns`. Three different surfaces, three different message prefixes — the agent should be able to tell which tool produced the error from the message alone. F2 / F4 tests pin Shell's wording; L6's `test_send_timeout_emits_send_timed_out_message` pins Send's. (`Send timed out after 5s` was chosen because it reads naturally for an interactive-session surface — the agent "sent" something and the response timed out.)
- **`Requires = (FilesystemConfig,)` on Send** — declarative, NOT consulted: Send's body does not call `_cwd_check` or read `fs_cfg` directly. The declaration exists so the L1b cross-Config dispatch view stays uniform across the execution family (Shell + python_exec + start + send all declare it; close + list don't because they're session-id-only operations). Future flights may use `Requires` for static analysis (e.g. "which tools are affected by a `FilesystemConfig` change") — keeping the declaration set inclusive avoids retrofitting later.
- **`MockPtySession` promotion**: cross-test-module imports (`from tests.test_session_registry import MockPtySession`) are fragile under pytest's collection ordering — when `test_session_tools.py` collects before `test_session_registry.py`, the import can fire before pytest-imports the source module, and Python's module cache may not have it. Promoting to `tests/_pty_fixtures.py` (underscore-prefixed so pytest doesn't collect it as a test module) is the canonical fix. The promoted mock also gained two test affordances over the L5b version: `self.sent: list[tuple[str, float]]` records every `(input, timeout)` pair the tool layer sends, and `self.send_response: bytes` lets a test inject canned output without subclassing. L5b's tests don't exercise these new fields — they continue to pass unchanged.
- **Pre-existing CSS-token failure**: `tests/test_token_definitions.py::test_every_var_reference_is_defined` flags `--font-size-h3` as an undefined CSS custom property referenced in `components.css`. **Notes**:
- **Lock-and-await deadlock avoidance is the central design constraint**: `close()`, `_reap_once()`, AND the cancel-handler drain in `_reap_loop()` all follow the snapshot-under-lock / close-after-release pattern. Holding `_lock` across `await session.close()` (which includes the ~1s SIGTERM→SIGKILL ladder via `loop.run_in_executor`) would block every other registry operation for that window. Snapshot+pop under lock, release lock, then iterate the snapshot is the only safe sequencing. Pinned implicitly by `test_reaper_continues_when_one_close_raises` (a deadlocked impl would never reach the second close).
- **`_RegistryEntry.agent_name` deliberately omitted**: the dict key already carries `(agent_name, session_id)`. Storing `agent_name` again on the entry creates a drift risk if the two ever fell out of sync (e.g. someone later writes a "rebind to a different agent" helper that updates the key but forgets the entry field, or vice versa). The dataclass holds only `(session, ttl_seconds)`. Documented in the dataclass docstring.
- **`MockPtySession` MUST use `@property` accessors, NOT class-level attributes**: `PtySession` declares `is_alive` and `last_activity` as `@property @abstractmethod`. Class-level attribute defaults do NOT satisfy abstract property descriptors — `MockPtySession()` would raise `TypeError` at instantiation. First implementation attempted `is_alive = True` as a class attribute and tripped on import; revised to instance vars `_alive` / `_last_activity` plus `@property` accessors. The leg-spec call-out for this anti-pattern is honored. (The leg's verification-snippet MockSession was acceptable because Python checks abstract methods at instantiation, not at class creation; that snippet uses class attributes only because it never inspects the resulting object as a `PtySession`.)
- **`_clear_for_test` MUST reset BOTH `_reaper_task = None` AND `_shutting_down = False`**: without resetting `_shutting_down`, any test that runs AFTER `test_register_after_shutdown_drain_raises` would inherit the True flag and every subsequent `register()` call in the suite would raise `RuntimeError`. Same for `_reaper_task` — leaving a torn-down event-loop-bound task in place breaks the next test's `_ensure_reaper_running_locked` (the `not done()` check would skip the spawn even though the task is pinned to a defunct loop).
- **`shutdown_drain` uses `contextlib.suppress(asyncio.CancelledError)`** when awaiting the cancelled reaper task, NOT a bare `try/except CancelledError`. Two reasons: (a) `contextlib.suppress` is the idiomatic single-line shape for "swallow this specific exception"; (b) bare `try/except CancelledError` outside an async-loop body can shadow legitimate cancellations of the awaiter itself in some corner cases. The reap-loop's own `CancelledError` handler runs the registry drain BEFORE the task actually finishes; we just need the awaiter to wait for that drain without re-raising the cancel out to the lifespan teardown.
- **`register()` after `shutdown_drain()` raises `RuntimeError`** (per leg AC) — fails loudly rather than silently orphaning a session that the reaper will never visit. The acceptable alternative ("accept and orphan; sessions die with the process anyway") was rejected because the orphan window could span a few seconds during graceful shutdown, during which a request could create a session that holds a real subprocess open through the kernel's grace period and into SIGKILL territory. Loud failure surfaces the race to the request handler, which can return a 503 cleanly.
- **`_reap_once()` is the deterministic test surface, NOT `_reap_loop`**: the leg spec called for one sleep-based integration test (`test_reaper_loop_actually_runs`) and otherwise prefer direct calls to `_reap_once`. The remaining 5 reaper tests drive `_reap_once` directly with explicit `last_activity` values — zero sleep, zero flakiness.
- **`_reap_loop` swallows non-cancel exceptions inside `_reap_once`**: defensive — an unexpected error must not kill the loop (otherwise a transient issue would orphan all subsequent sessions until `shutdown_drain`). Logged at exception level so the issue is visible. The next tick retries. `_ensure_reaper_running_locked` additionally checks `_reaper_task.done()` so that if the loop somehow does die outside the cancel path, the next `register()` respawns it.
- **Belt-and-suspenders drain in `shutdown_drain`**: even if `_reaper_task is None` (the reaper was never spawned because no sessions ever registered), `shutdown_drain` still snapshots `_sessions` under the lock and closes anything left. Covers the corner case where someone calls `register()` and immediately `shutdown_drain()` faster than the reaper can spawn — though the lock serialization makes this near-impossible in practice. Pinned by `test_shutdown_drain_with_no_sessions_is_noop`.
- **FastAPI lifespan `try/except Exception`, NOT `BaseException`**: `CancelledError` is a `BaseException` subclass since Python 3.8. Using `except BaseException` in the lifespan teardown would swallow the cancel that FastAPI uses to tear down the lifespan context, leaving the application in an inconsistent state. `Exception` catches misbehaving session-close errors while letting the cancel propagate cleanly. The pattern was called out explicitly in the leg notes.
- **Lifespan test data-dir isolation requires monkeypatching `settings.data_dir` directly, NOT `setenv`**: `Settings` reads env vars at module-import time (the `BaseSettings` instance is created once at `from the_one.config import settings`). `monkeypatch.setenv("THE_ONE_DATA_DIR", ...)` after import does nothing. It also resets `the_one.db.connection._connection = None` so the singleton from prior tests doesn't leak — without this, the lifespan's `get_connection()` returns a stale aiosqlite connection bound to a previous tmp_path (or a previous event loop), and `init_db` quietly applies schema to the wrong DB.

The leg-spec call-out for this kwarg is honored. `select_shell()[0]` is the production default when `shell=None`.
- **Idle-mark vs. terminal echo interaction (already covered above)**: production agents will see the echoed input bytes in the response — this is accepted noise; agents tolerate it. The session-tool layer (L6) decides whether to strip echo via the existing `_truncate_output` helper or pass raw bytes through. L5a is the primitive; no policy.
- **`is_alive` property handles three transition states**: (1) `_closed=True` → False. (2) `_pid=None` (close already nulled it) → False. (3) `os.waitpid(pid, WNOHANG)` raises `ChildProcessError` (kernel removed the entry between calls) → set `_closed=True`, return False. (4) `done == 0` → True (child still running). (5) `done == pid` → set `_closed=True`, return False. The `ChildProcessError` path is exercised by `test_is_alive_handles_child_process_error` (manually reaps the child to force the kernel-entry-removed state).
- **`_read_until_idle_blocking` returns partial output on EOF**: zero-byte read from `os.read(master_fd, ...)` indicates EOF (the slave side closed). We return the accumulated buffer rather than raising. This is the "shell exited cleanly" path — `is_alive` will return False on the next check, and the caller's `send` returns whatever the shell printed before exit (including `exit`'s echo).
- **Default executor saturation risk (documented in leg spec)**: each `send` ties up a thread in the default `ThreadPoolExecutor` for the duration of the blocking I/O. Acceptable for F4 — execution tools are not high-concurrency. L5b's reaper will not call `send`; only `close` (also via executor, but only at idle-TTL expiry). No mitigation in L5a.
- **Test isolation via `try/finally: await s.close()`**: every test that calls `await s.start()` wraps the body in `try/finally: await s.close()` so a test failure mid-body doesn't leak a zombie PTY child between tests. The `test_close_kills_subprocess` test additionally calls `os.kill(pid, 0)` post-close to verify the child is actually gone (not just unreachable from this test's perspective).
- **L2/L3/L4 backward-compat verified by re-export identity smoke test in the verification snippet**: `from the_one.tools.execution import _ENV_ALLOWLIST as A, _build_subprocess_env as B; from the_one.platform.env import _ENV_ALLOWLIST as C, _build_subprocess_env as D; assert A is C and B is D`. If a future refactor accidentally rebinds the name in `tools/execution.py`, the identity check trips before any test downstream can hit the re-export divergence.

## Anomalies

### Chat WebSocket blocks during long tool calls (post-flight fix)

**Observed (post-flight)**: operator noticed during HAT scenario 1 that switching conversations in the UI did nothing while the `sleep 200` tool call was running; the UI became responsive only once the 120s clip fired and the tool returned.

**Severity**: degraded UX (long-standing); actionable.

**Root cause**: `the_one/interfaces/web/app.py:780` (pre-fix) did `await _process_and_broadcast(...)` synchronously inside the WebSocket receive loop. While the agent's tool call ran, the loop could not call `await ws.receive_text()` again, so any subsequent action over the same WebSocket (`join`, `list_sessions`, `new_session`) queued in the kernel buffer until the in-flight reply chain completed.

**Resolution (committed on F4 branch in two commits)**:

*Part 1 — unblock the receive loop:*
- New `_spawn_message_processing(...)` wrapper creates an `asyncio.Task` per submitted message; the receive loop is no longer blocked.
- New `Session.processing_lock` (lazy `asyncio.Lock`) serializes successive messages on the same session (avoids `agent.messages` race); a second message politely waits.
- Module-level `_inflight_tasks: set[asyncio.Task]` tracks live tasks; FastAPI's `lifespan` teardown cancels them.
- Errors inside the spawned task are caught and broadcast to the session's subscribers as a `system` event.
- HTTP `POST /api/chat` is unchanged — callers expect a synchronous result.

*Part 2 — preserve in-memory history across rejoin:*
After Part 1 shipped, the operator surfaced a follow-up bug: rejoining the still-running session via `join` returned an empty chat. Root cause: `_restore_session` (`the_one/interfaces/web/app.py:250`) always rebuilt the agent and replaced `existing.history = ui_events` from the DB, but the user's just-submitted message + in-flight assistant chunks weren't yet persisted. **Fix**: `_restore_session` short-circuits to the cached in-memory session when its `processing_lock` is held. The rebuild's purpose (rebind agent for config edits) is intentionally suspended for the duration of the in-flight turn; the next join after completion picks up config edits as before.

*Part 3 — per-session UI busy state:*
After Parts 1+2 shipped, the operator surfaced a third bug: starting a NEW conversation while a long tool call ran left the new chat's input disabled. Root cause: the chat UI's `busy` flag was module-scoped (per-WebSocket), not per-session — switching from a still-processing session A to a fresh session B inherited A's `busy = true`, so `send()` early-returned. **Fix (two-sided)**: (a) backend `_build_session_joined_ok` now includes `is_processing: bool` derived from `processing_lock.locked()`; (b) chat.js replaces the single `busy` flag with `inFlightSessions: Object.create(null)`, keyed by session id, and on every `session_joined` it syncs the current session's busy state from `data.is_processing`. Result: switching to a new chat correctly enables input; rejoining a still-running session correctly shows the spinner; rejoining a since-completed session correctly enables input.

**Verification**:
- `tests/test_ws_responsiveness.py` (NEW, 9 tests): lazy lock creation, second-message-waits, exception suppression, task self-discard, restore-skip-when-locked, restore-rebuilds-when-unlocked, is_processing reports false (lock unheld), is_processing reports false (lock None), is_processing reports true (lock held).
- Live smoke 1: with `sleep 200` (120s clipped) in flight, `list_sessions` over the same WebSocket replied in **0.02s**.
- Live smoke 2: rejoining the in-flight session via `join` returned `history` with the user message + tool_call event.
- Live smoke 3: full per-session flow — A starts un-busy → submits → B fresh un-busy → B completes in 0.75s while A still running → rejoin A correctly shows `is_processing=true` with intact history.
- Full unit suite: 834 passed (was 825; +9 net).

**Pre-existing condition** (predates F4 — `git log -L` traces `_process_and_broadcast` invocation back to `09bd91f`). F4 didn't introduce the bug; it just made it more visible because the new 120s timeout cap turned previously-unbounded sleeps into deterministic 2-minute UI hangs.

### Stale uvicorn imports across L3-L6 source changes

**Observed**: Scenario 1 of the L7 HAT initially showed `[error] Command timed out after 200s` instead of the expected `120s` — the timeout cap clip was not engaging through the chat API. Direct `python` invocations inside the same container correctly clipped to 120s.

**Severity**: degraded (HAT-blocking until resolved; no production impact since flight is uncommitted).

**Root cause**: the FastAPI/uvicorn process was launched at container start (before L3-L6 source changes existed) and Python caches imports for the lifetime of the process. The bind-mount makes new code visible to NEW Python invocations (e.g., `docker exec the-one python /app/_tmp_clip.py` saw post-L4 code) but does NOT affect modules already imported by the long-running uvicorn worker. The container was last restarted between L1b and L2 (when the `tests/` bind-mount was added); L3-L6 source changes never propagated.

**Resolution**: `docker compose restart the-one` reloaded all imports; HAT re-run with all 10 scenarios passing cleanly thereafter.

**Documentation impact (deferred to L8)**:
- Add a one-line note in `agents.md` and/or `CLAUDE.md`: "When iterating on tool source code mid-flight, restart the container (`docker compose restart the-one`) so uvicorn picks up new imports. The bind-mount alone is not sufficient for the long-running server process."
- Optional follow-up (out of F4 scope): consider adding `--reload` to uvicorn in the dev compose file, OR an `App.onChange` script that auto-restarts on `the_one/**/*.py` changes. Either would eliminate the manual-restart step for future flights.
