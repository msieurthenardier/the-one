# Squawk 0248: Saving a tool in Settings wipes its default denylist

**Status**: completed
**Type**: defect
**Severity**: grounding
**Reported**: 2026-10-23
**Completed**: 2026-10-23

## Report
Settings › Built-in tools shows the denylist of a never-saved Filesystem or Execution tool as **empty**, though built-in defaults are in force: 18 paths such as `~/.ssh` and `~/.aws` for `path_denylist`, and tokens such as `sudo ` for `command_denylist`. Any Save from that editor stores `[]`, which replaces the defaults, even a Save that changes only another field. The result is a silent loosening of a safety boundary.

**Reproduce** (on a scratch instance):
1. Open Settings › Built-in tools › `move_file`. The tool has no stored config (`{}`). Path Denylist shows no chips.
2. Tick "Allow Binary Files" and Save.
3. `GET /api/tools/configs/move_file` now returns `config.path_denylist == []`, and the tool runs with no default denied paths. Only the app's `secrets` directory is still appended (`FilesystemConfig.model_post_init`).

**A second defect with the same root cause** (found while implementing, folded in by the Flight Director's decision): the tool policy resolver read a `default_factory` field's baseline as `field_info.default` (`PydanticUndefined`), so an agent override of `path_denylist` or `command_denylist` on a never-saved tool raised `NotImplementedError` and the agent could not be built. The schema fix alone would have made that crash easier to hit.

Found in Mission 31 Flight 4's planning survey (presentation walk, `denylist_probe.py`). The operator asked for a hotfix on `main` (2026-10-23).

**Squawk qualification, stated:** one item, an obvious fix, verifiable. It **fails "bounded blast radius"** on one count: it touches a security-sensitive surface (the tool safety denylists). The operator directed an immediate hotfix, so it runs on the squawk path with a Reviewer briefed on the security surface. Any change beyond making the real defaults visible (for example, changing PUT replace semantics or refusing an empty denylist) is out of scope and escalates.

## Evidence
- `the_one/tools/filesystem.py` `FilesystemConfig.path_denylist`: `Field(default_factory=lambda: list(DEFAULT_PATH_DENYLIST))`. `the_one/tools/execution.py` `command_denylist`: the same pattern with `DEFAULT_COMMAND_DENYLIST`. Pydantic omits a `default` from `model_json_schema()` for a `default_factory` field: the schema for `path_denylist` is `{"items": {"type": "string"}, "title": "Path Denylist", "type": "array"}`.
- `the_one/tools/_web_config.py:214,226,239`: `default_factory=list` fields. An empty default, so the display is accurate. Check that the fix also handles them consistently.
- `the_one/interfaces/web/api.py` `get_tool_config` returns `cls.Config.model_json_schema()` (via `_enrich_schema_with_markers`) and the stored `config` (`{}` when unsaved).
- `the_one/interfaces/web/static/js/areas/admin/tools-editor.js:146`: `var saved = (fname in config) ? config[fname] : prop['default'];`, so the field renders empty and Save serialises `[]`.

## Corrective Action
**Change (server only, no client JS).** `_enrich_schema_with_markers` in `the_one/interfaces/web/api.py` (the one place `GET /api/tools/configs/{name}` builds its schema) now also sets `default` on every property whose field uses `default_factory` and has no schema `default`: it calls the factory through `field_info.get_default(call_default_factory=True, validated_data={})` and passes the value through `pydantic_core.to_jsonable_python`. It never instantiates `Config()`, because `FilesystemConfig.model_post_init` appends the app's secrets directory at runtime and that must not be stored as part of the default. Fields covered: `FilesystemConfig.path_denylist` (18 entries), `ExecutionConfig.command_denylist` and `PythonExecConfig.command_denylist` (20 entries), and `WebConfig.host_allowlist`/`host_denylist`/`extra_allowed_hosts` (`[]`, so their display does not change). After the change every property of every built-in tool's served schema has a `default`. The prompt text the model sees, the PUT replace semantics and `GET /api/tools/configs` (list) are unchanged.

**Client.** No change needed. `tools-editor.js:146` (`prop['default']` fallback) now gets the real list, `renderField` renders an `array` field as a chip list (an array is never a dropdown, so `command_denylist`'s `ui_hint: dropdown` is not used), and `readChipListValue` keeps trailing spaces (`"sudo "`), so a Save round-trips the defaults exactly.

**Agent editor Tools tab (`tools-tab.js:175`, `tool-override-fields.js`, `agent-form-data.js`).** Same root cause, and the server fix covers it: `operatorVal` falls back to `prop['default']` too. Before the fix, an agent's `path_denylist`/`command_denylist` override for a never-saved tool showed no locked operator chips, so the panel implied the agent could replace the denylist; with the fix the 18 (or 20) defaults show as locked chips and are part of the union that is sent. Measured with a throwaway probe test (deleted): after adding `/probe`, the stored override was `['/probe']` before the fix and the 18 defaults plus `/probe` after it. Untouched empty arrays are still skipped by `collectFormData`.

**Resolver (same root cause, Flight Director decision: lands here).** `the_one/tools/resolver.py` read the operator baseline as `merged.get(key, field_info.default)`. For a `default_factory` field with no stored operator config that is `PydanticUndefined`, so `_check_narrow_superset` raised `NotImplementedError("NarrowSuperset on non-list field ...")`. `BuiltinToolProvider.get_tools` and `AgentFactory.create` do not catch it, so the agent could not be built. It failed closed, and it predated this squawk (any agent that added a denylist entry for a never-saved tool hit it), but the schema fix made it easier to hit: opening a Filesystem or Execution Overrides panel now seeds the locked defaults, so any later agent Save stores a denylist override. The resolver now uses `merged[key]` when the key is stored, else `field_info.get_default(call_default_factory=True, validated_data={})`. It never instantiates the Config (same `model_post_init` secrets-dir reason). The superset check now compares against the real defaults: an override that drops a default entry (for example `~/.ssh` or `sudo `) is refused with `ValueError("agent override widens ...")`, so an agent still cannot loosen the default denylist. `tests/test_execution_config.py::TestResolverDefaultFactoryFallback` had pinned the old `NotImplementedError` as a documented limitation (Mission 5 Flight 4 leg 2: callers had to store the tool-level row first). Its first test is rewritten to expect the refusal, and a second test checks that an extending override resolves. The other test in that class is unchanged.

**Operator check (not repaired here).** A database whose Filesystem or Execution tools were saved from Settings before this fix may hold `path_denylist: []` or `command_denylist: []`, which still overrides the defaults. Check with `GET /api/tools/configs/{name}` for each of the nine filesystem tools (`read_file`, `write_file`, `edit_file`, `delete_file`, `move_file`, `mkdir`, `glob`, `grep`, `list_dir`), `shell` and `python_exec` (the execution tools share `ExecutionConfig`). Where the stored value is `[]`, PUT the config without that key (the built-in default then applies) or re-add the entries in Settings › Built-in tools.
