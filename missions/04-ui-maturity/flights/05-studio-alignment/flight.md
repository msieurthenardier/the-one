# Flight: Studio Alignment

**Status**: in-flight
**Mission**: [UI Maturity](../../mission.md)

## Contributing to Criteria

- [ ] Each functional area (Chat, Studio, Administration) reflects the established design language and meets a quality bar suitable for showing to external developers without apology *(F5 brings Studio to the bar — sidebar restructure, agent tile grid, tabbed agent editor, modern save/back/dirty UX)*
- [ ] Common interaction patterns (creating a new entity, editing, confirming destructive actions, displaying empty states) behave consistently across all areas *(F5 establishes the tab idiom across the codebase, extracts `App.confirmDelete` + `App.confirmDialog` so chat + studio + future admin share the same destructive-action and unsaved-changes patterns)*
- [ ] Critical user flows (start a new chat, create and configure an agent, add and verify a provider) progress without dead-ends, unexplained errors, or unclear next steps *(agent creation/editing/deletion flow gets reworked end-to-end; test button on the General tab reuses the existing provider-test endpoint to give immediate config-correctness feedback)*
- [ ] Navigation state (current area and active sub-view, including selected entity) is reflected in the URL and survives page refresh *(hash routing extends to `#studio/{section}[/{name}[/{tab}]]` — sub-section, selected agent, and active editor tab all survive refresh)*
- [ ] Automated browser tests cover the critical user flows and fail on regression, runnable both locally and in CI *(tile grid + tab navigation + dirty-state confirm dialog + section navigation get explicit browser tests; existing agent-CRUD tests adapt to the new selectors via `data-testid`)*

## Pre-Flight

### Objective

Bring the Studio area to the F4 design-language quality bar through a coordinated rework of three surfaces: (a) **left-bar restructure** — replace the current agents-only sidebar with a titled three-section navigation (Agents / Knowledge / Tools); the Knowledge and Tools sections are stub destinations for later missions but are real navigation targets today, with hash-routable URLs and one-liner empty states; (b) **agents page** — replace the flat `.agent-list` with a tile grid, add a top-right "+ New Agent" header button matching chat's `.btn-outlined-cyan new-chat-header` placement, fix the F4-diverted keydown-bubble bug on agent-item delete, and extract `App.confirmDelete(...)` (queued by F4 debrief) so chat + studio share one canonical implementation; (c) **agent editor** — establish the codebase's first tab idiom (W3C ARIA `role="tablist"` with manual activation), with three horizontal tabs (General / Knowledge / Tools), name + description as a stable header above the tablist, save/delete/back buttons positioned together at the top-right, dirty-state tracking that gates the save button and triggers an in-app `App.confirmDialog(...)` modal on back-with-unsaved-changes (plus a `beforeunload` listener for tab-close protection). The General tab carries the existing form (name, description, system prompt, LLM config, `max_iterations`) plus an Advanced section stubbed for a future flight (temperature / top_p / max_tokens) and a Test button that reuses the existing `POST /api/providers/{provider_id}/test` endpoint. The Knowledge tab is a one-liner stub for a future flight that will attach knowledge bases to agents. The Tools tab carries the existing tool-selection UI, visually grouped into "MCP tools" and "Built-in tools" subsections. No backend schema changes; no agent-model field additions in this flight (`llm_overrides` deferred to a future LLM flight). HAT closes the flight per F2/F3/F4 precedent.

**Continuation of the F4 design-system push**: F5 is the second flight in a row whose primary deliverable is bringing an area onto the unified design system. F4 split `chat.js` into `App.chat.{...}` helpers + lifted shared CSS into `components.css` (`.list-item`, `.btn-*-cyan`, `.field-*`, `.chip`, `.empty-state`). F5 mirrors and extends both moves: split `studio.js` into `App.studio.{...}` helper sub-modules under `static/js/areas/studio/` (paralleling `static/js/areas/chat/`); consume F4's shared vocabulary verbatim where it applies; and **invent the next round of canonical primitives** as new visual surfaces land — `.section-nav` + `.section-nav-item` (sidebar section navigation), `.agent-tile` + `.agent-tile-delete` (the tile-grid item), `.tablist` + `.tab` + `.tabpanel` (the tab idiom), `.modal-overlay` + `.modal-dialog` + `.modal-actions` (the modal helper), `.form-actions` (the right-aligned action cluster used by editor save/delete/back and likely admin save/cancel in F6), `.editor-header` (the agent-name + description block above the tablist; admin's provider editor will likely need an analogous header). Every primitive lands in `components.css` (`@layer components`) under the F4 vocabulary contract: NEW canonical class names that future areas (F6 admin) consume, with per-area overrides only for genuine differences. The class-composition migration discipline from F4 leg 02 carries forward — preserve test selectors via composition (`<button class="agent-tile" data-testid="agent-item">`), never via rename. Net effect at F5 close: `components.css` grows ~120-160 LOC; `studio.css` shrinks (target ≤ 60 LOC, was 69 pre-F5; per-area file holds only studio-specific overrides + tile-grid layout); admin (F6) inherits a richer shared vocabulary so its alignment flight can be primarily a CSS-class migration rather than a CSS-invention exercise.

- [x] **`App.confirmDelete` and `App.confirmDialog` — one helper or two?** — **resolved**: TWO helpers, both exported. **`App.confirmDelete(itemEl, onConfirm, opts)`** is the two-step in-place confirm; `opts` enumeration (must be specified explicitly because chat and studio differ in transport, title selector, and post-delete cleanup): `{titleSelector?: string, confirmLabel?: string, revertMs?: number}`. Default `titleSelector` is `[data-confirm-title]` (a new attribute hook on the title element); chat and studio both add it to their existing title elements during migration. Default `confirmLabel` is `'Confirm delete?'`. Default `revertMs` is `3000`. The `onConfirm` callback signature is `(itemEl, revertFn) => void` — the helper passes a `revertFn` so callers can roll the UI back on transport failure (e.g., studio's DELETE fetch fails). For chat, `revertFn` is unused (WS delete is fire-and-forget); for studio, the catch handler in the fetch promise calls `revertFn()` and surfaces a flash. **`App.confirmDialog({title, message, confirmText, cancelText, onConfirm, onCancel})`** is a true modal dialog with focus-trap, Escape cancel, Enter confirm. They serve different UX needs: in-place confirm for single-action destructive (delete one tile), modal for multi-option / blocking decisions (discard unsaved changes). Consolidating them would either bloat the in-place case or cripple the modal case.

- [x] **Tablist activation mode** — **resolved**: **manual activation**. Arrow keys move focus + visual highlight only; Enter / Space (or click) commits the tab (mutates URL via replaceState + reveals panel). Auto-activation would mutate the URL on every arrow-key press (Right arrow rotates through three URL states, polluting browser history even with replaceState). Manual activation is the W3C ARIA recommendation for tabs whose activation has side effects (URL change, panel content load). Implementation requires roving `tabindex`: only the active tab carries `tabindex=0`; others carry `tabindex=-1`. After arrow-key navigation, focus moves but `tabindex` does NOT update until activation; the `App.tabs` helper updates `aria-selected` + `tabindex` together at activation time.

- [x] **`App.tabs` helper API** — **resolved**: callback-style — `App.tabs(tablistEl, panelsEl, {onChange, initial})`. `tablistEl` is the `<div role="tablist">`; `panelsEl` is the parent of the three `<div role="tabpanel">` panels (helper finds them via `[role="tabpanel"]` selector). `onChange(tabId)` fires on activation (after URL replaceState); `initial` is the tab id to activate on mount (parsed from hash by the studio area, defaults to `'general'`). Returns a small object with `{activate(tabId), getActive()}` for imperative control if needed (e.g., switching to General when a Test button click wants to focus the test result span). The `aria-controls` attribute on each `<button role="tab">` references the corresponding panel's `id`; the helper enforces this mapping.

- [x] **`App.confirmDialog` focus-trap depth** — **resolved**: full Tab + Shift-Tab cycling within the dialog (not just the minimal steal-on-open + restore-on-close). Implementation: on dialog open, query all focusable descendants (`button, [href], input, select, textarea, [tabindex]:not([tabindex="-1"])`); track `firstFocusable` and `lastFocusable`; on `keydown`, if Tab + activeElement === lastFocusable, prevent default + focus `firstFocusable`; if Shift+Tab + activeElement === firstFocusable, prevent default + focus `lastFocusable`. WAI-ARIA 1.2 says modal dialogs SHOULD trap Tab; this is achievable in ~30 LOC. **Fallback**: if the leg 04 (now leg 04 post-merge) Adaptation Criteria fires and Tab cycling proves problematic, fall back to minimal trap (steal + restore + Escape only) and document the residual gap as a NEW item in this flight's Known Issues — not just a future debrief recommendation.

- [x] **`window.confirm` migration in existing studio.js sites** — **resolved**: studio.js currently has two synchronous `window.confirm` sites (`studio.js:175-176` in `selectAgent` dirty-check and `studio.js:189-190` in `enterCreateMode` dirty-check). `App.confirmDialog` is async (callback-based), so the guard-and-return pattern doesn't translate directly. **Restructure**: the click handlers dispatch the dialog and the dialog's `onConfirm` callback invokes the real navigation; the `onCancel` is a no-op. Equivalent to: `if (dirty) App.confirmDialog({onConfirm: () => doNavigate(target)}); else doNavigate(target);` Captured as part of leg 04 (post-merge) implementation.

- [x] **Sidebar section nav idiom** — **resolved**: vertical list of three buttons, each a `<button>` element with `aria-current="page"` on the active section. Mirrors the section-nav pattern that admin uses for category nav (admin.js's category list). Keyboard: Tab to enter the list, Up/Down arrows to move between sections (W3C `tab-like` behavior), Enter to activate. Same focus ring as the rest of the design system.

- [x] **`beforeunload` scope and lifecycle** — **resolved**: only fire when `dirty === true`. Idle/clean state must NOT show the browser's native dialog (it's annoying when the user has nothing to lose). **Lifecycle** (corrected for F3 area-lifecycle reality — `app.js:109-186`): register the `beforeunload` listener ONCE at the studio area's `init()` time (which runs once per area lifetime, gated by `initialized[areaId]`). **Do NOT remove on `deactivate()`** — `deactivate()` fires on every cross-area transition (chat → studio → chat would remove the listener and never re-register), which would silently break tab-close protection. The listener body reads the studio area's closure `dirty` flag as the sole gate: when in another area, `dirty` stays `false` because the editor isn't mounted; when in studio with unsaved changes, `dirty` is `true` and the listener calls `e.preventDefault(); e.returnValue = ''`. Listener persists for the lifetime of the page; the closure-flag-as-gate is the simpler and more correct contract.

### Design Decisions

**Three-section sidebar with hash-routable sub-section navigation**: replace the agents-only flat sidebar with a header (title "Studio") + three section buttons (Agents / Knowledge / Tools) + a content pane that renders one of three sub-views. URL contract: `#studio` redirects to `#studio/agents`; `#studio/{section}` selects the section. The `serializeState()` returns `{section}` (or `{section}/{name}[/{tab}]` for agent-editor sub-state); `hydrateState(sub)` parses and dispatches.
- Rationale: matches the three-area mental model the user articulated. Aligns with the M04 navigation-state-survives-refresh criterion. Establishes a sub-section pattern that admin (F6) can mirror.
- Trade-off: extends the studio area's hash-routing complexity from 1-level (agent name) to 3-level (section / name / tab). The serialize/hydrate contract carries the cost; it's bounded.

**Agent tile grid replaces the flat list**: Agents section renders a CSS-grid (`grid-template-columns: repeat(auto-fill, minmax(280px, 1fr))`) of tiles. Each tile is a `<button class="agent-tile">` with name, 2-line-clamped description, and a provider/model footer caption. Hover/focus-within reveals a delete X-button (top-right). Click → enter editor. Keyboard: Tab/Shift-Tab cycles tiles + X-buttons; Enter/Space activates; X-button keydown-bubble-fixed.
- Rationale: tiles are the right density for an inventory of configured agents (typical N is 3-20). Matches the visual paradigm of modern app inventories (Linear projects, Stripe products). The "+ New Agent" button stays in the header for consistency with chat.
- Trade-off: tile grid uses more vertical space than a list. Acceptable; agent configuration is not high-frequency.

**Tab idiom: W3C ARIA `role="tablist"` with manual activation, hash-encoded active tab**: this flight establishes the codebase's first tab idiom. `<div role="tablist">` containing three `<button role="tab" aria-selected="..." aria-controls="..." tabindex="0|-1">` elements; below it, three `<div role="tabpanel" id="...">` panels (one shown per active tab). **Manual-activation keyboard**: Arrow Left/Right within the tablist moves focus + visual highlight only (no URL mutation); Home/End jump to first/last; Enter or Space commits the focused tab (mutates URL via `replaceState`, fires `onChange`, updates `aria-selected` and roving `tabindex`); Tab moves out of the tablist into the active panel's contents. Manual (rather than auto-on-arrow) activation prevents URL pollution from arrow-key roving and aligns with W3C ARIA Authoring Practices for tabs whose activation has side effects. Active tab is reflected in the URL (`#studio/agents/{name}/{tab}`) so refresh restores it.
- Rationale: ARIA-recommended pattern; well-understood by screen readers; establishes a clear `App.tabs(tablistEl, panelsEl, {onChange, initial})` helper for F6 to reuse if admin wants tabs. Hash-encoded active tab fulfills the M04 "navigation state survives refresh" criterion at the sub-page level too.
- Trade-off: the tab helper is new code (~60-90 LOC) and requires its own keyboard-a11y test coverage including roving-`tabindex` correctness. Worth it; the pattern is going to recur.

**`App.confirmDelete(item, onConfirm, opts)` extraction (F4 debrief recommendation 2)**: F4 left chat with an inline two-step delete-confirm pattern; studio has its own. F5 extracts a single canonical implementation: first click marks the item with `.confirm-delete` class, changes label to "Confirm delete?" (or `opts.confirmLabel`), starts a 3s revert timer; second click within window calls `onConfirm()`. Chat's existing call-site migrates to the helper as part of this leg; studio's tile-grid delete uses it from day one. Lives in a new `static/js/confirm.js` (or `App.confirm.{delete, dialog}` namespace).
- Rationale: the third site (admin, F6) is imminent; promote now. Same pattern, one source of truth. F4 debrief flagged it explicitly.
- Trade-off: chat.js gets touched as part of a studio flight. Mitigated by treating the chat migration as a low-risk swap (existing tests catch behavior regressions).

**`App.confirmDialog({...})` modal helper for unsaved-changes**: NEW modal-dialog primitive. `<div role="dialog" aria-modal="true">` with focus-trap + Escape-cancel + Enter-confirm + restore-focus-on-close. Used by: back-button when dirty, sidebar section change when dirty, tile click when dirty. The `beforeunload` listener handles tab-close (uses the native dialog because that's the only intercept point browsers expose).
- Rationale: a modal is the right primitive for blocking decisions. Native `window.confirm` is functional but ugly; users notice. Establishing the modal helper now also unblocks future "are you sure you want to..." flows in admin.
- Trade-off: focus-trap correctness is non-trivial (Tab + Shift-Tab must cycle within the dialog; the dialog must steal focus on open and restore on close). Dedicated leg with browser-test coverage.

**Test button reuses provider-test endpoint**: the General tab's Test button POSTs to `/api/providers/{provider_config_id}/test` (the endpoint lives at `the_one/interfaces/web/api.py:538-590` — `/api/...` routes are in `api.py`, not `app.py`). Empty request body; response shape `{status: "ok"|"error", detail: str}`. Renders the response in an `aria-live="polite"` span (mirrors `admin.js:716-738`). Disabled when `provider_config_id` is unset. NO new endpoint; NO change to the existing endpoint.
- Rationale: gives the user immediate "is my LLM config working" feedback without a backend addition. The endpoint already runs a real chat + tool-use validation, so it's a meaningful test. A future flight can layer a per-agent test endpoint.
- Trade-off: tests the provider, not the full agent config (system prompt etc.). Documented in the General tab's Test button hover-tooltip.

**Advanced section: STUB only (excludes `max_iterations`)**: the General tab's Advanced section is a collapsible region with disabled inputs for temperature, top_p, and max_tokens, plus a "Coming soon — provider-bound config in a future flight" caption. NO storage, NO transport plumbing, NO schema migration for those three. The currently-existing `max_iterations` field on `AgentConfig` (`config.py:91`) is REAL storage and stays in the General tab's main form (NOT inside the Advanced stub) — rendering it disabled would lie about the persistence model.
- Rationale: the user explicitly asked for stub. Real provider-bound config requires a per-provider config schema (`LLMProvider.config_schema()` classmethod returning `{key: {default, min, max}}`) plus an agent-model field plus transport plumbing — easily a flight by itself. Defer cleanly. Keeping `max_iterations` outside the stub preserves the truth-in-UI invariant.
- Trade-off: the user sees the Advanced section but can't interact with it for the duration of F5. Acceptable; the placeholder communicates "coming soon" clearly.

**Knowledge tab + Knowledge sidebar section + Tools section sidebar = stubs**: each is a centered `.empty-state` with one sentence. No interaction. The Knowledge tab on the agent editor explicitly notes that knowledge bases can be attached to multiple agents. The standalone sidebar Knowledge and Tools pages note that they're for management and curation, not attach.
- Rationale: communicates the future shape without committing implementation. Aligned with the "stubs literally just mostly blank with one-liner" user direction.
- Trade-off: the stub pages add navigation surface area that won't be useful for at least one mission. Acceptable; users understand "coming soon" empty states.

**Save button placement: top-right of the editor, next to delete and back**: three-button cluster at the top-right of the editor: `[← Back]  [Delete]  [Save]`. Save uses `.btn-filled-cyan` (same as chat's send button); Delete uses `.btn-muted-destructive`; Back is a tertiary `.btn-outlined-cyan` or a text-only button. Save is disabled when not dirty. All three are keyboard-reachable.
- Rationale: matches the user's explicit direction ("a save button up by the delete button"). Keeps destructive + persistent + navigational actions visually grouped.
- Trade-off: takes top-right real estate from the agent name. Acceptable; the name lives below the action cluster as a heading.

**No backend changes in F5**: every requirement maps to frontend work. No new endpoints, no schema migrations, no agent-model fields. The provider-test endpoint is reused. The agent CRUD endpoints are unchanged.
- Rationale: keeps F5 frontend-pure (the mission is "UI Maturity"). Backend additions (Advanced config storage, per-agent test endpoint, MCP integration, KB attachment) all belong to future flights.
- Trade-off: the General tab's Advanced section is a stub; the Knowledge tab is a stub; the MCP subsection of the Tools tab is a stub. The user explicitly asked for these stubs.

**Design-system contribution as a first-class concern (mirrors F4 leg 02 ethos)**: every new visual primitive lands in `components.css` (`@layer components`) as canonical vocabulary, NEVER in `studio.css`.
